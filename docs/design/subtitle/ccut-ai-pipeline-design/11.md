# 11. Orchestration, Progress and the CLI Command Surface

> From [ccut transcript post-processing AI pipeline design (polish / segment / chapter / translate / subtitle alignment)](../ccut-ai-pipeline-design.md)

## 11.1 Stage Dependencies and Automatic Orchestration

```
asr ──▶ polish ──▶ segment ──▶ chapters
              └──▶ translate(lang) ──▶ display-split(lang)
```

- `ccut auto <media> [--lang zh]`: transcribe → (by default) polish (which also performs the first segmentation) →
  if `--lang` is given, translate and align → **one closing round of targeted re-alignment**;
- The closing refinement closes the loop between detection and repair: alignment warnings from `check` only go into `warnings`
  (they do not affect `ready`). If the pipeline stopped at translate, these auto-fixable defects would stay in the report
  indefinitely, waiting for a human. After translation, auto runs one round of the `refine-align` flow in place (check → collect hotspots →
  `translate --align-only --sentences …` → re-check), at most one round per language and at most 40 sentences. This auto sub-call does not
  get a fresh global align repair budget and gets no extra continuation rounds; after the re-check, it terminates regardless of the
  result. The result lands in the envelope at `data.refine[]`
  (`lang`/`rounds`/`refined`/`remaining`/`deferred`); what remains is handed to an explicit `ccut refine-align`. `--no-refine` turns
  this closing pass off. If this round fails, auto's `status` is unchanged: translation and alignment are already on disk, and the failure is
  explained only in stderr and in `data.refine[].error`;
- Before each stage starts, dependency stamps are checked: before translate, a segmentation is ensured (`ensure_segmentation`), but
  **manual layout editing takes priority**: when the `asrLayout` stamp shows manual intervention, an empty pin is passed and nothing is overwritten;
- When the transcript has manual text edits (the `asr` stamp no longer matches), `--polish` defaults to flipping to no polish
  (the current literal-translation state); an explicit `--polish` can force it;
- `ccut check` reports the stale state of each stage and the `next` suggested command (the `stale` error class is clear enough to branch on).

## 11.2 Studio Projection and Stage Commit

The CLI uses `studio/data.json` to carry the projection of subtitle body text, and `studio/progress.json` to carry the
high-frequency stage status. The commit order is a hard constraint:

1. Stage outputs are atomically written to their owning source transcript; for a single source that is `transcript.json`; timeline translation may update several `transcripts/<srcId>.json` in one pass;
2. `studio_projection::refresh` atomically rebuilds `studio/data.json`, `rev + 1`, and writes `contentFingerprint`. If the project lacks `studio/` or `studio/data.json` (`ccut auto`
   writes directly into a directory that has not had `project create` run), the skeleton and default data are first self-healed, then the refresh runs. Projection is
   not an optional step: a missing Studio no longer degrades into a silent skip;
3. `progress.json` is updated with the same fingerprint, and only then is the current stage marked complete or the next stage entered.

While a run is in progress, `progress.json` may also carry `callsDone` / `callsTotal` / `callsActive`
(instantaneous in-flight counts self-reported by the provider lanes, cleared on stage change), `callsRetried`, `activity`,
`inFlight`, `flow`, `lang`, `taskId` and `error`. These are all backward-compatible optional fields. Batch translate/brief extract still commits in the order above
as soon as a single page's result is ready; the whole batch finishing is not treated as the gate for refreshing the body. `flow`/`lang` are written by the translation flow
before it enters a long silent stretch (`begin_with_context`). When the agent path dispatches a new task directory (the alignment stage is a new directory), it keeps this
ownership as long as it is in a translation/alignment context: file-v1 payloads are HTML/Markdown, and failing to read a language does not mean there is no target language. Only a new task
from a non-translation flow clears the `lang` left over from the previous run.

**Wave observability** (`activity` / `inFlight` / `callsRetried` / estimated `pct`). The polish chain is not a single wave of calls: per-page polish (up to 3 attempts per page) → review of low-similarity sentences → seam-merge judgment (≤2 rounds) → splitting of over-long paragraphs (≤3 rounds) → punctuation repair of long sentences (≤3 rounds), and each wave adds new calls. If only the cumulative `callsDone/callsTotal` is reported, the user sees the denominator grow for no clear reason, with a pile of `retry 2/3`, and cannot tell what is happening now or why it is retrying. So the provider executor (the in-memory ledger in `ProviderLlm`) additionally self-reports:

- `activity`: the current wave phrase, `{wave}[ · round {n} | · attempt {n}] · {this-wave done}/{this-wave total}`.
  The wave phrase is chosen by kind: `analysis` 分析上下文 (analyzing context), `speaker-repair` 说话人归属修复 (speaker attribution repair),
  `speaker-names` 推断说话人实名 (inferring speakers' real names),
  `polish` 逐页润色 (per-page polish), `polish-retry`
  低相似度句复核 (review of low-similarity sentences), `seam-repair` 页缝合并判定 (page-seam merge judgment), `segment-repair` 超长段落补切 (splitting over-long paragraphs), `punct-repair` 长句标点补修 (punctuation repair of long sentences), `segment`/`segment-index` 语义分段 (semantic segmentation), `chapters` 生成章节 (generating chapters), `translate` 整句翻译 (full-sentence translation), `brief`/`translate-brief` 提取术语与风格 (extracting terminology and style), `align*`
  拆分并对齐双语字幕 (splitting and aligning bilingual subtitles); everything else falls back to the stage action. **This wave** = one batch dispatch; a retry round is a new batch, and it is not the same basis as the cumulative `callsDone/callsTotal` across waves. `detail` correspondingly expands to
  `"{action} · {activity} · 已完成 {done}/{total} 次模型调用"` (completed {done}/{total} model calls) (the first segment is still the action, so the client's phase keyword matching is unaffected; when the wave phrase equals the action, it is not repeated).
  The agent path writes an `activity` of the same shape from the request/response counts in the task directory.
- `inFlight`: `[{id,kind,attempt,retryReason?,startedAt}]`, earliest-started first. The call log `logs/llm/<kind>.jsonl` is only written when a call **finishes**, so a request still waiting for its response was completely invisible before; the in-flight ledger fills exactly that gap. Registration and removal are guaranteed by an RAII guard, so success, failure, cancellation and panic unwinding all clear the entry. `callsActive` takes the ledger length directly, so the two share one source. Tail-latency hedge replicas are also registered (they really are an in-flight request), but the cumulative `callsDone`/`callsRetried` count them once per index only. The agent path does not report `inFlight`.
- `callsRetried`: the number of completed calls with `attempt > 1` (cumulative basis; hedge replicas are not counted).
- Estimated `pct`: the polish chain itself does not write `pct`, and once a call completes the client treats progress as determinate yet can only get 0%. So when `linesTotal` is empty, a monotonically non-decreasing estimate is written per wave: `analysis` 2→6, `speaker-repair` 6→8, `polish` 8→75, `polish-retry` 75→82, `seam-repair` 82→88, `segment-repair` 88→95, `punct-repair` 95→99, `speaker-names` 99→100, other kinds 5→95, linearly interpolated within the wave by this batch's `done/total`.
  This is an **estimate**. A real `pct` written by the flow itself (per-sentence checkpoints in translate/align) takes priority, and the stage commit still writes 100. The agent path (`--llm agent`) uses the same range table and the same gate: at dispatch and at `task submit` it interpolates by the request/response count of **this kind** in the task directory (the same task directory may successively hold the brief, full-sentence translation and `align-rewrite`, so counting by the directory total would mix them); submit only carries the estimate into the registry if the projection still belongs to this task/stage. `pct` is on a **per-stage** basis: it resets to zero and restarts when translation enters alignment; clients that need a whole-run basis (the App translation run-state header's four-stage ladder and the translation task card `translate_badge::translate_run_pct`, and the Web read-only progress `jobDisplayPct`) convert by stage themselves.

When a command ends with a terminal error (unified in `events::error`), if progress is still active it writes `error`, zeroes `callsActive` and resets `inFlight` to `[]`. This lets the client show the failure reason in the Running dialog, rather than stalling on an in-flight request that will never return. Projects that are already ready, or unrelated to this failure, are unaffected.

Translation validates all sources for each page first, then atomically checkpoints per source; so the web view shows translations page by page, and if the process crashes leaving a cross-source half-page, the next idempotent resume converges. Polish, alignment, transcription,
chapters, speaker renaming and page-edit write-back reuse the same refresh function. If body projection fails, the transcript results already written are kept, but progress must not advance. The page shows the completion tick only when `contentFingerprint` matches between progress and data; when they differ it shows “正在同步字幕内容” (“Syncing subtitle content”).

`ccut studio sync <project>` provides an explicit rebuild entry point; Python `studio_sync.py` is only a compatibility shim.

## 11.3 Command Surface (aligned with the CLI design doc; only the AI stage increments are listed here)

```bash
ccut auto <media|url|project> [--download-dir DIR] [--lang L]...
          [--polish/--no-polish] [--no-refine] [--llm MODE]
ccut polish <project> [--repair --paragraphs p1,p2]   # full / targeted re-polish
ccut segment <project>                                 # segmentation only (rarely used; usually bundled with polish)
ccut chapters <project> [--target N] [--title-style S]
ccut translate <project> --lang L [--stale-only] [--align-only [--sentences …]] [--fit N]
ccut review list <project>
ccut review accept|reject <project> polish|translate|chapters
ccut check <project> [--for srt|mp4|…] [--lang L] [--strict]
```

`polish`, `chapters` and `translate` all support `--review`: the engine completes all validation on in-memory candidates and
writes only `ai/reviews/<kind>.json` (containing the body baseline SHA, the candidate transcript and a summary), without overwriting
`transcript.json`. `review accept` re-checks the baseline under the project lock before committing the body and refreshing Studio; if the body has
already been changed by the App, Studio or an Agent, it returns `stale`. `review reject` only marks the candidate
`rejected`; the body stays unchanged.

For timeline projects, `--sentences` uses routing keys of the form `srcId:s-…` (the slash form is also accepted); a bare `s-…` is accepted only when it is unique across the whole project, and ambiguity consistently returns `ambiguous`. A cross-source translate review saves a baseline and a candidate per source, and accept validates all baselines once before writing.

Targeted re-polish (`--paragraphs <p-…>`): the requested paragraph ranges are first sorted by position, and adjacent or overlapping ones are merged into a single scope before paging (20 consecutive paragraphs make 1 page, not 20 single-paragraph pages), with no carry-over. `ai/polish.json` is **merge-written**: sentence records and suggestions inside the processed set follow this run, while those outside it (including sentences still on fallback) are kept as-is; `fallbackSentences` is the whole-article basis after the merge; `scopedRun{paragraphs, retainedSentences, runFallbackSentences}` records this run's details. Only an old artifact with the same fingerprint as `stages.polish` takes part in the merge; otherwise the whole file is overwritten. Without this semantics, a `polish-fallback` fix that re-polishes only some paragraphs would wipe the fallback records of the rest and produce false-negative blockers.

## 11.4 Three Writing Tools (`summary` / `blog` / `titles`)

```bash
ccut ai summary <project> [--instructions "…"] [--lang L] [--force]
ccut ai blog    <project> [--instructions "…"] [--lang L] [--force]
ccut ai titles  <project> [--instructions "…"] [--lang L] [--force]
```

These three are **tools that read a draft and write text**, not pipeline stages: they do not write `transcript.json`,
do not write `stages.*`, and are not in the §3.3 staleness rule table, so they have no `--review` candidate channel
and no `ccut review accept` entry. The only prerequisite is a non-empty `transcript.json` in the project.

**Input shape**: the draft is derived from Sentences (`derive_cues` → `derive_sentences`) and rendered as numbered lines `[n] original text`. The model may only cite **sentence number `n`** and never writes timestamps itself; `summary`'s `t` is back-filled by the engine from `Sentence::start(doc)`. This is not about saving tokens: it makes “timecodes fall within the draft's range” a structural fact rather than a validation item. An out-of-range sentence number is judged `Malformed` and retried, and is **not clamped**, because clamping would quietly turn a hallucination into a plausible-looking time point.

**Paging**: the same tier as chapters (8000 words, overridable with `CCUT_LLM_PAGE_WORDS`). A single page produces the final output in one call directly. Multiple pages first Map (extract key points per page, page id `mNNN`, via `complete_batch_retry_with`; both the agent multi-worker path and the provider multi-lane path run this concurrently), then Reduce (page id `final`) writes the final output from the key-point excerpts. Excerpt lines have the same shape as draft lines (`[n] …`), so the final-output prompt is shared by both paths.

**Artifacts** (the version-directory semantics of `ArtifactWriter`):

```
ai/<stage>/
  vNNN/result.json     flat, one level: ccutWriting/kind/version/createdAt/lang/instructions/
                       model/inputFingerprint + payload fields merged in per tool
  vNNN/pages/*.md      file-v1 per-page attempt archive
  vNNN/manifest.json
  latest.json          {ccutWriting, kind, version, dir, result, createdAt, lang,
                       instructions, inputFingerprint} (just a pointer; does not copy the payload)
```

Payload fields are shaped per tool: `summary` = `"points":[{"t":<seconds>,"text":"…"}]`;
`blog` = `"title"` + `"markdown"`; `titles` = `"candidates":[three items]`
(too many gets truncated, too few triggers a retry: “exactly three” is a contract, not a suggestion). The result is deliberately **not** wrapped in an extra `result` object: the artifact is itself the result, and one more layer would only make readers write one more `["result"]`.

**Reuse and follow-up fine-tuning**: when the draft fingerprint matches, `--lang` matches, the previous version also had no instructions, and neither `--instructions` nor `--force` is given, the previous version is reused directly (`reused: true`, zero model calls; the envelope shape matches a fresh run: `{kind, reused, version, dir, path, result}`). Passing `--instructions` counts as a follow-up fine-tune: it is never reused, and the previous artifact is read via `latest.json` and injected as context at the **tail of the user message** (order: media background → previous artifact → custom instructions, with the instructions last and highest priority). Placing them in the user message rather than the system prompt keeps the prompt cache intact. Every run produces a new `vNNN`, so the fine-tuning chain stays traceable rather than being overwritten in place.

**Progress**: writes `studio/progress.json` and jobs events; `jobStage` takes each tool's own kind name (`summary` / `blog` / `titles`), and `detail` is the App's MODEL ACTIVITY copy; on finish it returns to `active: false` / `phase: "ready"`. The three-stage rows are derived from the transcript, and **no stage completion stamp is written** (going through `complete_stage` would record “polish complete” as a fact). Known limitation: `ccut_jobs::studio::Stage` has only three phases (polish / translate / split-align), so writing can only borrow `Stage::Polish`'s `phase` (the ownership gate for fine-grained progress is `phase == stage.phase()`). As a result, during a run the three-stage row shows “polish” as active, and it is restored at finish.
