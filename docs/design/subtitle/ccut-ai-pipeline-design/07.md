# 7. Stage 3: Chapters (chapters)

> From [CucCut transcript post-processing AI pipeline technical design (polish / segmentation / chapters / translation / subtitle alignment)](../ccut-ai-pipeline-design.md)

## 7.1 Contract: file-v1 HTML (since 2026-08)

Chapters have used the file contract since 2026-08 (for the historical contract of a single whole-document NDJSON+`json_object` call, see §7.5).
The carrier is in [`filepipe/chapters_html.rs`](../../../../core/crates/ccut-flow-core/src/filepipe/chapters_html.rs):

```
Input (chapters-source/1):
  <article data-ccut-format="chapters-source/1" data-part="k/N"
           data-range="HH:MM:SS–HH:MM:SS" data-total="HH:MM:SS" data-aim="N" data-project-fp="…">
    <p id="p-<first-word-id>" data-at="HH:MM:SS">full paragraph text</p>…
Output (Map page and Reduce outline have the same shape): one entry per chapter, in time order
  <h2>chapter title</h2>
  <p class="summary">one-sentence summary (≤20 words)</p>
  <p id="<start paragraph id>">first few characters of the paragraph</p>
```

- Paragraph projection is the same as §18.5 (`derive_cues` + `derive_paras`, paragraph id `p-<first-word-id>`). `data-at` is the offset relative to the media start; it is read-only and never written (chapters need a sense of duration; the model never writes times back).
- User-level settings (`--title-style`, `--instructions`, recording background) go into the system prompt. Per-page differences (which part, the time range, the `data-aim` unit/chapter target) go only into carrier attributes. The agent-path contract file is unique per kind and cannot differ page by page.
- The output **contains only what code cannot infer**: the tail anchor and `end` are not part of the protocol (`end` is backfilled deterministically from the next chapter's `start`). The opening fragment of the first paragraph is the fallback for the anchor id. If the id is miscopied (`p-g1203.0` → `p-g1230.0`), it is repaired by a unique fragment match (`anchor-repaired` diagnostic). If nothing matches, the row is dropped (`unknown-id`).
- Parsing uses html5ever, and tag names are not part of the protocol: h1–h6 or `class="title"` count as titles, elements with an `id` count as anchors, and the id-less text blocks between a title and its anchor count as the summary. The `<section id>` container form, code fences and chatter are all tolerated.
- Problem codes: `missing-id` (no anchor after a title, or no rows at all), `unknown-id`, `empty-title`, `chapter-overflow` (Reduce only). Repeated anchors keep only the first row (diagnostic). `temperature 0`, at most 3 attempts per page; the retry reason is the structured problems.

## 7.2 Paging and Map/Reduce (long recordings)

Paragraphs are split into evenly balanced pages by word budget (`budgets::CHAPTERS` = 8000 words, overridable by `CCUT_LLM_PAGE_WORDS`). A paragraph is atomic: a single paragraph over budget gets a page to itself.

- **Single page** (≤ about 100 minutes): one call produces the chapters directly, with `data-aim` = the global target.
- **Multiple pages**:
  1. **Map** (kind `chapters`, all pages in parallel): each page is cut into “topic units”, with `data-aim` ≈ page duration / granularity in seconds, clamped to 2–40 (the same tier as chapters). In testing, deepseek-v4-flash in non-thinking mode copied the outline verbatim all three times when asked to “merge to data-aim”, so Reduce is responsible only for page seams and unified naming. The opening of a non-first page may continue the previous page's topic; the first unit need not start at the top of the page.
  2. **Reduce** (kind `chapters-outline`, one small call): concatenates all units in order into an outline `chapters-outline/1` (`<h2 data-at>` + summary + `<p id>` fragment). At page seams it inserts `<hr data-seam="k|k+1">`, and the root node carries `data-units` / `data-aim`. The model merges, prunes and unifies naming according to the global `data-aim`, and anchors may only be taken from unit starts. Row guardrail: if the output exceeds `aim + max(2, aim/5)` rows, it reports `chapter-overflow` and retries. If it is still over after three attempts, the attempt with the most rows is adopted (more chapters, but full coverage). Even a 7-hour recording's outline is only about a hundred rows, a few thousand tokens.
  3. Seven-step deterministic cleanup (§7.3), then write back.
- Tiered degradation; the whole thing never fails: if a page's Map has no usable rows after three attempts, that page degrades to an **untitled placeholder unit** (`<h2 data-untitled="true">` + a “no summary” note, anchored at the top of the page), which Reduce names or merges into a neighboring chapter. If all three attempts yield rows but with problems, the attempt with the most rows is adopted (`degraded: true`). If all three Reduce attempts fail, the Map units are adopted directly as chapters (the untitled placeholder unit is skipped, and its time merges into the previous chapter). Terminal errors (auth, model not found) and Cancelled still abort immediately, as before.

## 7.3 Deterministic cleanup

Model output goes through seven cleanup steps. No step trusts the model:

1. Discard unknown paragraph ids and empty titles;
2. Sort by (segment start time, output order);
3. Deduplicate entries with the same start;
4. **Force the first chapter to start at 0**;
5. Force starts to be strictly increasing;
6. Backfill each chapter's `end = next chapter's start` (the last chapter goes to the media duration).

Written back to the transcript's `chapters[]` (id `c-<base36ms>-<n>`), and `stages.chapters = fingerprint(words)` is committed.

## 7.4 Chapter count and artifacts

- Target chapter count `chapter_count(duration, granularity)`: broad ≈ 10 min/chapter, balanced ≈ 5, detailed ≈ 2.5. The minimum is 2. The maximum **scales with duration**: `max(20, round(hours × 20))` (up to 60 minutes it matches the old fixed 2–20; for 7 hours, balanced ≈ 81, detailed 135, broad 40). The Mac `PolishEstimator.chapterCount` and the GPUI `ai_estimates::chapter_count` are parity copies; all three must change together. `--target` is still the global total and explicitly overrides the formula.
- Per-page attempt archive `ai/chapters/vNNN/{manifest.json, pages/pNNN.src.html, pNNN.out[.aN].html, pages/outline.*}` (§4 layout; the manifest `params` records `pageBudget/granularity/target`). The stable pointer `ai/chapters.json` contains `fingerprint / rows / review / parts`, where `parts` = `{count, pages[]{id,start,end,segments,units,attempts,degraded}, outlineAttempts, outlineFallback}`. It is the first entry point for troubleshooting long recordings.
- The candidate under `--review` is an **overlay shape** (`ai/reviews/chapters.json`, `reviewVersion 4`). It stores only `candidateOverlay.{chapters, stages.chapters}` + `mediaHash/mediaDuration` + `parts`, and no longer embeds the whole transcript. `review accept` changes only these two fields, and baseline validation is by media identity (hash + duration), so editing text during review no longer makes “Replace N chapters” fail.

## 7.5 Boundary sources: the LLM, or chapters supplied by the source

Chapter boundaries are proposed by the model on the paragraph projection and then go through the deterministic cleanup of §7.3. The only exception is **chapters supplied by the source**. When a project is created from a URL, yt-dlp's `chapters[]` and the full video description are stored in `project.json` under `media.sourceMetadata` (the same shape for the App and the CLI download leg). `ccut-flow-core::source_chapters` reads this into structured timestamps: `chapters[]` first, then, failing that, timestamps at the start of description lines (`M:SS` / `H:MM:SS`), or outline lines of the form title + timestamp or timestamp + title at line end. Timestamps over an hour are accepted. Both paths use it:

- **Through the model**: the full outline goes into the `chapters` / `chapters-outline` contract as reference (“Prefer the author's boundaries and titles, still anchor to the input paragraph ids, and only add, remove or merge where the draft clearly diverges”). The default target chapter count becomes the number of outline entries, and when paginating, each page's `data-aim` becomes the number of entries falling on that page.
- **Not through the model** (CLI `ccut chapters --from-source`, and the App chapters page's “use video chapters directly”): each source chapter is snapped by time to a structural start point in the transcript. Paragraph > sentence > cue is searched first in the near window `[-1 s, +2 s)`. If none is found, paragraphs and sentences are widened to `[-4 s, +6 s)` and the nearest is taken. Finally, word starts in the near window are used. If several starts match the same second, it counts as **ambiguous**: the CLI takes the earliest and counts it in `source.ambiguous`, while the App lists the candidates for the user to pick one, or to keep the source time. Source chapters that match nothing keep their source time. Write-back still follows the §7.3 row rules (sorting, same-start deduplication, first chapter pulled to 0, last chapter to media end) and stamps `stages.chapters`, so once saved it is identical to model-chaptered output.

The earlier local embedding-based candidates (the `embedding` / `hybrid` modes and the `--chapter-scorer` parameter) were removed entirely on 2026-08-18 along with the local text-model feature. For the historical design, see [`archive/ccut-semantic-reranker-alignment-design.md`](../../../archive/subtitle/ccut-semantic-reranker-alignment-design.md) (archived).
NDJSON contracts from before 2026-08 (`{"title","startSeg"}` one object per line, `json_object` mode, whole-document single call, single retry) exist only in the historical `json-v0` task directories. `task submit` still lints those by the old NDJSON rules.
