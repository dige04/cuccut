# 8. Stage 4: Translation (translate)

> From [ccut post-transcription AI pipeline technical plan (polishing / segmentation / chaptering / translation / subtitle alignment)](../ccut-ai-pipeline-design.md)

## 8.1 Granularity: persistent unit = Sentence; call order = final timeline

Three granularity levels, each with its own role:

| Granularity | Role | Key |
| --- | --- | --- |
| **Sentence** | Complete natural translated sentence; the unit for dirty detection and persistence | `s-<first-word-id>`; the timeline routing key is `(srcId, sentenceId)` |
| **Page** | LLM call and checkpoint unit | Deterministically paged from the visible Sentence order in the final timeline |
| **transAlign piece** | Display and export split overlay | `<sentenceId>#<N>`; does not own a separate translation source of truth |

In v0.3, sentence derivation prefers the end-of-Cue sentence-final period as the boundary. When there is no sentence-final punctuation, only pauses of at least 1.8s count as semantic sentence boundaries. Natural thinking pauses of 0.6–1.2s still affect only Cue display and the LLM soft markers. As a fallback for long unpunctuated streams, speaker changes and 80 words also serve as boundaries.

Without `timeline.json`, routing degrades to the source sentence order. When a timeline exists, the projector collects cross-source Sentences in the order each audience first appears, deduplicates reused material, and takes the ordered union of visible words for the same source sentence appearing in different clips/cuts. The route ids given to the LLM are opaque keys. Each one also carries its own `sourceLang`, so a single page can safely contain different source languages. Context comes from the global preceding and following source pages, not from the original order of any single source file.

## 8.2 Contract: compact JSON echo

```jsonc
// Request page (user payload)
{ "lang": "zh", "context": "Preceding source: …\nFollowing source: …",
  "lines": [ { "id": "r000001", "sourceLang": "en",
               "source": "Ninety days, eight times the growth.",
               "maxChars": 18, "rt": ["CucCut"] } ] }
// Response: translation only, source not echoed (halves response tokens)
// sample "90 天，翻了 8 倍" = "eight times the growth in 90 days"
{ "translations": { "r000001": "90 天，翻了 8 倍" } }
```

Key points of the system prompt:

- Identity as a professional subtitle translator + Document summary (brief) + style guide + **glossary** (two tiers, `[LOCKED — use target verbatim]` and `[preferred]`, from the glossary in §5.2) + named entities;
- **Understand the whole sentence first, then translate faithfully in the natural word order of the target language.** Per the subsequent alignment stage, “the alignment stage is responsible for mapping the natural sentence back onto the timeline.” The model is told explicitly not to sacrifice word order for alignment;
- `maxChars` is the character budget computed from CPS (reading speed) and the display duration of the group;
- Each line gets exactly one translation. Slash or bracketed alternatives are forbidden. However, terms that contain slashes themselves, such as CLI commands like `/compact`, must be kept verbatim; see the brief glossary slash rule in §10.4. Route ids are treated as opaque strings. Each id appears exactly once and must not be merged, split, dropped, or reordered. Also CJK spacing rules, and Simplified/Traditional handled per the target code.

**Validation**: two-way id reconciliation. Three failure types each fail the attempt and trigger a retry: `unknown id` / `empty translation` / `missing id`. After saving, term violations and CPS violations are counted separately into the check report (advisory, non-blocking).

A CJK-target translation that passes validation goes through the same idempotent AutoCorrect before it is written to `trans`. This step must run before display splitting. If `transAlign.pieces` were generated first and only the whole sentence formatted afterward, the `concat(pieces) == trans` invariant would break. The `align-only` entry point also runs formatting once more before deriving pieces, for compatibility with unformatted translations in legacy projects.

## 8.3 Concurrency

Pages have **no serial dependency** on each other. Rolling context does not use the "previous page translation." Instead it uses static **neighbouring-page source text** (Preceding/Following source). The engine first builds all page requests, then dispatches them in batch through `complete_batch_with`. The agent executor enqueues the whole queue at once, and up to 3 distinct workers claim pages in parallel (`CCUT_LLM_MAX_WORKERS` overrides this; `0` = unlimited, with everything opened according to pendingCount). When it is not overridden and the median duration of workers that have delivered calls is ≥ 90 s, it automatically scales up to `ceil(pendingCount/2)`, clamped to 3..16. The provider executor connects directly and runs concurrently per lane. Priority: `--llm-concurrency <N>` > `CCUT_PROVIDER_MAX_LANES` > config key `llm.maxConcurrent` > default 4, with `0` = unlimited. The command-line switch applies only to this run, and the lane count is resolved once when the executor is constructed.

As soon as each page passes validation, it immediately triggers its callback, checkpoint, and a Studio refresh. Failed pages carry their own `retryReason` and enter the next round independently, without waiting for other pages in the same batch. Glossary matching is computed outside the retry loop, because it is expensive and must not be recomputed just because the JSON was malformed.

Targeted retranslation of a page treats the unselected sentences as read-only frozen context. If the model changes any frozen sentence, the whole page is rejected and never overwrites the old translation. When many frozen sentences on the same page are rewritten at once, attempt artifacts still keep per-sentence diagnostics. However, the `retryReason` injected into the next round is aggregated into a count summary by identical error code + detail, so repeated errors do not crowd out the real repair instruction.

Each page result is first reconciled by route id, then scattered back into the corresponding `transcripts/<srcId>.json` or the main `transcript.json`. Before saving, all source documents are validated. Then each file is replaced atomically in turn, and Studio's projection is refreshed once. A multi-file checkpoint is not a filesystem-level transaction. If the process crashes between files, the sentences already written are recognized on resume by their matching `transSrc` stamp, and unwritten sentences continue processing. So re-entry converges idempotently.

## 8.4 Resumable runs: the sentence id is the persistent unit

The progress file stores a `{routeId → translation}` mapping rather than page numbers. On resume, the valid route set is recomputed from the current final timeline. Changes to paging parameters or clip order do not invalidate translated sentences that already have the same visible-word fingerprint. Sentences that no longer exist structurally are cleaned up from their owning source's `trans` / `transSrc` / `transAlign`. Source translations that are still valid but not currently arranged in the timeline are kept, so assets are not lost just because a sentence was removed from or restored to the timeline.

## 8.5 Incremental retranslation (`--stale-only`)

Group-level dirty detection (§3.3 `transSrc`) plus paragraph-level rerun:

```
staleSentences = { 句 | 译文缺失，或 transSrc stamp 缺失/不等于当前可见词指纹 }
stalePages     = 含任一 stale 句的最终时间线页面
```

- Rebind guarantees that "a small-scope polish → only the touched sentences become stale." Cut/restore makes stale only the sentences whose visible-word set changed. After re-transcription reissues ids, everything is rebuilt.
- **An existing translation with no stamp is treated as stale.** Old data must be re-confirmed against the current visible-word semantics and must not forever pass as fresh.
- The translation input contains only stale Sentences, but the brief and neighbouring-page context still comes from the whole final timeline. The display duration and CPS budget are also computed from the audience's actually visible time window.
- Each result covers only the sentence-level `trans` and `transSrc` of its owning source, and deletes that sentence's old `transAlign`. It then realigns against the exact visible-word id subsequence.
- `--review` candidates save a body-text baseline SHA per source. `review accept` first verifies that no source has changed, then writes any of them, avoiding a half-committed state.

Parameters: page budgets are tiered per executor (`paging::PageExecutor`). Agent: 2000 source words. Provider: 2000 source words. The two tiers are declared separately and currently share the same value. The basis is the `word_count` measure plus §5.3 slack. `CCUT_LLM_PAGE_WORDS` can override both tiers together for tuning comparisons. Also `temperature 0.3`, and retry 3 × 2s. For consecutive translate pages, only source word counts are balanced. Sentence count, serialized character count, and worker slots do not change the number of translation pages. A sentence is the atomic unit of paging and is never split across pages. Align has additional per-item complexity guards; see §9.2. Motivation for the tiers: single-page response time scales roughly linearly with the page's word count. For an agent worker, a 5000-word translate page takes about 5 minutes and align about 11 minutes (measured on Codex thread 01a003ff). A 3571-word talk at the 5000 tier becomes only 1 page, leaving multiple worker slots idle with no parallelism. At 2000 + 10% slack, the largest page is 2200 words, so a ~3500-word talk splits into 2 pages and ~10000 words into 5 pages, giving workers something to claim.

Provider lanes are direct in-process connections with no claim or submit round trip. Single-page time still scales linearly with output tokens, though, and the lanes (default 8) are usually not saturated. Measured on DeepSeek v4-flash with the brief cached: a 3571-word talk takes 1 page at the 4000 tier, 147/208s, versus 2 pages at the 2000 tier, 108/95s. A 9784-word talk takes 3 pages at the 4000 tier, 244s, versus 5 pages at the 2000 tier, 140s, with fewer residual violations. So the provider tier is also set to 2000. The only extra cost is one more brief and the page-leading system prompt. The two tiers are still declared separately and can be tuned independently later. Agent mode dispatches in batches consumed by multiple workers. Provider mode runs direct per-lane concurrency. Both are batch concurrency. Only the concurrency limits come from different environment variables.

Persistent artifacts: each source transcript's `trans[lang]` / `transSrc[lang]` / `transAlign[lang]`. Timeline routes and page state are rebuildable progress, so they get no separate sentence translation file.

## 8.6 Fused alignment: the translation call also yields a block-alignment draft

Motivation (fWZ benchmark, 2026-08-02): a typical short video runs 7 LLM calls, of which align accounts for 4, each answering with only ~1.2k characters. Yet the translation itself was just produced by the same model in the translate call. The information alignment needs can be given to the model at translation time.

Mechanism (enabled by default when `manyToOne`, `TranslateOptions.align: Some(TransParams)`; protocol in [alignment block design §6.1](../ccut-alignment-block-subtitle-split-design.md)):

- **Payload**: only for editable `<p>` that the deterministic criteria already require to split, attach `data-align-words="[1]I [2]didn't [3]go …"` (in-sentence anchor words, one word per ordinal, same basis as `TransAlign.words`; CJK sources counted atomically per `words[]`) and `data-align-needed` (the source side exceeds the single-line display width, or the whole-sentence speech window exceeds the ~7s dwell guard). Short sentences do not repeat the fusion attributes. If their translation unexpectedly overflows the fit, the dedicated `align-edges` still serves as the fallback. The payload contains no source Cue ids or boundaries, no pause hints, and no split suggestions. The model no longer splits the source, splits the translation, or resolves crossings. The system prompt appends a fusion contract section (the `<span data-src>` microformat). The translation contract also keeps the preference for sentence-order-driven output: among equally natural word orders, stay close to the source clause order (simultaneous-interpretation-style sequential rendering), which reduces word-order crossings in display alignment at the source.
- **Answer**: the sentence body is still one complete translation. Inside `<p>`, the model only wraps the translation as `<span data-src="../3 4 5">我们昨天讨论的</span><span data-src="../1 2">计划</span>…`, i.e. minimal natural semantic chunks plus the source word ordinals each chunk corresponds to. Ordinals may be out of order, non-contiguous, or empty, and each ordinal belongs to at most one chunk within a sentence. Spans are transparent to the translation: `element.text()` is still the whole sentence, and body text outside spans counts as a chunk with empty attribution. The translation truth always comes from the `<p>` body text. The sentence is written first, then alignment is considered. Fusion must never distort the translated sentence to fit alignment.
- **Answer-side attributes should be omitted**: `<p>` only needs to keep `id`. `data-align-words` / `data-align-groups` / `data-align-needed` / `data-budget` / `data-rt` / `data-source-id` / `data-sid` / `data-translation` are all **input-only** directives. Every check in `parse_translate_page` / `lint_agent_answer_file` (alignment draft, mandatory `data-rt` terms, `data-editable=false` frozen-sentence detection and existing translation) reads only the **input page** (`TranslatePage` / the rendered payload source), never same-named attributes in the answer. This is why "the answer can safely drop all attributes": it is not lenient validation, the parser simply never reads that copy. Keeping attributes is not an error, since old behavior is tolerated. But the system prompt explicitly asks to omit them. The ideal sentence element is `<p id="s-g1.0">translation</p>`. Frozen sentences likewise only need to echo the existing translation text verbatim, without carrying back `data-editable` or `data-translation`. In a measured run, a 59-sentence translate answer shrank from 25277 characters to 5871 characters (provider output, `on` mode). The `<article>` and each `<section id>` structure must still be preserved verbatim, because locating a sentence depends on which section its id falls in, not on attributes.
- **Acceptance**: the translate side only performs structural pre-checks (ordinals valid and non-repeating; the block text, after normalized concatenation, equals the translation). Once it passes, the draft is handed to the align engine unchanged (`FusionDraft { chunks }`). The engine expands the chunks into soft alignment edges (weight 0.75), merges them with `AnchorAligner` hard edges, and runs the **exact same** deterministic block merge → bilingual DP (`align_block::plan_sentence`) as dedicated `align-edges`. `Aligned` is stored with zero calls (`AlignOutcome.prealigned_sentences`). If a block exceeds hard, the sentence goes to the `align-rewrite` rewrite round. Insufficient evidence (`SentenceLevel`) is **not** accepted directly. It falls back to a dedicated round to obtain block annotations again. So this channel only saves calls and does not lower the standard. A span parse failure only discards the draft and never rejects the whole translation page.

- **Not applicable**: independent/oneToOne modes, `--align-only`, refine-align, and routed (final timeline) translation do not fuse and take the original path. Under the table carrier (`--align-carrier table`), the fused draft still goes through block checking first. Sentences with `NeedsRewrite`/`SentenceLevel` go into the table round.
- **Trailing payload reminder**: if the page has any fused sentence (`on` or `rows`), a plain-text line `Reminder: …` is appended after `</article>` when rendered. Each of `on`/`rows` has its own wording, reminding that "the answer keeps only ids" and that "every sentence with fusion attributes must be annotated, not a few annotated before falling back to plain translation." This is not protocol content: `parse_translate_source` stops at `<article>`, and trailing text at root level is always ignored. The motivation is that in long documents the contract section in the system prompt gets "diluted." In a measured run, deepseek annotated only the first 3 of 59 sentences on a page and fell back to plain translation for the rest. Placing the most critical requirement where the model reads last is the least intrusive remedy. `off` mode has no fused sentences, so no reminder is added.

Expected effect: when the draft acceptance rate is high, translate+align collapses from 1+N calls to 1. When the acceptance rate is low, it does not cost more calls than before. Omitting read-only attributes also makes the answer itself much shorter (see above).

**Switch (`--align-fusion rows|on|off`, default `rows`)**: `rows` (default; see §8.6.1) defines the contract as display-row partitioning, `TranslateOptions.align_rows: true`. After the fifth comparison round met its targets (Trilemma overFit 15%→10%, wall-clock ~60s→16s, Pi Agent 40s vs 86–130s for `on`, and all three width/reading-speed metrics better than `on`), it moved from experimental mode to the default. `on` is the old minimal-semantic-block contract from before that promotion. It still goes through the same `TranslateOptions.align: Some(_)`, just with `align_rows: false`, and is kept as an optional fallback. With `off`, `TranslateOptions.align` is set to `None`. The payload carries no `data-align-*`, the system prompt has no fusion contract section, and the round neither produces nor trusts drafts. The parse side is unchanged: if an answer still carries `<span data-src>`, it is treated only as translation text and does not reject the page. The provider's `parse_translate_page` and the agent's submit-time `lint_agent_answer_file` share this behaviour, each with its own regression test. The switch exists only on `ccut translate`. `ccut auto` internally syncs the default `rows` and does not expose the parameter. `refine-align` does not rerun translation. It always verifies existing drafts against the old `on` contract, and neither follows this default change nor exposes the switch.

## 8.6.1 Row-partition mode (`--align-fusion rows`, default)

Motivation: the fused draft in `on` mode is the "smallest semantic block", and getting from blocks to display rows still requires another round of the align engine's bilingual DP. Since the translation and the line split are the same cognitive load, let the model produce "translate + split into display rows" for the whole sentence in a single translate call. What is saved is not evidence but one more round of questioning.

- **Carrier**: `rows` reuses `on`'s `data-align-words` / `data-align-needed`, and additionally appends `data-align-groups` to the editable `<p>`. This is a deterministic source-side grouping with a duration per group, in the format `firstOrdinal-lastOrdinal@startSec-endSec`, with multiple groups separated by `;`. For example, `1-4@0.0-1.4;5-9@1.4-3.2`. Ordinals are 1-based closed intervals; seconds are relative to the sentence start and fixed at one decimal place (stored internally as integers in units of 0.1 s; rendering, parsing and equality share one source, see `filepipe/translate_html.rs::{render_align_groups, parse_align_groups}`). `data-align-groups` is **rendered only in rows mode**; the carrier shape in `on` mode is unchanged.
- **The answer also needs only ids**: `data-align-words`, `data-align-groups`, `data-align-needed` and the like are all input-only (see the general note in §8.6). The rows contract additionally stresses "every sentence must be marked": the reminder at the end of the payload reads `EVERY sentence that carried data-align-groups — all of them, not just the first few — must come back cut into <span data-src>display rows`. This is because rows is more prone than `on` to falling back to plain translation for an entire later section of a long page (the context freed by dropping attributes is exactly what is used to mark more sentences).
- **Grouping rules** (`engines/align.rs::fusion_groups`, zero LLM, zero randomness): seed boundaries first reuse the first words of existing subtitle Cues on the source side. Two local rules are then added: the previous word ends with a clause punctuation mark (`,;:—–，；：、…`), or the silence between words is ≥ 0.35 s. Groups with fewer than 3 words and shorter than 0.8 s are merged into an adjacent group (preferring the left neighbour; a group at the start of a sentence merges into the right neighbour). Groups longer than 5 seconds or 14 words are recursively split at their largest internal pause (keeping ≥ 2 words on each side).
- **Four hard constraints of the response contract**: each `<span data-src="../a-b">` is **a single, continuous, strictly increasing interval**; adjacent rows abut each other, and all rows together cover `1..N` exactly (in sync with the source word order: row order may not be shuffled for naturalness; when word order does not line up, merge the relevant groups into one row; if the whole sentence cannot fit in source order, degrade to a single span covering `1-N`). **A row may only be one group or a union of several adjacent groups**, and may not be cut inside a group. Each row must be ≤ `fit`, never exceed `hard`, and the reading speed (display units / sum of the group durations covered by the row) must not exceed 6 units/second.
- **Coverage criterion**: `needs_split || source_words >= 8` (`FUSED_ROWS_MIN_WORDS`). This is looser than the `on` mode's "source side already needs splitting": short sentences with enough words also take the align-free pass-through path.
- **Acceptance**: `format_fusion_draft` re-validates `is_row_partition` after AutoCorrect, using the source word count of the stored translation. When `accept_fused_drafts` encounters a row-partition draft, it switches to `align_block::plan_sentence_rows` (block alignment design §6.1): row boundaries are frozen directly as block boundaries, and bilingual DP is run again on candidate cut points inside a row only when a row exceeds `hard`. Rows are never merged across. The written `TransAlign.aligner` is the new label `llm-rows+anchor/1`, while `correspondence` remains `Block`. **Block granularity therefore changes from "semantic block" to "display row"**: downstream field shapes (`blocks[]` / `pieces[]`) and the I3/I4 block-layer invariants are unchanged; there are simply fewer and coarser blocks.
- **Short-row merging**: after grouping into rows and before entries are written, there is a deterministic post-processing step `align_block::merge_short_rows`. The motivation is that in practice the model splits rows one-to-one along source-side groups (the number of rows per sentence is clearly higher than the semantic blocks of regular fusion), so the contract's "prefer merging" wording has almost no effect. Width, reading speed and duration are all computable quantities, so the engine handles this rather than spending another call persuading the model. The criterion applies to two adjacent pieces within the same sentence: if either piece is "too fast" (reading speed > 6 units/s) or "too small" (duration < 1.0 s or width < 6 units), the merge is triggered. However, **the merge guard is graded**: a merge triggered by "too fast" may reach width `hard` after merging (zh 20), because there is no cheaper remedy for reading speed than lengthening the time window. A merge triggered only by "too small" still respects `fit` (zh 16). Both levels also require the merged duration to be ≤ 7 s. This is a deliberate "width for reading speed" trade-off, on the same basis as the `pair_cost` in `on` mode's bilingual DP, where exceeding `fit` is only a penalty and only exceeding `hard` is a hard constraint. In the fourth round of comparison, rows' overFit had already dropped to 1–2%, while cps>6 remained at 12–13% (`on` median 7.9%); letting width give way to reading speed is exactly the missing step. When both sides can merge, the side with the lower reading speed after merging is taken (ties go left, so the result is independent of traversal order); iteration continues until no legal merge remains (each merge removes one piece, so it necessarily converges). **Only pieces (`groups`) are merged; blocks (`blocks`) are not**: blocks still record the source-word-to-translation correspondence the model gave for each row, so downstream bilingual highlighting does not become coarser through merging. Fragments cut by the in-row bilingual DP because they exceeded `hard` are not glued back together by this step (both guard levels are ≤ `hard`, and those fragments were cut precisely because joining them would exceed `hard`). Rows removed by merging are counted in `AlignOutcome.rows_merged`, summarised as `rowsMerged` in `--json`, and shown in the advisory details as `(N short row(s) merged)`. They are not persisted to the transcript, and `aligner` remains `llm-rows+anchor/1`.
- **Soft re-send for a page missing rows**: if a page has at least 3 sentences whose "carrier requested rows" (non-empty `data-align-groups`), and fewer than 30% of those received a valid row partition (`draft.rows`), the whole page is judged to have abandoned row annotation. Measurements show the model occasionally returns a structurally complete, clean answer that keeps only `id`s and gives no `<span data-src>` at all. This is not a bad draft but a page-wide omission, and resending once usually gets rows. The engine resends the page unchanged (same system/user), with `retry_reason` switched to an emphasised version (pointing out that "last time there was not a single display row"). This is a **soft** retry: at most one resend per page, it does not consume the page-level error retry budget (the separate count under `RetryPolicy::SPLIT_THEN`), and it does not reject the page. If the second attempt still lacks rows or the transport fails, the engine gives up and keeps the first attempt's translation and draft; if the second attempt is usable, both the translation and the row draft come from the second attempt (a overwrite for the same batch of sentence ids). The provider and agent executors share the same criterion. `routed` (final timeline) translation does not apply, because that path never runs fusion drafts. The count is recorded as `rowsPageRetries` in `--json`.
- **Fallback** (if any of the following fails, the engine silently falls back to the regular `on`-mode path; a bad draft never enters `problems[]` and never rejects the translation): the partition itself is invalid (`is_row_partition` is false: a gap in the ordinals, not increasing, or not covering N); validation fails after AutoCorrect; locating the block character ranges fails (`chunk_char_ranges` returns empty); a row boundary is crossed by a hard anchor and cannot become a block boundary (`plan_sentence_rows` finds no corresponding block start); or a row exceeds `hard` and the in-row bilingual DP has no solution. A row boundary that fails to fall on a group boundary from `data-align-groups` (`on_groups` is false) **is not a failure**: the draft is accepted as usual, and only the hit rate of the `alignFusionRowsOffGroup` observation hint is counted.
- **Not persisted**: `data-align-groups` is only a hint attribute in the translation request payload. It is recorded together with the page-level audit artifact `ai/translate/<lang>/vNNN` for that round, treated on the same footing as other prompt content. The parsed `FusionGroup` is not written to any field of the transcript and does not enter `TransAlign`. It is used only inside this call to drive the in-row re-split decisions of `plan_sentence_rows`, and is discarded afterwards.
- **Translation page budget reduction**: rows raises the per-source-word call cost by about 1.6–2×. Coverage is widened to ≥ 8 words, and each covered sentence carries one extra `data-align-groups` input (measured on a 30-sentence sample: user payload 8928 → 10206 characters). On the answer side, each sentence must also return `<span>` rows rather than a one-line text per sentence. More importantly, compliance falls as page length grows: deepseek-v4-flash, on a page of 59 sentences, gave row spans only for the first 3 sentences, and the other 56 sentences fell back entirely to plain translation; the same model on shorter pages reliably gave 38/50. Therefore the `agent` and `provider` executors share a smaller tier under rows, [`budgets::TRANSLATE_ROWS_WORDS`] = **800** words (`+10%` slack → a per-page cap of 880 words, `ceil(total words/880)`), instead of the 2000 (`/2200`) of `on`/`off`. A 30-minute talk (about 3500 words) is therefore split into 4 pages run in parallel, with roughly 30 sentences per page. This tier was tightened in one round: first set at `2000/1.67 ≈ 1200`, the fourth comparison round showed that at 1200 words, a 59-sentence page still produced zero spans for the whole page. Together with the soft re-send for missing rows above, this turned the exposure from unrecoverable into recoverable, but the page itself also needs to be smaller: 800 is what falls within the range where measured output reliably gives rows. The override semantics of `CCUT_LLM_PAGE_WORDS` are unchanged: when set, it overrides everything, rows included. The page-split tiers of the align stage are not affected (see §10.4).
