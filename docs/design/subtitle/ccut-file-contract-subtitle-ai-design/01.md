# 1. Goals and motivation

> From [CucCut File-Contract Subtitle AI Pipeline Design (File-Contract Pipeline, v0.3)](../ccut-file-contract-subtitle-ai-design.md)

The current per-page JSON contract has four structural costs:

1. **Token and page-budget waste.** Inbound: the polish request renders words as a sparse map, `{"words":{"<word index>":"<word>"}}`. The keys and quotes cost roughly as much as the body text. (The outbound direction has been `paragraphs/sentences` text since M28, so the waste is mainly inbound.) Each translate page envelope carries `{id, source, maxChars}` per line; fusion mode adds `sourceMarked/sourceWords/needsSplit/sourceBreakHints`. The historical fusion path once cut the translation page budget to 1000 words. After fusion was retired, it was first raised to 3200 words, and the current starting stress-test value is further unified at 8000 words.
2. **Models are not good at it.** LLMs are far more reliable at "edit a document" and "translate an HTML page" than at "produce strictly structured JSON". Structural failures under JSON mode (missing id, wrong nesting, broken escaping) account for most of the retry budget.
3. **Fragmented context.** When translating small pages, the model cannot see paragraph context, so terminology and style drift from page to page. (This is one root cause of the 9× worker style variance found in the translation optimization campaign.)
4. **Not directly reviewable.** JSON payloads are unreadable for both humans and agents. Under the file contract, every intermediate artifact can be opened, read, edited and diffed directly. The diff capability itself is the prerequisite for versioning (§4).

At the same time, this plan is **not a rewrite from scratch**. The agent response loop (`tasks/<taskId>/`) is already file-driven. This plan changes "JSON inside files" to "documents inside files", and extends this file semantics uniformly to the Cloud Model path.
