# 9. Execution layer: unified document interface for Agent and Cloud Model

> From [CucCut File-Contract Subtitle AI Pipeline Design (File-Contract Pipeline, v0.3)](../ccut-file-contract-subtitle-ai-design.md)

## 9.1 Core abstraction (zero I/O; paths do not enter core)

```rust
pub struct DocumentArtifact { pub name: String, pub format: DocumentFormat, pub content: String, pub sha256: String }
pub struct DocumentRequest {
    pub kind: &'static str,              // "polish" | "translate" | "align" | …
    pub contract: String,                // contract description (system)
    pub input: DocumentArtifact,         // page to edit
    pub references: Vec<DocumentArtifact>, // read-only references such as context/glossary (separate from input)
    pub output_format: DocumentFormat,
    pub attempt: u32,
    pub problems: Vec<Problem>,          // structured: { code, scope, detail }
    pub temperature: f32,
}
pub trait LlmDocument { /* complete / complete_batch_with, same skeleton as the current LlmJson */ }
```

- `ccut-flow-core` stays zero-I/O: file paths exist only in the CLI host; core receives in-memory artifacts with a name and hash. (The current `LlmRequest` is all `String` with no paths, and must not regress.)
- Separating `input` from `references` is the shared premise of three things: provider inline layout, prompt caching, and "references are read-only."
- Model selection is a host policy and does not enter the core request structure.
- `problems` elements are structured (`code` see §10, `scope` marks the repair scope), so retry waves can decide the cost.

**M1–M4 implementation verdict: only the data structures landed, not the transport channel.** `DocumentArtifact` / `DocumentRequest` / `DocumentFormat` are defined and exported in `filepipe/common.rs`, but **there is no `DocumentRequest` construction site anywhere in the repo**, and the `LlmDocument` trait **does not exist**. All file-contract stages still go through `LlmJson` (`llm.rs:69`); the payload is the bare `user: String` of `LlmRequest`, and the format is decided by the host-side kind→extension mapping table. This has two consequences: `references` is a dead channel (§5.3/§9.3); the `sha256` field is empty throughout, so the content-addressed cache in §9.5 is also out of reach. Completing this channel is a prerequisite for deprecating the JSON contract (§17).

## 9.2 Agent path

Extension of the `tasks/<taskId>/` protocol (claim/submit, leases, hedge, `task watch`, and `--next` are all unchanged). Changes:

- **Directory split**: data plane `inputs/ references/ outputs/` separated from control plane `requests/ responses/ claims/`; **`responses/<callId>.json` no longer embeds the full body and only references the output file path and hash** (embedding would JSON-escape the entire page HTML once more, which is exactly what this change aims to eliminate). **M1–M4 implementation verdict: not implemented.** The task directory is still the five directories `contracts / payloads / requests / responses / claims`; payloads land at `payloads/<callId>.<ext>` (the extension already differs by kind: translate/align→`.html`, polish→`.txt`, analysis/translate-brief→`.md`), and `CallResponse.text` still embeds the body. Reason for staying put: renaming the directories would require changing the CLI, the worker-side skill docs, and in-flight tasks at the same time. That is a cross-surface breaking change and cannot be done in the same batch as switching the contract (§17).
- **New fields in the claim envelope.** **M1–M4 implementation verdict: four landed, two missing.** In non-json protocols the envelope adds `protocolVersion` / `input` / `inputFormat` / `outputExtension`; **`references[]` and `answerTemplate` were not added.** `input` currently **equals** `payload` (the same file), and it will only diverge once the data-plane split above lands.
- **Protocol/carrier self-consistency check (added in M5)**: before consuming a request, claim checks whether `protocolVersion` and the payload extension match each other. Declaring `file-v1` while pointing at a `.json` payload, or the reverse, is always rejected on the spot. Without this check, the worker would run HTML through json-v0's lint and parser, and the symptoms would only surface after the lint budget is exhausted.
- **Worker steps**: claim → read contract/input → copy input to a temporary output → edit output only according to the contract → `task submit --file <output> --next`. **M1–M4 implementation verdict: the local self-check step is not implemented.** There is no read-only validator subcommand on the worker side; validation only happens in the server-side lint of `task submit` (the `ccut task` subcommand set is still claim/submit/status/cancel/resume/watch). Submitting with `--file` itself has landed.
- **Lint budget.** **M1–M4 implementation verdict: unchanged; still keyed by `(callId, leaseId)`** (`claims/<callId>.lint.json` carries a `leaseId`, and the count resets to zero when the lease does not match; existing regression tests lock in this semantics). Changing to a constant per-call budget would require a new task-level cumulative ledger that does not reset with the lease, which is a semantic change to the lease system. The file contract itself does not create new handover pressure, so observe the real handover rate before changing this (§17).
- **Lease tiers.** **M1–M4 implementation verdict: `default_lease_sec` has not been re-calibrated**; it is still the 900/1800/3600s tiers by payload character count (the last change predates M0). Under the file contract, HTML payloads are **larger** than equivalent JSON rather than smaller (tag overhead), so they fall into the same or a higher tier; in that direction the existing thresholds are safe. Re-calibration requires new worker tail-latency measurements, so it is not changed without the data (§17). `request_item_count` **has switched over**: under the file contract it parses the document and counts nodes (translate counts `sentence_ids()`, align counts `tbody data-sid`), but it is currently only used for observation and does not participate in scheduling.

## 9.3 Provider path

- **Inline layout** (multiple files in one user message):

```text
<BEGIN INPUT name="translate.src.html" media-type="text/html">
…
<END INPUT>
```

**M1–M4 implementation verdict: only the INPUT envelope, no REFERENCE segment.** The `references` channel has not been wired up (§9.1); `request_user_content` only wraps a single `<BEGIN INPUT>…<END INPUT>`; `name` takes `<kind>.src.<ext>` rather than the page file name (core does not know the page file name); retry context is appended **outside** the envelope, so as not to pollute the sole convention that "the content inside the envelope is the document to edit."

- Accept only one complete file as the answer. A single outer fence is stripped at zero cost according to the declared format; multiple fences, surrounding explanations, or truncation go to the format repair in §10. **Does not use the provider Files API** (lifecycle, permissions, cost, and capabilities are inconsistent across vendors).
- **`max_tokens` is set from the target output length estimated from the input page, plus a safety margin**, no longer using the fixed value that only suited short JSON. Otherwise long file-contract outputs would inevitably be truncated, and the truncation shows up as "the trailing sentence lacks an id," which gets misjudged as a missed translation and burns an entire round of targeted retries (together with the `document-truncated` attribution). **Implemented**: `max_output_chars(input) / 2`, converted to tokens and clamped to `[4096, 16384]`, landed separately in each of the three providers (OpenAI / Anthropic / Gemini); Gemini additionally sets `thinkingBudget = 8192`. The same `max_output_chars` (4× input, floor of 4096 characters) is also the criterion for the output hard cap in §16 and for `document-oversize`: **the input-side sizing and the output-side rejection use the same ruler.**
- **JSON mode is removed per vendor**: OpenAI-style drops `response_format`, Gemini drops `responseMimeType`, Anthropic never had a JSON mode and needs no change. ~~chapters still use NDJSON+JSON mode, not migrated~~ (migrated 2026-08: `chapters` / `chapters-outline` use file-v1 HTML, likewise not sending JSON mode and sizing `max_tokens` by input). **Implemented**, in the form of a **short-circuit rather than a state flag**: `if compat.response_format && !file_contract`. Under the file contract the JSON-mode field is not sent, but the persistent state of `CompatFlags` is **not changed**. After the deprecation is executed, the short-circuit remains: JSON-v0 single-turn kinds not yet migrated (segment/cleanup/broll, etc.) continue to use JSON mode, and their capability-probe results are not polluted by file-contract calls.
- **The 400 downgrade has been expanded from a single boolean into a three-dimensional `CompatFlags`** (`response_format` / `limit`(MaxTokens|MaxCompletionTokens|Reduced) / `default_temperature`). It locates the dimension by substring-matching field names in the 400 response body; each 400 downgrades only one dimension and resends only once; the state is encoded in an `AtomicU8` shared across lanes. The motivation is exactly the `max_tokens` increase in the previous item: after replacing the fixed value with a dynamic one, "the output-limit field name or value is not accepted" became a new common 400, and it needs to be downgraded independently without implicating the other two dimensions.
- Lane count, 429 handling, and TailTracker hedging are carried over. Response text is written to `pages/pNNN.out.*` on disk before being passed to the parser.

## 9.4 Model routing

Per-kind overrides: config `llm.stages.<kind>` / CLI `--llm-for <kind>=<mode>`. Typical configuration: `segment-only` and the small-page repair wave use the small model; analysis/align use the large model. By default all inherit `--llm`. Default temperatures: analysis 0.2 / polish 0.2 / translate 0.3 / align 0.2 (consistent with the current behavior).

**M1–M4 implementation verdict: per-kind routing is not implemented.** `llm.stages.*` and `--llm-for` have zero hits across the repo; all stages inherit the same `--llm`. The temperature tiers still take effect as before. See §17.

## 9.5 Reuse cache (new mechanism, not carried over)

The current "reuse" is a linear scan with full string equality comparison of system/user strings (`reuse_prior_response` scans `tasks/*/requests/`; the provider side scans `logs/llm/*.jsonl`). Under the file contract, the cost of comparing whole pages rises significantly, and **after a validator upgrade, old answers would be wrongly reused**. The envisioned replacement is a content-addressed cache, with the key =

```
protocolVersion + kind + contract sha256 + input sha256 + ordered reference sha256s
+ source/target language + explicit instructions + renderer/parser version + model parameters that affect content
```

The renderer/parser version must be part of the key, so that a new validator does not silently accept old answers from the lax era (a quality regression would be invisible).

**M1–M4 implementation verdict: not implemented; reuse is still the "current" form described in v0.2.** `reuse_prior_response` linearly scans `tasks/*/requests/*.json` and does full string equality on payload+contract; `reuse_logged_response` scans `logs/llm/<kind>.jsonl` and checks equality of provider/model/attempt/system/user; there is no sha256/blake3 digest anywhere in the repo. The prerequisite is the `DocumentArtifact.sha256` channel in §9.1 (currently always an empty string); the switch cannot be made until that is filled in. See §17.

## 9.6 Protocol versioning and gradual-rollout coexistence

- Both the claim envelope and the manifest carry `protocolVersion` (`json-v0` / `file-v1`). **Historical tasks' `json-v0` is always interpreted by the old runner; a new parser never guesses old responses.** When the switch is turned on, calls that were claimed but not yet submitted are completed according to the protocol declared in their envelope. (For the manifest-side implementation approach, see §4.2: json-v0 does not write a manifest.)
- ~~Gradual-rollout switch: `--contract file|json`~~ **Deprecated in execution 2026-08**: the `--contract` parameter has been removed entirely; the five migrated kinds always use file-v1, and align and translate naturally share the same chain (the same chain never mixes file contract and JSON halfway). The historical-task semantics from the first item are preserved: in this version, submissions for json-v0 migrated kinds are not linted and are passed through as-is; protocol determination only recognizes the `protocolVersion` in the request envelope and never sniffs the payload.
