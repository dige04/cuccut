# 6. Stage 1: Polish + Segmentation (txt contract)

> From [CucCut File-Contract Subtitle AI Pipeline Design (File-Contract Pipeline, v0.3)](../ccut-file-contract-subtitle-ai-design.md)

Polishing and segmentation are merged into a single edit. (In the current state, polish already produces paragraphs as a side effect; this makes that an explicit contract.)

## 6.1 Rendering and line-break semantics (protocol core, must be unambiguous)

- The word sequence is rendered to natural text according to language joining rules (the `atomize` convention: Latin words joined by spaces, CJK joined directly). **Words marked `hidden` are excluded from the projection** (consistent with the current behaviour where `Sentence` derivation excludes hidden words; otherwise polishing would bring back content that has already been cut).
- **No timestamps and no word ids at all.**
- Soft markers keep the current characters and thresholds from `markers.rs`: `⏸` (≥0.6s) / `⏸⏸` (≥1.0s) / `⏸⏸⏸` (≥1.8s) / `⏹` (speaker change). In multi-speaker documents, `⏹` carries a stable speaker label `⏹S2` (the label names the speaker on the right; see `speaker::SpeakerLabels` for the rule; no timing, consistent across the whole document). A bare `⏹` is still recognized. **Soft markers and labels exist only in the input and stay out of the diff baseline** (both sides are stripped before comparison at parse time).
- Existing paragraphs (on re-polish) render as blank lines. Manual paragraph pins (the `asrLayout` stale scenario) must be preset verbatim. The model may make minor adjustments, but the parse side is bound by the §2 rule "manual layout takes priority."

**Line-break semantics table (output side):**

| Form | Meaning |
|---|---|
| Single line break | A readability line wrap. Treated as a space at parse time. It **carries no boundary meaning at all**. |
| Blank line (two consecutive line breaks) | Paragraph boundary → `paraBreaks` |
| ≥3 consecutive line breaks | Invalid structure. Collapsed to one blank line at parse time, with a warning recorded. |
| `⏹` / `⏹S<n>` | **Hard guarantee**: a speaker change forces a sentence and paragraph break at that point. The model is not trusted. It must keep the marker in place and must not delete, duplicate, or cross it. At parse time, the program enforces the boundary at the original position whether or not the model kept the marker. Any leftover `⏸` / `⏹` / speaker labels in the output are always stripped. |

We explicitly reject two designs: “single line break = sentence boundary” and “the program inserts sentence-final punctuation.” A Sentence is always derived deterministically from rules such as sentence-final punctuation (the red line “derived projection”). Inferring layout signals back and then modifying the `words[]` text would bypass the proof that LCS rebinding depends on.

**Paragraph quality gate (implementation addendum, 2026-08):** Segmentation is a mandatory output, not an option. A paragraph in the core region whose word count exceeds **Latin 300 / CJK 500** (per the `atomize::word_count` convention; the script type is determined by `is_cjk_text`; constants `MAX_PARAGRAPH_WORDS_LATIN` / `MAX_PARAGRAPH_WORDS_CJK`) counts as a segmentation degeneration. The motivation is a real incident: the model (measured with deepseek-v4-flash) returned the whole page with no blank lines. The old validation only rejected “zero paragraphs,” so a 9-minute transcript clumped into one paragraph was still accepted and stamped `segment`. The system prompt declares this limit as the acceptance line, but **the lint of the main polish page does not reject the page for exceeding the limit**. Oversized paragraphs are targeted for repair after the wave by a dedicated `segment-repair` carrier that adds segmentation (§6.6). `paragraph-oversize` appears as a Problem only inside that carrier (§10.1).

## 6.2 Paging and read-only context

- The core-region budget is 2200 words (per the `atomize::word_count` convention; see §12). Break-point scoring reuses `paging.rs` (speaker change 3 > long pause 2 > sentence-final punctuation 1, choosing the best within the last 20% of the budget window). **Sentence boundaries take priority** (2026-08, corrected by measurement): if the window contains any sentence-final punctuation, take the highest-scoring sentence boundary; fall back to pauses only when there is no sentence boundary. Measured on a single-speaker long talk (a 7-hour interview with Xie Saining (谢赛宁) that flattened speaker labels), 30 of the 47 page seams fell mid-sentence (e.g., 「我们大 ‖ 脑的皮层」, “we big ‖ brain's cortex” in the sample transcript). This happened because a 0.6s hesitation pause (rank 2) always beat the sentence end (rank 1) in the window. After giving sentence boundaries priority, only segments with no punctuation at all are split mid-sentence (same corpus: 30 → 8). Long turns with speakers already prioritized sentence boundaries internally, so the two paths are now consistent.
- **Rule when there is no good break point** (the current behaviour cuts hard at rank 0, which under the file contract would produce broken sentences that tempt the model to complete them; this must be handled explicitly): allow the core budget to overflow by up to +15% to reach the next sentence boundary, then the next break with rank ≥1. If there is still none, mark `<<<HARD-CUT>>>` at the hard cut point. The contract states explicitly that the first or last sentence of this page may be a fragment, to be kept as-is and not completed. A speaker change is never crossed by a page seam. **Paragraphs on either side of a hard-cut page seam are merged unconditionally by the engine** (`hard_cut_seams_merged`). The contract already tells the model that HARD-CUT is not a paragraph boundary, so the engine must not place paragraph pins there.
- **Read-only context regions on both sides**: `min(200 words, 3 complete sentences)`, and **at least 1 complete sentence** (a 60-word-scale window is too small for one sentence in CJK, which makes it ineffective). Sentinel fence:

```
<<<CONTEXT-BEFORE 只读，勿修改>>>
…tail of previous page…
<<<EDIT-BEGIN>>>
…this page's core region, editable; leave one blank line between paragraphs…
<<<EDIT-END>>>
…head of next page…
<<<CONTEXT-AFTER 只读，勿修改>>>
```

- **Sole ownership**: parsing takes only what is between `EDIT-BEGIN/END`. The paragraph boundary on a seam is determined by the page that owns the word. The context regions are read-only context (the next page can see the complete sentences at the end of the previous page). There are no writable overlaps and no consensus-seam algorithm, because that would double the token cost and bring back serialization. (If v2 benchmarking proves the seam quality insufficient, consider referring to B's `TextPatchSet` merge.)
- **Page seams are not paragraph evidence** (2026-08, corrected by measurement): paging only sets the starting points. The boundary between the last paragraph of page k and the first paragraph of page k+1 is produced mechanically. Previously the engine wrote every page seam unconditionally as a `paraBreaks`. Measured on the single-speaker long talk, only 9 of 47 page seams (19%) actually had a paragraph boundary. Page seams are now handled in three tiers: ① Page seams at speaker changes: the ⏹ hard guarantee applies, so the paragraph pin is necessarily set. ② The next page leaves **one blank line** after `EDIT-BEGIN` and before the first sentence (`PolishParsed::starts_new_paragraph`). This is the model explicitly declaring “the first paragraph starts a new paragraph.” The paragraph pin is kept and no longer questioned (`seam_signaled_paragraphs`). In the contract, this is the **only** meaningful leading blank line. When the preceding context is empty (first page) or the page starts with a hard cut, it does not count as a signal. No blank line only means “no position taken.” It must not be inferred as “continuation.” ③ All other page seams are passed to the **seam-repair wave** after the main wave and punct-repair (§6.8) for judgment. If the model says continuation, the seam is merged. If it says boundary or rejects, the seam is kept.
- Fence lines must be kept verbatim (they are parsing anchors). A broken fence → `document-truncated` (§10).

## 6.3 Instructions and model tiers

- Instructions = the current polish edit-category switches (`typo/term/punct/grammar/filler/wordy`) + the line-break semantics table + the terminology rows hit on this page. Temperature 0.2.
- **`segment-only` mode**: the instructions are narrowed to “verbatim fidelity, only insert blank lines,” routed to a cheap model by kind (§9.4). Full re-segmentation goes through this mode, replacing the current segment engine's main contract. Polishing and pure segmentation are two instruction-strength tiers: the former requires the main model, while the latter can use a very cheap model.

## 6.4 Parsing and write-back (degradation ladder)

1. Validate the fences → strip fences and soft markers → parse line-break semantics → normalize with `normalize_chars`.
2. **Verbatim fast path**: after normalization, if the text equals the core-region source text, write `paraBreaks` only at the blank-line positions (the expected path for segment-only).
3. **Diff rebinding**: align words with the core region using `atomize` + LCS. **Page-level threshold 0.7** (`MIN_TEXT_MATCH_RATIO`). Sentence-level similarity is 0.7 for Latin and 0.75 for CJK. These three values are current constants (the file-contract page is larger, so the page-level threshold is listed as an item to re-calibrate under load testing). On pass → `rebind` keeps ids and timings and swaps the text. Blank lines snap to word boundaries, and the first word id of a paragraph enters `paraBreaks`.
4. **Terminology replacement protection**: before comparing similarity, the “variant → canonical form” replacements for matched terms are tokenized as opaque tokens. Otherwise a correct fix such as `宝卡特 → CucCut` (a mis-transcription of “CucCut” rendered in Chinese) would be judged as low similarity and wrongly trigger a re-polish.
5. **Local re-polish of spans**: if the proportion of low-similarity sentences is > 0.3 (`MAX_SIMILARITY_FAIL_RATIO`), or the match rate is insufficient, send a span-level txt repair request for the failed word range ± one sentence of context (same contract, with only that span inside the fence). At most 2 attempts.
6. **Cut-point recovery**: for spans that still fail, discard the LLM text and keep only the paragraph cut points (corresponding to the per-sentence fallback that follows the current `low_similarity_retry`. Polish has no tier naming system for segment).
7. **Deterministic fallback**: revert the whole page to the original text and apply rule-based segmentation (never fails), recorded in `report.json`. **Subject to the §2 rule that manual layout takes priority**: when manual paragraph pins or line breaks exist, the fallback only keeps the original text and does not rearrange paragraphs.

**The snowball guard changes to “accept + targeted punctuation repair”** (2026-08): a single sentence whose source span exceeds 1200 characters / 300 seconds (`MAX_SENTENCE_SOURCE_CHARS` / `MAX_SENTENCE_SPAN_SECONDS`), or a corrected single sentence that by itself exceeds the capacity of one paragraph (Latin 300 words / CJK 500 characters), is judged an **overlong sentence**. However, it **no longer fails the page attempt**. On the first wave, the main pass accepts the body text directly. Overlong sentences are split by a targeted `punct-repair` carrier that adds punctuation after the wave. When the rounds are exhausted, the engine splits sentences deterministically according to the source timeline. This replaces the M1–M4 approach, which was `Problem::page(document-oversize)` rejecting the whole page, followed by retries and deterministic fallback. That approach failed in a real incident: a Chinese sentence of 1,652 / 1,822 characters with no full stop, same speaker, and many pauses, which was returned unchanged on all three page retries until the whole page reverted to the original text. The old 900-character re-split of corrected text only honoured existing full stops and never created boundaries, and it has been deleted. **M1–M4 implementation decision** (intentional, see §13.1):

- `resplit_oversized` **is not wired into the file path**. It re-splits by sentence-final punctuation, which would create paragraph boundaries that come from neither a blank line nor a `⏹`. That directly contradicts the §6.1 rule that “paragraph boundaries have only two sources.” `punct-repair` and deterministic sentence splitting only split **sentences** (by adding sentence-final punctuation). Paragraph boundaries still come only from blank lines and `⏹`.
- The carry-over mechanism is fully retired (`run_polish_file_contract` is independent per page, with no carry-over). During the gray-release period, the json-v0 path and the `MAX_CARRY_CHARS = 600` guard were kept. On 2026-08, when the json path was deprecated, they were removed along with the json version of `run_polish`.

**Paragraph degeneration does not go into a whole-page retry. Instead: “accept the body text on the first round + targeted paragraph repair after the wave + deterministic closure”** (implementation decision, 2026-08; replaces the earlier “whole-page retry + forgiveness on the last round” approach). The polished text is itself valid. Discarding the whole page's text because of one paragraph defect, and spending another full page of tokens to redo it, is a bigger loss, and redoing it often still does not produce blank lines. So `lint_page` / `validate` in the main wave **do not reject the page** for oversized paragraphs. The page is accepted as-is and its `words` are written back as usual. After the main wave ends, the engine collects the paragraphs in the final accepted set that still exceed the limit (regardless of which page they came from, including large single-block paragraphs left by the whole-page fallback and large paragraphs formed by merging across page seams), and **gathers them across pages**. Then it adds segmentation block by block through the `segment-repair` index contract in §6.6, until no oversized paragraph remains or the round limit is reached. When the rounds are exhausted, any remaining oversized multi-sentence paragraphs are **deterministically closed** by the engine using the inter-sentence pause level (`fallbackParagraphs` accounting: the segmentation is valid, but the cut points were chosen by the machine). Therefore the output never contains oversized multi-sentence paragraphs, and `stages.segment` is still stamped as usual. `degenerateParagraphs` is kept as an invariant check. It counts the multi-sentence paragraphs still oversized after closure, which should always be 0 under normal conditions. If it is non-zero, the good paragraphs' `paraBreaks` still land, but `stages.segment` is **not stamped**, and the stage stays pending for the dedicated segment process. A fake `segment: fresh` is never produced. The CLI reports `degenerateParagraphs` and points `next` to `ccut segment`. The number of paragraphs that repair successfully split is reported as `repairedParagraphs`. The re-polish path (where `stages.segment` is already stamped) does not produce paragraph pins, so this gate passes directly, without sending a wave and without an alert.

`fingerprint` write-back semantics are fully consistent with the current behaviour: text changes write `words` (`IdSource` allocates new word ids), and paragraphs write `paraBreaks`. Stamp `stages.polish = fingerprint(words)`. If the document was not segmented before, or is re-segmented, stamp `stages.segment = id_fingerprint(words)` (on paragraph degeneration the stamp is withdrawn, as described above). `ensure_balanced_cue_layout` still runs (its early return when `breaks` is empty is the layout protection). `report.json` keeps `firstWordId/lastWordId/t0/t1/fallback` and suggestions for each sentence. **`ai/polish.json` continues to be dual-written within one version** (the review accept chain and the `writes` declaration in `spec.rs` depend on it, see §13).

## 6.5 Parallelism

Pages have no dependencies between them (the context zone is rendered statically and does not wait for the previous page's result), so all pages are dispatched in one batch. Successful pages stream their results back to the checkpoint; failed pages enter a retry round. **M1–M4 implementation decision**: the signature of `parallel_kind` is `parallel_kind(kind, file_contract)`. Polish runs in parallel only under a file contract. Once execution is deprecated, new tasks are always file-v1; this protocol parameter only affects the `workerPlan` of **legacy json-v0 tasks**, which still honestly report `serial`.

## 6.6 Targeted segment-repair carrier `segment-repair` (2026-08, index contract)

After the main wave's first pass accepts the body text (§6.4), paragraphs that still exceed the limit are re-segmented by a separate carrier with `kind = "segment-repair"`. Like polish, it is a `text/plain` file carrier (the agent task directory writes `payloads/<callId>.txt`, `protocolVersion: file-v1`; the provider path uses inline layout), but its contract, parser and acceptance granularity are different. It is an **index contract**: the model sees the sentence lines with line numbers and returns only line-number ranges, never repeating the body text.

- **Why not "repeat verbatim and insert blank lines" anymore**: the first version required the model to repeat several hundred lines of body text verbatim and only allowed inserting blank lines. In measurement on Xie Saining's (谢赛宁) 7-hour single-speaker corpus with deepseek-v4-flash, of 87 segment-repair calls, 22 were rejected as `source-drift` because the model changed one character on the side (`也是都都是` → `也是也都是`, a Chinese typo-like wording change). 19 inserted no blank lines at all, and the ones that passed often split into only two groups, so three rounds were not enough. The answer text was only used to locate boundaries and was never written back, so verbatim repetition was fragility paid for something that was never used. The index contract turns acceptance into pure arithmetic, cuts the output down to a few dozen characters, and lets the block header state a checkable hard requirement such as "split into at least N paragraphs."
- **Payload**: one payload carries **one or more** over-limit paragraphs. Each block is wrapped by a pair of fences, with one blank line between blocks. The block header gives the serial number, sentence count, word count (CJK counted in characters) and the minimum paragraph count (`ceil(words / single-paragraph cap)`, `block_min_paragraphs`). Inside the fences, **one sentence per line** (final-form sentence text, including content already rewritten by polish; excluding timestamps, soft markers and ids), each line prefixed with a 1-based line number `N| `:

```
<<<BLOCK 1 | 63 sentences | 1832 characters | at least 4 paragraphs>>>
1| 第一句…
2| 第二句…
…
63| 最后一句…
<<<BLOCK-END>>>

<<<BLOCK 2 | 40 sentences | 410 words | at least 2 paragraphs>>>
1| …
<<<BLOCK-END>>>
```

- **Answer**: each block replies with `<<<BLOCK k>>>` … `<<<BLOCK-END>>>`. Inside the fences, **one `a-b` line-number range per line** (one range = one paragraph). Ranges must start at 1, be contiguous end to end, and run through the last line. No sentence text is repeated, and nothing is output outside the fences. The parser is lenient: it accepts a block header without angle brackets (`BLOCK 2`), several ranges on one line (comma- or space-separated), en/em dashes and `~`, single-line single-sentence ranges (`7`), out-of-order blocks, and an omitted block header for single-block payloads. If the model still repeats the numbered sentence lines, grouping by blank lines and using only the line numbers is also accepted.
- **Cross-page batching and re-pagination**: the engine scans all `committed` paragraphs in the final accepted set. Any paragraph whose word count exceeds `paragraph_word_limit` and that has ≥ 2 sentences enters this round's work set, regardless of which page it originally came from. It is re-paginated with `balanced_page_sizes` according to each paragraph's word count, using the main polish core-zone budget (2200 words). Overlong paragraphs get at least one page to themselves, and several paragraphs merge into one or more payloads. Page ids are `sr{round}-{serial:03}` (e.g. `sr1-001`, `sr2-003`), recorded in `manifest.json` and per-page attempt files; `report.json` is booked as usual.
- **Per-block acceptance** (`parse_segment_repair_page`; the agent-side `task submit` mirrors lint, and the engine uses the same implementation; all criteria are string-level, so the agent side is a complete check): first `guard_output_size` (over limit ⇒ document-level `document-oversize`, and all blocks are void). Then each block's answer is sliced by its header. Missing block / no ranges / not starting at 1 / not contiguous end to end / not covering through the last line / out of bounds ⇒ that block is `range-invalid` (detail pinpoints the first defect: "line k is not covered by any range", "range a-b overlaps the previous range", "out of bounds", …). A valid answer with only one range while the whole block is over limit ⇒ that block is `paragraph-oversize` (detail is a targeted instruction, including "split into at least N ranges"). ≥ 2 ranges (or a block that was not over limit to begin with) ⇒ the block passes and is cut into subgroups by range, with paragraph pins placed on group boundaries. **Passing blocks in a payload land immediately; a rejected block affects only itself.** A subgroup that is still over limit is **not** a Problem for that block. The engine handles it by overflow magnitude: subgroups under `SEGMENT_OVERFLOW_TOLERANCE` (15%) are deterministically re-cut immediately at the pause-tier level (pure capacity convergence such as 584→526 does not burn an LLM round); those above it go unchanged to the next round, where the model splits them semantically.
- **Rounds and cap**: `SEGMENT_REPAIR_MAX_ROUNDS = 3`. Each round = rescan the paragraphs still over limit → re-paginate → one `complete_batch`. There is no carrier-level retry inside a round; **the round is the retry**. Rejected blocks (invalid ranges / only one range returned) and subgroups that remain clearly over limit after splitting all go into the next round together. From round 2 on, the request carries `attempt = round` and `retry_reason = "[paragraph-oversize] block k: <previous round's feedback for that block>; …"` (the provider path injects `[retry context …]`; the agent path feeds it back via the call request). For a rejected block, the "previous feedback" is its Problem's `[code] detail`. For a subgroup still over limit after splitting, it is "after the last round's split, N words remain, above the single-paragraph cap of M: please split this block into at least K ranges", addressed by the word index of the paragraph's opening sentence. Subgroups have different opening sentences after splitting, so this naturally distinguishes the two sources. Retryable transport errors count only as "no answer obtained this round"; the paragraph keeps its original group and goes to the next round. Terminal / Cancelled propagate as usual.
- **Deterministic closure (after rounds run out)**: paragraphs still over limit that contain multiple sentences are split by the engine's `split_by_rank`. It accumulates word counts from the start. When adding a sentence would exceed the limit, it returns to the sentence boundary with the highest pause tier in the last 40% of the current window (≥1.2s → 3, ≥0.6s → 2, otherwise 1; ties go to the latest) and cuts there. If the window has no other sentence boundary, it cuts before the current sentence. A single sentence that is over limit by itself can only occupy a group alone (overlong sentences are handled earlier by punct-repair). Each original paragraph that is closed this way is recorded once in `fallbackParagraphs`, and `stages.segment` is stamped as usual. This matches the tier-5 deterministic fallback of the standalone segment engine: it never fails, and its cut points are legal but not semantic. The same ruler is also used for the overflow-tolerance re-cut in the previous item.
- **Skip condition**: a single-sentence group has no inter-line position where a break can be inserted, so it does not enter the work set. This is not a degradation; an over-limit single sentence belongs to punct-repair's account.
- **Prompt**: `segment_repair_system_prompt` shares one system prompt with every request in the wave (on the agent path it is saved as `contracts/segment-repair.md` / `-2.md` / `-3.md` by `(kind, attempt)`). It only states: one or more blocks; numbered sentence lines, one sentence per line; reply with ranges only; ranges must cover contiguously; the block header states the minimum paragraph count; each block is checked individually; blocks still over limit are sent back again. It contains no batch-specific information, so all rounds and pages can share it.

## 6.7 Targeted punctuation-repair carrier `punct-repair` (2026-08)

After the main wave's first pass accepts the body text (§6.4), and before the single-sentence similarity retry and `segment-repair`, sentences that are still **overlong** are punctuated by a separate carrier with `kind = "punct-repair"`. "Overlong" means a single-sentence source span > 1200 characters / 300 seconds, or corrected text exceeding single-paragraph capacity. The design motive is to separate "polish and segmentation" from "adding punctuation". Polish pages are only asked to add punctuation along the way, rather than forcing the model to break sentences by rejecting pages. One sentence missing punctuation should not cause the whole page of body text to be re-generated, and it should not create `。。` / `。，` noise during a full-page rerun. Like the others, it is a `text/plain` file carrier (agent `payloads/<callId>.txt`, `protocolVersion: file-v1`; inline layout for providers). It runs before `segment-repair` because paragraph repair can only insert breaks between sentences. An overlong sentence has no seam to insert into unless it is cut first.

- **Payload**: one payload carries **one or more** overlong sentences. Each sentence is wrapped by a pair of fences with an id, with one blank line between sentences. The body is that sentence's final corrected text. The pauses between source words are projected via atom-LCS into soft hints: `⏸` (≥0.6s) / `⏸⏸` (≥1.0s) / `⏸⏸⏸` (≥1.8s). The prompt declares these marks are hints only and must not be copied back into the answer. `min-sentences` = ⌈sentence words / (single-paragraph capacity / 2)⌉ ≥ 2 tells the model the minimum number of sentences it must split into:

```
<<<SENTENCE-BEGIN id=s01 min-sentences=3>>>
…第 1 句 corrected 文本，含 ⏸ 停顿提示…
<<<SENTENCE-END id=s01>>>

<<<SENTENCE-BEGIN id=s02 min-sentences=2>>>
…第 2 句…
<<<SENTENCE-END id=s02>>>
```

- **Answer**: each sentence is echoed back verbatim with its fence (same id) and body. **The only permitted change is adding sentence-final punctuation** (`.?!` / `。？！`). Non-punctuation characters are copied verbatim: no fixing typos, no rewording, no merging/splitting, no adding or deleting words. Do not copy `⏸`, and do not create conflicting punctuation such as `。，` / `，。` / `，，` / `,,` / `..` / `.,` or dangling fake sentence ends (the prompt and the polish main page share the same dangling-word list). Entries do not interfere with one another, and nothing may be output outside the fences.
- **Cross-page batching and re-pagination**: the engine scans all `committed` sentences in the final accepted set, regardless of which page they originally came from. Fallback-page source sentences are excluded, since they are already original wording and are not rewritten again. Sentences are re-paginated with `balanced_page_sizes` according to each sentence's word count, using the main polish core-zone budget (2200 words). If `PolishOptions.worker_slots = Some(n)` (n > 1) and the page count is below n while the sentence count is above the page count, `balanced_page_sizes_for_count` raises the page count to `min(n, sentence count)` to fill the concurrency slots. Page ids are `pr{round}-{serial:03}` (e.g. `pr1-001`, `pr2-003`), recorded in `manifest.json` and per-page attempt files.
- **Per-sentence acceptance** (`parse_punct_repair_page`; the agent-side `task submit` mirrors lint and shares one implementation with the engine; all criteria are string-level): first `guard_output_size` (document-level `document-oversize`). Then each sentence's fence window is found by id. Missing fence / unpaired id ⇒ that sentence is `missing-id`. The atom sequence after removing punctuation differs from the payload (rewritten, added or removed) ⇒ `source-drift` (detail points out "word k was rewritten / added / removed"). The body contains no sentence-final punctuation at all ⇒ `sentence-oversize` (detail is a targeted instruction: add `.?!` / `。？！` where the meaning completes, and leave everything else alone). Conflicting punctuation or dangling fake sentence ends ⇒ `document-oversize`. Sentences that pass are sliced by the engine at sentence-final punctuation; each slice is re-anchored to that sentence's source word range via atom-LCS, followed by `heal_boundaries`. If fewer than 2 slices can be cut, or re-anchoring fails, the sentence is likewise recorded as `sentence-oversize`, because the newly added sentence-final punctuation cannot be projected back onto source words and the sentence stays as it was. **Passing sentences land immediately; a rejected sentence affects only itself.** Slices that remain overlong after cutting are not a Problem; they simply go to the next round.
- **Rounds and cap**: `PUNCT_REPAIR_MAX_ROUNDS = 3`. Each round = rescan the sentences still overlong → re-paginate → one `complete_batch`. **The round is the retry**: rejected sentences and slices still overlong after cutting go into the next round together. From round 2 on, the request carries `attempt = round` and `retry_reason = "[sentence-oversize] sNN: <previous round's feedback>; …"`. For a rejected sentence, the feedback is its Problem's `[code] detail`. For a slice still overlong, it is "after the last round's split it is still overlong (reason): please continue adding sentence-final punctuation where the meaning completes", addressed by the word index of the sentence's first word. Retryable transport errors count only as "no answer obtained this round". Terminal / Cancelled propagate as usual.
- **Deterministic fallback (after rounds run out)**: sentences still overlong are cut by the engine along the source timeline, guaranteeing that no overlong sentence leaves the pipeline. Candidate cut points (between adjacent source words) are scored: speaker change (5) > preceding word ends with sentence-final punctuation (4) > pause ≥1.8s (3) > pause of 0.6–1.8s where corrected text places it after a comma, semicolon, enumeration comma or colon (2) > any pause or comma (1) > none (0). Within the word-count window [capacity/5, capacity·4/5] (also bounded by the hard limits of 1200 characters / 300 seconds), the highest score wins; ties go to the latest point (filling the window). If the window has no candidate, it falls back to the last feasible position. The left slice has trailing commas and whitespace removed, then gets `。` / `.` appended per language (nothing is appended if it already ends in sentence-final punctuation). The right slice is kept as is. This loops over each slice until none is overlong. It only cuts sentences and does not create paragraph boundaries (§6.1 unchanged).
- **Counts**: `punctRepairedSentences` (sentences cut after the model added punctuation), `punctSplitSentences` (sentences cut by the engine's fallback) and `oversizedSentences` (residual overlong sentences after both, which should always be 0) are reported in the `data` of the polish success envelope.
- **Prompt**: `punct_repair_system_prompt` shares one system prompt with every request in the wave (on the agent path it is saved as `contracts/punct-repair.md` / `-2.md` / `-3.md` by `(kind, attempt)`). It only states: one or more sentences, each with a pair of id fences; add sentence-final punctuation only; `min-sentences`; each sentence is checked individually; sentences left untouched will be sent back again. It contains no batch-specific information.

## 6.8 Seam-judgment carrier `seam-repair` (2026-08, index contract)

The judgment wave for the ③-tier page seams of §6.2. It uses **the same index carrier and the same parser** as `segment-repair` (`parse_segment_repair_page`; the agent `task submit` mirror lint is `lint_agent_answer_seam_repair`). The only difference is that "one interval covers the whole block" is a legal answer inside a seam block and does not count as `paragraph-oversize`. It is a separate kind only because the system prompt and the block header differ; the agent path stores results by `(kind, attempt)` as `contracts/seam-repair.md` / `-2.md`.

- **Timing**: main wave accepts body text → punct-repair (sentence text finalized) → re-polish of low-similarity single sentences → autocorrect → **seam-repair** → segment-repair. It must run before paragraph filling: filling splits groups and changes group indices, while seams are addressed by `committed` group index. It runs only when this polish pass is responsible for producing paragraph pins (`stages.segment` not stamped).

- **Block = window, not whole paragraph**: one block = the **tail window** of the last paragraph of page k + the **head window** of the first paragraph of page k+1 (`SEAM_WINDOW_WORDS = 250`: accumulate sentences from the paragraph end/start until ≥ 250 words; the sentence that crosses the threshold is included; at least 1 sentence per side). In the final text form, sentences are one per line with line numbers. The block header states the seam position `page seam before line N` (the previous page ends at line N-1, the next page starts at line N). When the head window exactly fills the right paragraph and the next seam immediately follows, the blocks chain into one (header `page seams before lines N, M`). Windows decouple block size from the length of the paragraphs on either side. The first version concatenated whole paragraphs into blocks; for a single-speaker corpus where each page is a single paragraph, adjacent seams chained into a giant block of 541 lines / 21k characters. The model answered "whole block is one paragraph," then merged it into a 15k-word giant paragraph, and segment-repair could not bite it across three rounds. That is the direct motivation for switching to windows. Blocks containing empty sentence lines are skipped entirely (keeping the paragraph pins).

- **Paging and parallelism**: pages are packed by block word count using `balanced_page_sizes` against the main polish's core-area budget (2200 words); one payload carries one or more blocks, and the whole wave is dispatched in parallel; page id `sm{round}-{serial:03}`. A 7h single-speaker corpus has ~48 blocks ≈ 10 payloads, 15–30 s per round. This is the shape of "Map in parallel + Reduce that only looks at seams." A serial carry-over, where "the last paragraph carries into the next page," stretches the page wave from 2 min to 13 min (deepseek-v4-flash at 14 s per page; on slower models, 6 → 47 min), so it is not adopted.

- **Judgment: only the two ends of a cross-seam interval are adopted.** The wave first flattens `committed` into a sentence sequence plus a set of paragraph starts (global sentence indices); seams are the paragraph starts within it. The answer is cut into groups by interval, and for each seam in the block the **interval containing the seam line** is found. If that interval starts at the seam line ⇒ keep (`seam_kept_paragraphs`). Otherwise, remove the seam paragraph start (`seam_merged_paragraphs`) and set the interval's start/end inside the **window** as paragraph starts/ends. This gives "the true start and end of the seam paragraph" (for example, the last three sentences of page k's final paragraph had already opened the next topic). Boundaries at the window edge and intervals that do not cross a seam are all ignored: the window is truncated, so boundaries at its edge are not trustworthy. All edits are set operations on the paragraph-start set, so blocks do not interfere with each other and need no shifting by group index. **No capacity re-cutting is done.** Paragraphs still over the limit after merging are left to the immediately following segment-repair to split semantically.

- **Rounds and degradation**: `SEAM_REPAIR_MAX_ROUNDS = 2`. Round one sends all candidates; round two resends only the rejected blocks (`retry_reason = "[range-invalid] block N: …"`). Rejected blocks (invalid interval / missing block), retryable transport errors, or exhausted rounds ⇒ **keep the original paragraph pins**, exactly as if no judgment were made. The degradation direction is always the status quo: a bad answer never drops a boundary or runs two paragraphs together. Terminal/Cancelled propagate as usual.

- **Measurements** (Xie Saining's 7h interview with speakers flattened, deepseek-v4-flash): In the first version, a full-chain rerun with whole-paragraph concatenation: sentence-boundary-first paging cut mid-sentence seams from 30 to 1 (only fully unpunctuated stretches remain). Of 48 seams, 37 were merged, 2 kept, and 9 were rejected in both rounds and kept; the wave made 32 calls. The kept seams were all at questions/answers or at “嗯。” (um.) interjections. Compared with the natural paragraphing of the multi-speaker run, 21 of 36 merges fell in the same paragraph there, and 13 were speaker switches that are invisible in single-speaker text. The explicit signal (a leading blank line) was triggered 0/49 times by deepseek-v4-flash: it is unaware of this contract and degrades to seam-repair judgment, which is the designed behaviour. In the multi-speaker run all 46 seams are ⏹, so the wave does not trigger.
  **Index contract + windowed full-chain rerun** (same corpus, same model): of 48 single-speaker seams, 29 were merged and 19 kept, in 11 calls, all passing on the first round. This includes the "move the boundary by one sentence" judgment: the intervals `1-15 / 16-21` merge the seam and start a new paragraph at line 16. segment-repair made 47 calls with **zero** `range-invalid` and zero characters changed, and converged in 3 rounds (round 2: 5 blocks; round 3: 1 block): `repairedParagraphs 66`, `fallbackParagraphs 0` (the deterministic closing step never triggered), `degenerateParagraphs 0`, `segmentedByPolish true`. Paragraphs went from 343 to 467; the median from 338 to 290 characters; the longest from **19625 to 711** characters. Multi-speaker run: all 46 seams still ⏹, so the wave does not trigger. segment-repair made 6 calls and converged in two rounds: `repairedParagraphs 17`, `fallbackParagraphs 0`, `degenerateParagraphs 0`. Of 1950 paragraphs, `shortInterjectionParagraphs 750` (interjections of ≤10 characters and ≤3 s, such as “嗯。”, per spec §18.5). These are reported only, not changed.

## 6.9 Speaker-attribution repair carrier `speaker-repair` (2026-08, index contract, before paging)

polish treats ⏹ as a hard guarantee (§6.1: sentences may not span a speaker change and must be split into paragraphs). So a diarization fragment that was misjudged (in “打 DOTA 什么 | 的 | 就是宿舍…” (play DOTA what | the | that's the dorm…), the 「的」 (the particle) was assigned to the other speaker) would, in the main polish, only be forced into standalone sentences with punctuation. The repair therefore sits **before paging**, as the first wave of polish (`engines/speaker_repair.rs`, `kind = "speaker-repair"`), and only modifies `words[].sp`. `sp` is not part of any fingerprint, so it does not trigger stage re-runs. Before it there is a deterministic row-attribution restoration step (for joint-model projects, per `ai/asr-rows.json`; see AI pipeline design §4.3/§5.0). That step is not part of the carrier contract.

- **Gate**: runs only when `speaker_turns(words).len() > 1`. A single speaker gives zero calls (`skipped: single-speaker`). It is skipped for targeted re-polish with `--paragraphs` (`scoped-run`), turned off by `--no-speaker-repair` (`disabled`), and reports `no-candidates` when the candidate list is empty.

- **Candidates** (screened deterministically by the engine, **not dependent on whether punctuation exists**: punctuation chunking in raw ASR is unstable. In one MOSS transcription, 1115 of 3385 rows have no punctuation and the pattern fluctuates by chunk, so "no sentence-final mark before the word" is only a negative signal): sandwiched short islands (turn ≤4 words and ≤1.2 s, with the same speaker on both sides) and unnatural switch points (gap <0.25 s and no sentence-final punctuation before the word). Islands whose text, stripped of punctuation, falls entirely within the acknowledgment allowlist “嗯/哦/对/OK/是的/对吧…” (uh-huh / oh / right / OK / yes / right?…) are kept directly and not sent to the model. “啊/呃” (ah / er) are deliberately not in the table. Each candidate gets a synthetic window with 40 words of context on each side. Overlapping or adjacent windows are merged, with merged windows ≤240 words. Each call carries ≤8 windows; page id `sk{round}-{serial:03}`.

- **Payload**: each window is a pair of fences, `<<<WINDOW k | n lines | speakers S1,S2 | current: 1-13 S1, 14-14 S2, 15-31 S1>>>` and `<<<WINDOW-END>>>`. Inside the fence there is **one word (one CJK character) per line**, `N| word`, with pause markers `⏸`/`⏸⏸`/`⏸⏸⏸` after the word (time is the strongest signal besides grammar). The block header lists the speaker labels appearing in the window (`SpeakerLabels`, the same table as the ⏹S2 in the polish payload) and the **current** attribution intervals.

- **Answer**: within each window's `<<<WINDOW k>>>` … `<<<WINDOW-END>>>`, one line per interval, `start-end label`, without repeating the words. The lenient forms match §6.6: the block header may omit angle brackets; en/em dashes, single-line `a LABEL`, `a-b: LABEL`, and lowercase labels are accepted, and a single-window page may omit the block header.

- **Validation** (`parse_speaker_repair_page`; the agent `task submit` mirror lint `lint_agent_answer_speaker_repair` uses the same implementation as the engine): intervals start at 1, are contiguous, and run to the last line; labels ∈ the block header's `speakers`. After merging adjacent same-label intervals, the **paragraph count must be ≤ the current paragraph count**. The model can only fold fragments back into neighbours or shift existing switch points; it cannot create new speaker changes out of nothing. Any failure ⇒ that window is `range-invalid` (the detail locates the first defect, which becomes the targeted instruction for the next round). Other windows in the same payload land normally.

- **Application and degradation**: windows do not overlap. Each window's intervals are applied to `sp` (`relabelledWords`). A reduced paragraph count is recorded as `islandsMerged`, a boundary-only shift as `boundariesMoved`, and an unchanged result as `windowsConfirmed`. Before landing, a **deterministic change cap** applies: if a window changes more than 12 words in total, or any contiguous changed run exceeds 8 words / 2.5 s, the whole window is ignored (`windowsCapped`). The contract's "paragraph count must not increase" cannot stop the model from assigning a whole quoted passage to the narrator. In practice, flash assigned 38 words of guest original speech to S1 at the opening of a 7h interview, while the other 266 windows all confirmed the current state. So this wave's evidence scope only reaches fragments and few-word boundary offsets; reassigning whole segments is not its job. `SPEAKER_REPAIR_MAX_ROUNDS = 2`: round two resends only the rejected windows (`retry_reason = "[range-invalid] window N: …"`). Windows still rejected after the rounds are exhausted, or hit retryable transport errors ⇒ **kept as is** (`windowsRejected`), exactly as if no repair were performed.

- **Measurement basis** (multi-person 7h interview, MOSS): 577 sandwiched islands among 1911 turns (the allowlist caught about 530), and 153 unnatural switch points, giving about 150–200 windows ⇒ over twenty calls. Specific figures are in AI pipeline design §5.0.
