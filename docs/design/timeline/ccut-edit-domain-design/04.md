# 4. Derivation and projection

> From [CucCut edit-domain protocol design (Cut / Clip / Element / Watermark / project export)](../ccut-edit-domain-design.md)

## 4.1 studio/data.json extension

`refresh()` remains an idempotent pure derivation and adds a `timeline` section:

```jsonc
"timeline": {
  "rev": 7,                        // independent monotonic rev of timeline.json (same mechanism as the transcript rev)
  "duration": 743.1,               // total timeline length (= output duration, no cut segments)
  "views": {                       // media views (per srcId, including "main")
    "main": { "viewDuration": 743.1,
              "keptSpans": [ { "t0": 0, "t1": 12.40, "viewStart": 0 },
                             { "t0": 13.10, "t1": 47.02, "viewStart": 12.40 } ],
              "cuts": [ { "id", "t0", "t1", "kind?" } ] }
  },
  "clips": [ { "id", "srcId", "in", "out",
               "tlStart", "tlEnd", "viewIn", "viewOut" } ],   // tl*/view* are derived convenience fields
  "tracks": [ /* element windows evaluated to timeline seconds (word anchors resolved); place/animate kept as is */ ],
  "main": { /* as is */ }
}
```

- `views.keptSpans` is the materialized contract of the “database view”: the frontend and the Agent use it to convert any source time ↔ view time, without recomputing the complement of cuts themselves;
- In the projection, word anchors are **evaluated to seconds and the original anchor string is kept** (`{start: 42.6, startAnchor: "~main:g42.0"}`);
- `cues[]`/`sentences[]` keep the media source times unchanged — **view subtitles and timeline collapse are consumer-side behaviour** (recomputed on the JS side from the `views` + `clips` tables, cross-checked with contract fixtures, see §5.5);
- Derivation still happens in a single place, `studio_projection::refresh()`; timeline changes and transcript changes share the rev+fingerprint invalidation mechanism.

## 4.2 Global subtitles = derived view

The principle in one sentence: **content follows the source, presentation follows the timeline.** The output (global) subtitles are not a separate dataset; they are a live derivation of “assembling each source's view subtitles in timeline order” — at any moment they can be rebuilt bit-for-bit from `sources[].cuts` + `clips[]` + each source's transcript.

**Derivation chain**:

1. Each source with a transcript first derives its **view subtitles**: Cues are derived word by word (§18.5), cut words are removed (§3.3-4), and word timestamps are converted to view time — “like subtitles after a physical trim”;
2. The view subtitles of each source are then mapped onto the timeline according to the clips arrangement (§2.3 `clampEvent`): cues that are entirely cut or not arranged are omitted but **numbered consecutively**, drops under 10ms are kept, cues crossing a split boundary are truncated to the clip window, and sentences from reused footage are shown in both places;
3. **Styling and presentation are timeline/project-level configuration** (persisted in `studio/style.json`, projected as `studio/data.json.style`: font, subtitle track set `tracks` [since round 108, the source of truth for “which lines appear on screen”; the legacy display `mode` orig/trans/bi is demoted to a write-only compatibility field derived from the track set], layout position, bilingual layout) — the look of subtitles in multi-source output is uniform and independent of content source;
4. An untranscribed extra source placed in the timeline → that segment simply has no subtitles (or run `clip transcribe` first) — the derivation model behaves correctly by nature; “subtitles without a source” (a hand-written line over a music segment, a title card) **are not subtitles, they are text elements** (§3.6), which the model already covers.

**Transcript editor** (source view): cut words are shown as “strikethrough/collapsed” (UI state); in view mode they are hidden and view times are shown. `hidden` words and cut words both take effect at the subtitle layer (neither is emitted), but their origin is distinguishable (one is a subtitle intent, the other a cut derivation). Markdown export keeps the literal text without retiming; all other exports (SRT/VTT/ASS/MP4/project subtitle tracks) consume the timeline assembly result from step 2 — semantics aligned with the old `CutTimelineMap` + `presentedSubtitleEvents`, generalized to multiple sources.

**How translation works** (decision 11, four rules):

1. **Translations follow the footage**: the `trans[lang][sentenceId]` table continues to live in each source's own transcript ([Transcript v0.3 §18.7](../../bcf/cuccut-format-spec.md) already supports this; `sentenceId = s-<first word id>` anchors to the source word). When footage is cut, spliced, reused or repositioned, existing translations all remain valid — not a single character needs re-translating; a sentence reused twice is translated once and shown in both places.
2. **The input to translation is the timeline projection**: `translate` assembles all **visible** sentences in timeline order (across sources, after cut words are removed) and feeds the output's word order to the LLM as context — the output's word order is what viewers actually hear, and is more correct than the original order of any single source (this correctly handles the context problem of stitching multiple videos); it then **scatters the results back** into each source's trans table by `(srcId, sentenceId)`.
3. **Half a sentence cut → targeted re-translation**: the sentence staleness fingerprint extends from the “source word sequence” to the “**visible word sequence**” (a direct extension of the existing `transSrc` mechanism). When cut/restore changes a sentence's visible words → that sentence's translation becomes stale → only that sentence is re-translated. What gets translated is always the text the viewer actually sees.
4. **Edits to global subtitles are routed**: when the UI edits one translated line in the output subtitles, the change is actually written back to the corresponding source's trans table (located via `(srcId, sentenceId)`) — the same pattern as today's studio writing cue edits back into the transcript overlay, with no new mechanism; the `translation` op of `transcript/apply` only needs cross-source routing added.

Concrete changes to the existing translation pipeline: the `transSrc` fingerprint is computed over the visible word sequence; after a cut/restore transaction (including clip add/remove/trim and source deletion), a stale scan is **triggered immediately** — results go into the CLI receipt and into `staleTranslations` in the `timeline/apply` response, rather than surfacing lazily only at `ccut check`; the `translate` assembly stage reads the timeline projection rather than a single transcript; stage stamps/fingerprints are slotted by srcId (each source's transcript document carries its own `stages`; extra sources write asr/asrLayout stamps through `clip transcribe` using the same builder). **Protective boundary of stale detection**: only translations carrying a `transSrc` stamp can become stale — purely manually entered translations (the edit route writes no stamp) are never judged stale, so that `check` does not guide re-translation that overwrites manual text (same semantics as `stale_sentences` for a single document). Whether polishing/segmentation/chapters are opened to extra sources is scheduled separately (§11).

## 4.3 Bridge to BCF (one-way, compile time)

`timeline.json` can be deterministically compiled into an equivalent BCF document fragment (not written to disk, or written explicitly via a future `export --to bcf`):

```
clips (cuts subtracted, expanded into kept sub-segments) → main clip sequence of the visual track: video element + mediaStart/segment/rate
element                                                 → overlay clip (place → style px converted to the target canvas; animate kept as is)
word anchor                                             → BCF ~ anchor (refId converted to the qualified form of the corresponding clip id)
subtitles                                               → captions track derived via from (reusing §8.4)
```

This is the semantic basis for overlay burn-in and reuse by the BCF rendering domain: **the burner does not reinvent sampling semantics; it consumes the animation/element model already expanded by BCF** (§6.5). In addition, the “reference window” definition in [format spec §18.6](../../bcf/cuccut-format-spec.md) is extended by one item: **the kept sub-segments of a timeline clip are also media reference points** (revision checklist §10). The reverse direction (BCF → timeline) does not exist — BCF expansion output is not written back into the timeline document. Note that this only bounds the timeline domain: when the project uses TSX as the source of truth (`entry` exists), UI edits to BCF elements are written back to the TSX/data layer per the three-channel contract in format spec §13.3 (design in [ccut-bcf-direct-edit-design.md](../../bcf/ccut-bcf-direct-edit-design.md)), and do not cross into the timeline domain.
