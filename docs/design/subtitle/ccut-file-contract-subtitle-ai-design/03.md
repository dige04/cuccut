# 3. Overall Architecture: Swapping Tracks by Contract

> From [CucCut File-Contract Subtitle AI Pipeline Design (File-Contract Pipeline, v0.3)](../ccut-file-contract-subtitle-ai-design.md)

Every LLM stage follows the same four-step pattern:

```
render (code) → edit (LLM/Agent edits the files) → parse+lint (code) → apply (code writes the source of truth)
```

| Stage | Input file | What the LLM does | Output file | Parse and write back |
|---|---|---|---|---|
| analysis | full-text txt (paged) | summary + glossary | `context.md` | stored in `ai/` for later reference |
| polish+segment | per-page txt (read-only context fence) | revise the text in place, insert blank lines at paragraph breaks | per-page txt | diff → LCS rebinds `words`; blank lines → `paraBreaks` |
| translate-brief | `context.md` | translate the summary and glossary | `context.<lang>.md` | stored in `ai/` |
| translate | sentence-level HTML (paged by paragraph) | translate the whole page, ids unchanged | isomorphic HTML | parsed by id → `trans` + `transSrc` |
| align | HTML table of over-long sentences | split rows in both columns in sync | isomorphic table | parsed row fragments → `transAlign` |

Key points:

- **The renderer, parser and validator are all pure functions inside `ccut-flow-core`** (zero I/O; inputs and outputs are in-memory strings or structs, new module `filepipe/`). The host only moves files. This guarantees that submit lint, the provider path and offline tests are one and the same implementation.
- **HTML is always handled by a real HTML5 fault-tolerant parser** (html5ever or equivalent), not by regexes. Reason: regexes cannot determine where element text begins and ends (embedded `<em>`, `<br>` added by the model, and literal `a > b` would all break the heuristics), whereas html5ever tolerates unclosed tags and misnested elements, which is exactly the leniency we want. **Tag names are not part of the protocol**: the parser extracts nodes by their id/data attributes, so a model writing `<p>` as `<div>` is not an error (§7.4).
- LLM output is always written to a file first and only then parsed. The provider path also writes `pages/pNNN.out.*` before entering the parser, so the artifacts and audit trail of both paths are fully isomorphic.
