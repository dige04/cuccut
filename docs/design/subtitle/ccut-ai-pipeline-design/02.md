# 2. Overall architecture

> From [ccut transcript post-processing AI pipeline technical plan (polish / segment / chapters / translate / subtitle alignment)](../ccut-ai-pipeline-design.md)

## 2.1 Stage pipeline

```
 Media file
   │  ccut transcribe (no LLM)
   ▼
 ┌──────────────────────────────────────────────┐
 │ Stage 0  ASR + VAD + forced alignment → persist words │  rows → Word atomic
 │          interview.transcript.json (§18)              │  words are the single source of truth
 └──────────────────────┬───────────────────────┘
                        │  ccut polish / auto
   ┌────────────────────▼───────────────────────┐
   │ Stage 1  polish (LLM)                        │  edits text, keeps id/t0/t1
   │ Stage 2  segment (LLM + deterministic ladder)│  writes breaks/paraBreaks
   │ Stage 3  chapters (LLM)                      │  writes chapters
   └────────────────────┬───────────────────────┘
                        │  ccut translate --lang zh
   ┌────────────────────▼───────────────────────┐
   │ Stage 4  translate (LLM, sentence level)     │  writes trans / transSrc
   │ Stage 5  display split + alignment (LLM + deterministic) │  sentence translations → per-Cue fragments
   └────────────────────┬───────────────────────┘
                        │  ccut export / BCF `from` derivation
                        ▼
        SRT / VTT / bilingual karaoke subtitles / .ccut.json captions
```

The full order of `ccut auto` is `transcribe → [chapters skeleton] → [polish] → [chapters] →
[translate, including streaming alignment] → [final re-alignment]`; the actual execution sequence is recorded in the envelope `data.steps`.

## 2.2 Five core disciplines (pipeline-wide invariants)

These five rules are conclusions the voice-ink project reached through many milestone iterations. This design inherits them as **hard design constraints**:

1. **Timestamps never enter the LLM.** The LLM sees only plain text (plus soft pause/speaker markers) and returns only text. The word `id / t0 / t1` values are re-anchored by a deterministic algorithm after the response is received. Timeline correctness never depends on the model behaving well.
2. **Deterministic validation, not trust in the prompt.** Each stage applies decidable semantic checks to LLM output (coverage, normalized-character equality, id reconciliation, similarity thresholds). Failing any check fails that attempt. Rules like "the model may only add punctuation" are **proven** by strict equality of `normalize_chars`, not enforced by wording requests.
3. **Layered degradation; the whole never fails.** When retries are exhausted, fall back step by step to more conservative deterministic algorithms (the bottom layer is pure rule-based segmentation, which never fails). Text may degrade back to the original words, while **boundaries and the timeline always remain valid**. The sole exception: non-retryable errors such as authentication failure or a nonexistent model abort the entire run immediately. Degraded results must never mask configuration problems.
4. **Fingerprint-driven dirty detection.** Each stage output records content fingerprints of its inputs. Editing text makes polish and translation stale but does not make segmentation stale (segmentation is keyed on id). Re-transcription reissues all ids, which makes everything stale. "What must be rerun" is derived, not kept in a ledger.
5. **Resumable runs.** Page boundaries are deterministically re-derived from the fingerprinted word stream. The progress file stores only the minimal state of completed work. Re-entry after a crash or cancel is safe, and the progress file must be deleted on completion.

6. **Language and content are checked before settlement.** Before a transcript is written, check the explicit source language, the model-detected language and the dominant script of the full text. Translation answers must pass the target-script, placeholder, source-copy, abnormally-short-translation and batch-collapse checks before they reach the cache, hedge settlement and `trans` writes. Valid HTML/IDs only prove the carrier is parseable, not that the translation is complete. Translation carriers carry the validator version, so a version upgrade automatically invalidates old answer caches.

## 2.3 Rust placement

```
core/crates/
├─ ccut-speech-core       (existing) + refine wiring, word-tokenization build step
├─ ccut-speech            (existing) host inference layer, unchanged
└─ ccut-flow-core         (new) pure logic: fingerprints, pagination, atom-LCS, rebind,
                               per-stage engines (LLM injected as a trait), validation, degradation ladder

apps/cli/
└─ ccut                   (existing CLI) + host executor for ccut-flow-core:
                               direct provider calls (ureq) / agent reply loop (file contract),
                               progress persistence, command surface
```

The layering principle matches the speech side: `ccut-flow-core` has **zero I/O and zero network dependencies**. The LLM is a trait
(`LlmJson`), so all engine logic can be tested offline with scripted fake implementations (corresponding to voice-ink's `FakeLLMJSON`).

```rust
// ccut-flow-core/src/llm.rs
pub trait LlmJson: Send {
    /// One JSON-mode call: system + user → raw response text.
    /// Parsing, fence stripping and semantic validation all happen on the engine side (§10).
    fn complete(&mut self, req: LlmRequest) -> Result<String, LlmError>;
}
pub struct LlmRequest {
    pub kind: &'static str,       // "polish" | "segment" | "chapters" | "translate" | "align"
    pub model: String,
    pub system: String,
    pub user: String,
    pub temperature: f32,
}
```
