# Writing a good design system: rules

SKILL.md has the checklist; these are the rules behind it. A design system exists so that later agents can build on this brand - write it from the brand's **real** sources (the codebase, attached files, presentations, specs).

- **The README is usage rules written for the agents that use it** - the page shows it as the brand guide. Use the imperative and **name** tokens, styles and assets ("Use `body` for body text; use `ink` on `surface-100`; Clay only for Claude's own voice"). No heading (the page shows the design system's name), no sources, build notes or "next steps" - those go in your reply. Length follows the source: for a few dropped-in files, write a few bullet points; a real codebase or guide deserves sections, with the brand's own examples - content fundamentals (tone, capitalization, "I" or "you", emoji or not; quote real copy), visual foundations (color, typography, spacing, imagery, motion, state, borders, shadows, radii, layout), iconography (which icon system, format, emoji or glyphs). Never pad.
- **Assets are copied, never imitated.** No logo in the source ⇒ set the name in plain text and note that there is no logo; never draw or reconstruct a real company's logo from memory, and never restyle the brand with an identity the user did not provide. Copy the brand's own icons (icon font, sprite, SVG); if they really cannot be had, substitute the closest alternative and **flag** it under Iconography.
- **The source decides the inventory.** Tokens: the real names and values in the source, in its order. Components: exactly the families the source defines - no "common" extras (Toast, Avatar, ...) unless listed under "Intentional additions" with a reason; only a brand starting from scratch or with spec text alone gets a standard component set. List the **full** inventory first, track against it, build all of it; if you stop partway, report exactly what remains and ask - never quietly finish without being done.
- **Values are exact, taken from the real source.** The source beats any component library that resembles it (shadcn, MUI, ...); copy padding, radii, sizes and line heights exactly - 5px is 5px, do not snap it to a grid. Code is the truth, screenshots are a lossy reference; previews are replicas, never reinventions. If reading fails partway, say what you read and what you did not - never invent names, structure or values.
- **Each value has one source.** During a cleanup, values that went into `tokens.json` are **removed** from the stylesheets the previews load, so values changed on the page win; keep ones the page does not declare with the same `--name`. This amounts to redoing the stylesheet, someone else's stylesheet included: first move its old version aside whole (see "Move other people's work aside" below). The page writes `tokens.css` only when someone saves: when the design system has no `tokens.css` of its own, you write the first one, laid out like the "compiled tokens.css" item in `format.md`, with the first line `/* <title> — generated from tokens.json */` (the page takes over only a file whose first comment ends with these words). If the design system's components wrap themselves in an element that declares tokens, values from the page cannot get inside: still write their values into `tokens.json`, delete nothing, and tell the user that editing on the page will not change those previews.
- **Leave no stale `manifest.json`.** During a cleanup, **delete** the old `manifest.json` and never rewrite it: it lists paths that no longer exist, and the page writes no new one until someone saves an edit.
- **Move other people's work aside.** A cleanup deletes only the old `manifest.json`, `migration-map.json` and `publish-progress.json` at the design system's top level; files with these names at any other path belong to someone else. Any other file can leave its path only by a **move**: **one** change that writes the file to a free path (no file there, and no other file being written there) with content exactly as you last read it (copy it, never retype it), and deletes the old path. A file going unchanged to the place `format.md` gives it is moved there. Files you would otherwise delete (cards you split or redo, whether in their original place or on their way to their place; an HTML page showing color, typography, spacing or radius specimens) are **moved aside**, to `archived/` + their path in the design system. Stylesheets too are moved aside whole before values are extracted from them: **one** change moves the old file aside and writes the new file at its path. In `README.md`, fix the paths, delete the section appended at the end during migration ("## Migrated from …"), then add to it; delete or rewrite nothing else. Leave no kept file still linking to a path you emptied; the migration's own notes under `assets/notes/` (or `docs/`) are neither moved nor repointed.
  Files that cannot be moved (no free path; your tools cannot delete files) stay where they are: list them by name. Never move what was already in `archived/`, and never propose deleting it. Move a specimen page aside only after every color, size and `--name` it shows has gone into `tokens.json` with the same value (search the specimen page for `#`, `rgb`, `hsl`, `lch`, `lab`, `px`, `em`, `%` and `var(--`). An HTML page showing logos or icons is not a specimen page: redo it as a preview at `components/<Comp>/preview.html`, then move the old page aside like any other card. Never move away a file that kept files still link to, unless a new file takes its path or those links have been repointed.
- **Every token and asset has a usage note** saying where it is used (for an SVG with a single ink, the note names its ink - `<img>` cannot inherit color).
- **Legible in every theme.** A text color's usage note names the background it sits on ("Body text on `surface` and `surface-raised`"), and every such pair reaches at least 4.5:1 contrast in **every** theme (WCAG 2; 3:1 for 24px+ or 19px+ bold text, and for any meaningful border, focus ring, icon or other mark) - check the values of the later themes, not just the first theme's. What component previews and `bundle.css` draw must meet the same floor. Colors you choose yourself (a brand starting from scratch, previews' own styles, focus rings) simply meet it: a dark theme that lightens the accent usually needs dark text on it, so give such a fill an `on-…` token rather than hard-coding white; make a focus ring you choose solid, at least 3:1 on every surface it lands on, and write it under visual foundations. Pairs in a real source that fall short stay as they are - say so in their notes rather than quietly recoloring the brand.
- **Accessibility requests have fixed meanings.** A *high-contrast theme* is an **additional** theme, never a recoloring of the brand's own themes: every text color reaches at least 7:1 on the backgrounds its note names (4.5:1 for 24px+ or 19px+ bold text; WCAG AAA), and surfaces and controls are told apart by borders reaching 3:1, not by shade alone. *Color-blind-safe status colors*: each status also carries a word or icon, and success and danger must never be a green and a red distinguished only by hue - either the two differ in lightness by at least 3:1, or the success color moves off the red-green axis toward blue (an orange danger color next to an ordinary green does not count). A green and red in a real source that do not satisfy this stay as they are: the safe pair goes into an **additional** theme next to the brand's own, like the high-contrast theme, with their usage notes stating which theme is safe. No brand hue to keep ⇒ start from the Okabe & Ito palette, darkened where used as text. An *audit* for either of these lists the failing pairs by theme before changing anything, each with a suggested fix. This is what each request means on its own - the user's explicit instructions take precedence over these definitions, and a real source's own colors stay as they are, as above. This skill's `references/sample-seazar-tokens.json` is a worked example of all this (see its tokens).
- **Usage guides state what consumers must provide** (props, children, container, data), and when to use it, with dos and don'ts.
- **Fill in real material:** fill in everything in each theme that differs from the other themes, hook the type scale up to the brand's real font files, and give every component a live preview **and** a README.
- **Avoid AI clichés** unless the source really has them: blue-purple gradients, emoji as decoration, rounded cards with a colored left-border accent, filler statistics, overused fonts (Inter, Roboto, ...). No filler content; keep targeted changes targeted; never replicate a company's proprietary interface for someone who does not work there.
