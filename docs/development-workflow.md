## 1. Specification and Implementation

Before changing anything, find the specification section that owns the behaviour, the implementation, and the adjacent tests. Judge the target contract in the documents separately from the current implementation status. A feature is not implemented merely because the specification defines it.

- When you intentionally change a protocol, format or public behaviour, update the corresponding specification, implementation and tests in the same task. If usage is affected, update the related README as well. Parameters, defaults, error codes, exit semantics and JSON output all count as public behaviour.
- When fixing an implementation to satisfy an existing specification, do not mechanically rewrite the specification. If you find a gap in the specification, a conflict within it, or an implementation that deviates from it, state the relevant section and the difference. Product decisions that exceed the task's authorization are for the user to decide; do not hide a defect by changing the specification.
- Business semantics and state ownership follow [architecture design §1](architecture/architecture-design.md#1-overall-architecture). Do not duplicate authoritative logic in the UI, in scripts, or across several clients.
- Documents are consolidated into their owning topic according to the [writing rules](README.md#writing-rules): one fact in one place, one topic per document, with the body keeping its table of contents. Do not create a separate change log for this workflow, and do not append process records to the README.

### 1.1 Commit Classification

Both automatic and manual commits use `type(scope): summary`. The type and scope are in English. The summary and body are in English by default; if the user explicitly specifies another language, follow that instruction. The scope is a second-level category and uses a stable module or feature topic name (lowercase-dashed), such as `file-location`, `preview` or `release`. Multiple commits fixing the same kind of problem must reuse the same scope. Prefer existing categories and do not rename the scope in each commit. Other standalone items that cannot reasonably be assigned to a topic may omit the scope. Choose the type by the actual purpose of the change, so that changelogs can be assembled from commits and PRs at release time:

| type | Applies to |
| --- | --- |
| `feat` | Adding or extending product capability or user-visible behaviour |
| `fix` | Fixing a defect so that behaviour matches expectations |
| `docs` | Changes to documentation, specifications, development agent instructions or skill descriptions |
| `refactor` | Restructuring implementation without changing external behaviour |
| `perf` | Improving performance |
| `test` | Only adding or adjusting tests |
| `build` | Changes to the build, packaging mechanism or dependencies |
| `ci` | Changes to continuous integration and release workflows |
| `chore` | Routine maintenance outside the types above, such as version numbers and pinning to verified release versions |
| `revert` | Undoing an existing change; the body names the reverted commit and the reason |

The summary states the action, the object and the key result. Do not use vague summaries such as `update`, `fix some issues` or `auto commit`. For example, related file-location fixes are unified as `fix(file-location): handle Windows extended paths` and `fix(file-location): handle directory names with spaces`. A release-notes change uses `docs(release): require complete batched changelog summaries`. When the reason, impact or compatibility needs explaining, write it in the body. For breaking changes, add `!` after the type/scope, and state the impact and migration method in the body with `BREAKING CHANGE:`.

Each commit expresses one understandable purpose. A feature or fix together with its corresponding documentation and tests belongs in one commit, and the type is chosen by its main purpose. Unrelated changes are committed separately, but do not split one change into pieces just to classify them. Release notes must still be checked against the actual content. Do not skip sources or infer user impact from the type alone.

### 1.2 Commit Tidying Before Merge

Before a task branch or worktree is merged back into `main`, review all changes on that branch relative to the merge baseline. Consolidate the development attempts, patches, corrections and their matching tests and documentation into 1–N meaningful commits. The number is determined by the independent items: one feature or one fix usually gets one commit, and several independent items keep a small number of separate commits. Do not keep the count mechanically tied to the number of original commits, and do not squash unrelated content into a vague “merge branch” commit. A shared scope only helps classification; it does not mean that all fixes must be squashed into one commit.

Each tidied commit is named according to §1.1. Its summary describes the final delivered result. Its body lists the specific fixes, limitations, migration requirements and PR/issue basis that must be kept, so that it can serve directly as the source for the changelog. Reverted attempts must not be written up as final capabilities, and independent fixes must not be lost during consolidation. When a PR is squash-merged, the PR title and squash body follow these same requirements and must not reuse a temporary branch name or a running log.

You may squash or rebase on this task's exclusive branch, or generate the tidied commits at merge time. Tidying applies only to content from this task that has not yet been merged. Do not rewrite the history of `main` or of published tags. Shared branches and other people's commits keep their original history, and the same result is reached by consolidating at merge time. After tidying, verify that the net change before and after is equivalent. After resolving conflicts, re-verify according to the actual impact. After merging, confirm the commit boundaries and summaries. Branch tidying does not include authorization to push or force-push. Cleanup of worktrees, branches and dedicated targets still follows the root AGENTS.md.

## 2. Verification

First choose checks according to the scope of the change, then run them. For behaviour changes, add or adjust tests that cover that behaviour. When fixing a bug, prioritize covering the original failing scenario. Pass criteria and test levels are described in [acceptance and testing](acceptance/acceptance-spec.md). The table below only gives the execution entry points for the current repository.

Commands run from the repository root by default. Replace `<受影响 crate>` and `<测试文件>` with the actual name or path.

For system dependencies and platform installation steps for source development, see the [README](../README.md#run-from-source-macos-apple-silicon). `npm run doctor` only checks the environment and returns a non-zero exit code when a required tool is missing. `npm run setup` checks and builds the native Worker and WASM. `npm run dev` runs setup automatically and stops startup if the build fails. Shell development without Rust uses `npm run dev:lite`, which must clearly print its capability limits before startup. It is not an acceptance environment for native features. The minimum Node version is 22.12 (Vite's Node 22 requirement). npm scripts that execute TypeScript source directly must explicitly enable `--experimental-strip-types`, so they remain compatible with 22.12–22.17, which do not yet enable type stripping by default. When changing this group of development entry points, run `npm test -- tools/dev-check.test.ts`, and verify both the normal startup path and the failure exit path. Cross-platform simulated tests cannot replace an actual build on the corresponding operating system.

- Report build success, automated test results and visual acceptance separately. For UI changes, open the actual page and check the target state, interactions and console. - When a toolchain, model, credential or specific platform is needed but cannot be run, report the skipped items and the reason. Acceptance items are definitions and are not a record of anything that has been executed.
- Development startup scripts may continue to start after an engine or WASM build failure. You must check the build result. Do not treat a relevant capability as passing just because the window opened.
- After checks pass, expand or repeat verification only if new changes were made, something failed, or doubts remain. The delivery notes must report the actual check results and the known untested items.

## 3. Multi-surface sync

For any change to user-visible layout, visuals, interaction, copy or state behaviour, finalise it in the prototype first, then audit the corresponding feature on the existing surfaces below:

| Surface | Implementation and constraint entry point |
| --- | --- |
| Prototype | `designs/cuccut`; read the [local protocol](../designs/cuccut/AGENTS.md) first, and when shared components change, check the App / Web entries according to its rules |
| Electron | `apps/desktop` assembly; shared UI in `packages/ui` |
| Web | `apps/web` assembly, reusing `packages/ui`; scope is set by the current product and architecture specs and the entry point's capability limits |

- **Prototype first**: user-visible design changes are made in the prototype only; after verification and commit, hand them to the user for confirmation. Until confirmation, do not change the Electron and Web implementations (`packages/ui`, `apps/desktop`, `apps/web`). The delivery note states that the real pages are not yet changed and await confirmation. After the user confirms the prototype, change Electron / Web according to the confirmed result and complete the audit below. Changes that have no corresponding screen in the prototype, and defect fixes that do not change the design, may be implemented directly once the reason is stated.
- Sync the applicable corresponding features, reusing shared components and semantics, without directory-level copying. When shared UI covers multiple clients, still verify each entry separately, watching for differences in host capabilities, permissions and resource loading.
- If a surface has no corresponding feature or is out of its scope, do not add a placeholder implementation; state in the delivery note that it does not apply and why. Do not carry over Web freeze or desktop migration status from other repositories.
- Pure protocol, architecture, engine or background changes that do not yet change user-visible UI are not synced early on the grounds that some surface may adopt them later.
- Differences between the prototype and the spec are listed per its [sync discipline](../designs/cuccut/AGENTS.md#同步纪律). When the task has authorised changing product behaviour, sync the corresponding spec; otherwise report the difference first and do not change product decisions on your own.
- Icon size, semantics and sync checks refer uniformly to [repository conventions §4](repo-conventions.md#4-interface-icons).

## 4. Language and platform

The agent's reply language follows the [root rule](../AGENTS.md#reading-and-language); media, scripts, translations and dubbing processed by the product can be in any language, and the two are judged separately.

- Output language: prefer the language the user explicitly asks for, then the recorded preference, then infer from task context. Do not make a language the product default just because code, docs or examples use it.
- Prompts, task contracts, length, speaking rate and line-break rules use metrics suited to the target language; if a number only applies to one script, state its scope and how other languages are handled.
- When branching by language or script, unlisted languages must have an explicit fallback and must not be quietly treated as English. When adding or fixing such behaviour, cover the corresponding languages and the fallback path; objective limits such as the languages the model supports are kept as they are.
- Human-facing text goes through the unified multilingual mechanism ([repository conventions §5](repo-conventions.md#5-copy-and-multilingual-support)); English and every shipped language are written together; layout does not assume a fixed character count or text direction.
- Platform-specific APIs, dependencies and backends are isolated through target configuration or capability detection, avoiding unconditional introduction of Apple-only interfaces and the like. When a platform is unavailable, behaviour is explicit; a backend the user specified is never silently swapped.
- After changing prompts, defaults, language validation or platform branches, review the language and platform assumptions in the change, verify the relevant paths per §2, and report environments not covered.

### 4.1 Cross-platform system integration

When changing host capabilities such as opening, revealing, selecting or dragging in files or directories, and system menus or launching external programs, you must audit applicability on Windows, macOS and Web; do not infer other platforms from behaviour on the development machine.

- **Copy matches action**: for file-manager reveal, use the glossary term [glossary](glossary.md#english-ui-terms) “在文件夹中显示 / Show in Folder”; do not hard-code Finder or other platform names in shared UI. Distinguish 在 CucCut 中打开 (open in CucCut), 用系统默认应用打开 (open with the system default app) and 在文件夹中显示 (show in folder). When a project is not registered or the current format cannot be opened in the app, that does not mean the file or directory on disk cannot be located; the prompt must state which action is restricted.
- **Path checks across boundaries**: trace paths returned by Runtime / Rust, UI concatenation and host calls, checking files and directories separately. Windows covers drive-letter paths, UNC network shares, `\\?\C:\…` and `\\?\UNC\server\share\…` extended paths, mixed separators, and names with spaces and non-ASCII characters; macOS covers POSIX paths. Use the target platform's path rules and the existing conversion entry points; do not treat `path.normalize` as a guarantee that the Windows extended namespace is removed, and do not blindly strip unknown namespace prefixes.
- **Entries follow host capabilities**: the desktop app calls system interfaces through the host bridge; the Web cannot locate local directories on the computer running the Runtime, so it offers no action that implies it works. Where a platform lacks a capability, the behaviour is explicit: hidden, disabled or explained. Never show a clickable button that silently does nothing.
- **Cover the original failure scenario**: beyond path unit tests, on the target system, reveal the source file, project directory and video directory separately; cover creating from the CLI and then entering the desktop app, closing and reopening, and targets that do not exist or cannot be accessed; check which file manager actually opened, the selected target, the failure message and the console. Passing path-conversion tests or a successful IPC call is not enough to prove the system file manager opened.
- **Report verification limits honestly**: run checks proportionate to the impact per §2. Without a physical Windows / macOS machine, still verify the executable path branches, and explicitly list the untested system interactions; do not record local or simulated test results as cross-platform passes.

## 5. Workspace and artifacts

### 5.1 Dependencies and generated files

- Dependency changes are made with the corresponding package manager, and the lockfile is committed; do not edit it by hand. The root npm workspace corresponds to `package-lock.json`, and the Cargo workspace to `Cargo.lock`; independent directories (such as the prototype) maintain their own lockfiles.
- Build outputs are handled per [repository conventions](repo-conventions.md#2-placement-rules). Generated files in the prototype that must be committed are rebuilt and committed per the [local protocol](../designs/cuccut/AGENTS.md#验证), not hand-edited. Existing historical generated files are not staged in passing during unrelated tasks.
- Temporary answers, screenshots, rendered frames, test projects and media go in temporary directories outside the repository. Test fixtures that are intentionally maintained go in their owning test directory; do not commit user material, model weights or temporary output as fixtures.

### 5.2 Worktrees and preview

- Work in the checkout that belongs to the current task; do not switch back to the main checkout to modify or verify another copy of the code. Changes that existed before the task or appear concurrently belong to the user: do not overwrite them, and do not sweep them away with a bare `git stash`.
- Each worktree uses its own `CARGO_TARGET_DIR` and does not share it with the main checkout or other worktrees. First check the main checkout's local target configuration and available space; when an external drive is needed, create a dedicated directory named after the worktree in the same storage location.
- For the local configuration template, see [`.cargo/config.local.toml.example`](../.cargo/config.local.toml.example). Ignored local configuration does not automatically carry into a worktree; before building, check the returned `target_directory` with `cargo metadata --format-version 1 --no-deps`, and the build and verification for the same task keep using that path.
- The preview server must point at the current checkout, use its own port, and read the resources changed in this work to confirm where the server is serving from. For details of the prototype's HTTP preview, see the [local protocol](../designs/cuccut/AGENTS.md#验证); a page from another checkout cannot serve as acceptance evidence.
- When finishing, stop the preview servers this task started. Handle the worktree, branch and dedicated target directory per the [mandatory completion gate](../AGENTS.md#mandatory-completion-gate), cleaning up only resources this task owns.

### 5.3 Development data and session records

To review “what that last run did” (which tools the agent called, what the arguments were, where it changed the video, where the artifacts are), read the Runtime data directory directly; do not infer from UI screenshots or the agent's own account.

- **Location**: in development (`npm run dev` launching Electron, or Runtime launched from the repository), the CucCut home directory is the git-ignored `.dev/cuccut-home/` in the repository (see `apps/desktop/src/main/index.ts`; `CUCCUT_HOME` overrides it). The packaged app uses `~/.cuccut`, and the user project directory is `~/CucCut` (`packages/runtime-storage/src/home.ts`). `~/Library/Application Support/CucCut/` is v2 data and unrelated to v3.
- **Files for sessions without a project**: sessions not belonging to a project create videos and write files in their own working directory (architecture design §3.10). When the home directory is the default `~/.cuccut`, that directory is under the system's application data directory (macOS `~/Library/Application Support/CucCut/Sessions/<session id>/`, Windows `%LOCALAPPDATA%\CucCut\Sessions\`, Linux `${XDG_DATA_HOME:-~/.local/share}/CucCut/Sessions/`). In development and under other `CUCCUT_HOME` values, it is `scratch/<session id>/` inside the home directory; `CUCCUT_SESSIONS_DIR` overrides it. The `conversation.cwd` in the session record is this directory.
- **Session records**: `store/conversations/conv_<id>.jsonl`, an append-only log (architecture design §3.10). The first line is the file header, the second line is a snapshot (the full record), and subsequent `item` lines replace or append by `item.id`, while `meta` lines replace metadata. Do not `JSON.parse` the whole file. `grep -l` for finding files still works. For the full record, replay first, for example `node -e 'const L=require("fs").readFileSync(process.argv[1],"utf8").split("\n").filter(Boolean).flatMap(l=>{try{return[JSON.parse(l)]}catch{return[]}});const r=L[1];const ix=new Map(r.items.map((x,i)=>[x.id,i]));for(const l of L.slice(2)){if(l.op==="item"){const i=ix.get(l.item.id);i===undefined?(ix.set(l.item.id,r.items.length),r.items.push(l.item)):r.items[i]=l.item}else if(l.op==="meta"){Object.assign(r,{...l,op:undefined,tasks:{...r.tasks,...l.tasks}})}}console.log(JSON.stringify(r))' <file>`. `.json.migrated` files are old files from before migration, and `.corrupt-*` files are files that could not be recognised and were kept. After replay, the top level is `conversation` (title, `cwd`, `driverId`, times) and `items[]`. `items[].kind` takes `user-message`, `agent-message`, `reasoning`, `task`, `tool-call`, `video-created`, `video-change` or `slides-created`. Tool-call fields are `tool` (`mcp` / `command` / `web-search`), `title` (MCP tool name, such as `cuccut.speak`), `detail` (arguments as a JSON string), `output` (result), `status` and `durationMs`. Video changes have `label`, `transactionId`, the before and after `videoRevision`, and `durationSeconds`. After finding the file by title or by `grep -l` on a keyword, filter by `kind` with a script; do not read the whole file.
- **Tasks and artifacts**: `store/jobs.jsonl` is the job record (append-only: the first line is the file header, followed by `put` and `remove` lines; for the same `jobId`, the last `put` wins, and a `remove` deletes it; for example, use `jq -c 'select(.op=="put")'` and then take the last one by `.record.jobId`). The application ledger `store/applications.jsonl` works the same way. Artifacts are in `artifacts/<sha256>.<extension>` (synthesised audio, exported subtitles and saved JSON are all here; drop the `sha256:` prefix from `artifactId` to get the filename). Sessions without a project work in `scratch/conv_<id>/`, and files the agent saves to the working directory and exports are all there. When a session first creates a video it is bound to a new project; the contents move into the project and the directory under `scratch/` disappears (architecture design §3.10). The runtime log is in `logs/runtime.log`.
- **Boundary**: this is the user's data; read-only. When processing is needed, write the result to a temporary directory outside the repository.
