# CucCut Command and Protocol Specification

> The UI, the CLI and agents change videos through the same set of commands. This specification defines the command envelope, edit transactions, receipts, time inputs, batch pre-validation, undo, events and the error contract.

Protocol version: `protocolVersion: 1` (that is, `eventProtocolVersion`).

This specification defines the **shape and semantics of requests, responses and events**. For transport, authentication, the subscription mechanism and process boundaries, see [System Architecture Design](../architecture/architecture-design.md) §4; for the video data being modified, see [Video Format Specification](video-format-spec.md); for code synthesis, see [Code Bundle Specification](code-bundle-spec.md). For terminology conventions, see [Document Conventions](../README.md#conventions-for-this-document); for terms, see the [Glossary](../glossary.md).

## 1. Scope and Conventions

### 1.1 One Entry Point

All requests that modify a video follow the same path:

```text
Client (UI / CLI / agent tools)
  → Command from @cuccut/client
  → Runtime: authentication, authorization, idempotency, building the transaction
  → VideoEngine: validation, quantization, atomic commit
  → Receipt + events
```

UI gestures, agent tool calls and automatically applied task results use the same set of `EditOperation`s and pass the same validation. There is no bypass path reserved for any one class of caller.

### 1.2 Three Kinds of Request

| Type | Purpose | Changes state |
| --- | --- | --- |
| Command | Requests one modification or starts one execution | Yes |
| Query | Reads a version or the latest state | No |
| Subscription | Obtains a snapshot at a watermark and the events after it | No |

### 1.3 Status of the Types

Types are written in TypeScript notation. They are DTO outlines and do not represent a generated SDK or schema. The full set of methods and operations is generated from a single contract source (Architecture Design §13.2). This specification lists representative entries and the rules they must satisfy. Types marked "supplemented by this spec" have only a name or usage in the original design and are listed in §13.

The basic types `Id`, `Revision`, `VersionRef`, `JsonValue`, `Rate` and `MediaTime` are defined in Video Format Specification §1.2 and §2.3.

### 1.4 Numeric Values at the Boundary

- `Revision`, `eventSeq` and `ticks` are checkable decimal integer strings.
- Frame counts and the numerator and denominator of a frame rate must fall within the safe integer range set by the protocol.
- The interface boundary rejects NaN, Infinity, negative durations, unreduced `Rate`s and invalid time domains. It does not try to guess.

## 2. Envelope and Identity

### 2.1 CommandEnvelope

```ts
interface CommandEnvelope<T> {
  protocolVersion: number;
  requestId: Id;                     // relates only to this one network request
  commandId: Id;                     // business operation ID, unchanged on retry
  method: string;
  videoId?: Id;
  expectedRevision?: Revision;       // decimal string
  taskId?: Id;
  payload: T;
}
```

- Commands that modify a video must carry `videoId` and `expectedRevision`.
- Commands that belong to a task carry `taskId`. The server uses it to check the task contract, authorization and the stop barrier.
- The form of `method` is `<namespace>.<action>`, for example `edits.apply` or `tasks.stop`.

### 2.2 What the Client Cannot Declare

Public requests **must not** carry `actor`, `trusted=true` or an arbitrary `budgetApproved`. A request carrying these fields is rejected, not ignored.

The server determines the following:

| Item | Source |
| --- | --- |
| `actor` (who is operating) | Runtime builds it from the authenticated connection |
| `transactionId` | Assigned by the server |
| Available permissions and authorizations | Server resolves them by principal, video and task contract |
| `runGeneration` | Server fills in the task's current execution generation |
| Whether the budget is approved | Server judges from the authorization record |

### 2.3 Six Kinds of ID

| ID | Identifies | Lifetime |
| --- | --- | --- |
| `requestId` | One network attempt | Different on every send |
| `commandId` | One business operation | Reused when the same operation is retried |
| `transactionId` | One video transaction actually committed | Assigned by the server |
| `jobId` | One computation | Assigned by the server |
| `applicationId` | One action that applies an output to the video | Assigned by the server |
| `taskId` / `runId` | One delegation and one execution attempt of it | Assigned by the server |

**Retry versus a new operation**: retrying the same operation reuses `commandId`. A new operation formed after observing a new version gets a new `commandId`, and keeps its source relationship to the old operation.

### 2.4 Idempotency

Runtime maps `commandId` to an `idempotencyKey` within the video.

| Case | Result |
| --- | --- |
| Same video + key + same payload hash | Returns the same receipt; does not execute again |
| Same video + key + different payload | Rejected with `IDEMPOTENCY_CONFLICT` |
| Commit succeeded but the response was lost in transit | Retry with the same `commandId` to fetch the original receipt |

The idempotency record is persisted in the same atomic commit as the transaction.

### 2.5 Query

- A read request either specifies a version or takes `latest`. The response must carry the version actually returned.
- Reads support field selection, time range, object type, pagination cursor and byte budget. The response states the coverage, whether it was truncated, and the cursor for continuing the read. Truncated data must not be treated as the complete video.
- A long-running task does not read "the current video". It first obtains a frozen `snapshotRef` and works from that.

## 3. Transactions and Strict Version Checking

### 3.1 VideoTransaction

Runtime builds the transaction after authorization and hands it to VideoEngine. This is an internal DTO; public clients cannot submit it.

```ts
interface VideoTransaction {
  id: Id;
  videoId: Id;
  baseVideoRevision: Revision;
  idempotencyKey: string;
  actor: { kind: 'user' | 'agent' | 'system'; id: Id };
  readSet: Array<{ entityId: Id; revision: Revision }>;
  label?: string;                    // human-readable edit name; if omitted, the engine names it (see below)
  labelRef?: MessageRef;             // reference of label in the copy catalog; used only together with a non-empty label
  operations: EditOperation[];
  provenance?: { sessionId?: Id; turnId?: Id; jobIds?: Id[]; proposalId?: Id };
}
```

**Edit name** is the human-readable name shown in history, undo hints and change cards. Each receipt (§5), video event (§10.1), and each entry in history and the undo stack carries a `label` and an optional `labelRef`:

- A `label` supplied by the caller (trimmed of leading and trailing whitespace, up to 200 characters) is stored as given. If it comes from the copy catalog, `labelRef` is supplied with it (for example the editor's `editLabel.*`). The engine does not interpret the key; it stores it as is, and readers regenerate the text in their own language. If the key is not recognized, `label` is shown as is (in the caller's language at the time). Names without a `labelRef` (names written by agents, or from third parties) are shown as is and not translated. `labelRef` counts toward the idempotency payload (§2.4). If only `labelRef` is given without `label`, it is ignored and the engine names the edit as usual.
- If omitted or empty, the engine names the edit from its operations: `label` is the English default text, and `labelRef` is its message reference (keys under `engine.label*`, end of §11.1). The UI regenerates it in its own language with `localizeText(label, labelRef)`. Results of agent tools (CLI derived commands also go through them) are expanded in Runtime's language and carry no `labelRef`. When a transaction contains several kinds of change, the name is the main change name plus the number of changes (`engine.labelMoreChanges`, with the main change name as a nested argument). "Import and add" counts as one add.
- Undo and redo names put the forward edit name into `engine.labelUndo` / `engine.labelRedo` as a nested argument. Names that have a reference (engine-named, or with a `labelRef` supplied by the caller) are expanded in the reader's language. Names without a reference are shown as is, as a string argument. A step on the undo stack uses the forward edit name.
- Transactions committed before `labelRef` existed only have the text written at the time, and it is shown as is. When such transactions are undone or redone, the prefix is still shown in the reader's language, and the old text is passed in unchanged as a string argument. The reference is an optional field and does not change the video format version (Video Format Specification §1.4).

### 3.2 Strict Optimistic Concurrency

**P0 uses strict optimistic concurrency control on the video revision: on a mismatch, return a conflict; do not replay automatically.**

- When `expectedRevision` differs from the video's current revision, return `PROJECT_REVISION_CONFLICT`.
- The caller re-reads the affected objects, forms the operations again, and submits with a new `commandId`.
- `readSet` is kept from the first version. It records which version of which entities this operation relied on.
- **P1** is when automatic rebasing is opened up, for tested, mutually unrelated objects or fields.

Two commands must not be treated as independent just because they modify different fields. Changing the duration of source material affects subtitles, transitions and voiceover. The engine judges such dependencies; the caller does not declare that its commands are "unrelated".

### 3.3 Atomicity

The following contents of one transaction are committed atomically: either all of them hold, or none of them do:

- the results of domain validation;
- entity changes;
- the increments of the video revision and of the revisions of affected entities;
- the transaction log and the idempotency record;
- the pending events (outbox);
- the quantized results of time inputs (§6).

A transaction never persists partially. If any operation in a batch fails, the whole batch is rejected.

### 3.4 Validation Happens in the Engine

Version, locks, protected scope, domain rules and resource availability are all checked at the engine's serial commit entry. Runtime does not do a two-step flow of "check the version, then write blindly later". There is no gap between the check and the write.

Transaction commit also checks:

- Whether the task's execution generation is still valid (stop barrier, Architecture Design §7.4). Task and fixed-pipeline commits carry `run { runId, runGeneration }` on the Engine Host's private channel. On cancel, Runtime first sends `runs.invalidate { videoId, runId, runGeneration }`. A commit that arrives after invalidation and has no receipt yet is rejected with `TASK_STOPPED` and does not open a transaction. Ordinary user and agent edits do not carry `run`. Public requests must not carry `run`;
- Whether authorization still holds;
- Whether the operation's target falls within the scope of the task contract, and whether it touches protected scope or locked tracks. Writes inside a task carry `taskId` and `protections` (this video's protections in the task contract: `protectionId` and `target`) on the Engine Host's private channel. This covers agent commits and undos, and Job and pipeline application results under a task (actors `system:jobs` and `system:pipeline`, Architecture Design §3.2). The engine checks these against the transaction's entity changes. If they are touched, the whole transaction is rejected with `TASK_PROTECTED` (§11.2). User and manual edits, writes outside any task, and `jobs.reconcile apply` do not carry them. Public method parameters have no `protections`. The Engine Host checks only non-user commits that carry `taskId`; other commits that carry it have no effect.

Approving an edit does not mean the conflict check can be skipped. All low-risk automatic applications also go through the same validation.

### 3.5 No Arbitrary Patches

- The caller submits validated `EditOperation`s, not arbitrary JSON Patch paths into the database.
- A Patch may be used as a display format in a receipt, but it is not an input format.
- Whole-snapshot replacement is limited to import, restore or explicit administrative operations, and it must pass strict version checking. Ordinary UI operations and agents cannot submit a whole snapshot.

### 3.6 Long tasks do not hold the video

Long model computations and network waits are not inside a transaction, and they do not lock the video. When computation completes, the result is published as an artifact, then applied to the video through a separate, idempotent transaction. At apply time the input versions and the target are checked again (architecture design §7.3).

## 4. Command surface

### 4.1 Methods

The following are representative methods of each namespace.

The addressing of `media.resolve` is `MediaTarget`: `{ entryId }`, `{ conversationId, path }`, `{ projectId, path }`, asset `{ videoId, assetId, revision? }`, attachment `{ conversationId, attachmentId }`, and local file `{ localPath }`, which is sent only to the desktop client (an absolute path, checked with the file's own directory as the root, and only regular files are returned; other clients get `forbidden`, architecture design §4.5). Mixing fields is rejected with `invalid-request`. The media channel's `media.playback { url, playable? }` requests a playback address for a file handle already issued on the current channel (architecture design §4.5). It accepts only `url` and an optional `playable` (WebM codecs the client can decode natively: `vp8`, `vp9`, `av1`, `opus`, `vorbis`); unknown fields are rejected. A forged, expired or mismatched handle, or a source file that has been lost, returns `not-found`. If the file is not WebM, or the codecs of its first video frame and its audio are all in `playable`, it returns `{ status: 'ready', media: original handle }` directly. Otherwise it prepares a compatible copy, returning `{ status: 'pending', retryAfterMs: 250, progress? }` while not ready (`progress` is the 0–1 encoding progress, omitted when unknown), and `{ status: 'ready', media: MediaHandle }` when ready. Failures are returned through the existing RPC error envelope; missing FFmpeg, timeouts and decode failures follow the media analysis errors. The derived cache does not enter document history or the user task table. Downloading the source file continues through `media.resolve` and the original handle's `?download=1`. This method is in the Web read-only allowlist; the cached handle is still bound by the Web session and media permissions. It has no separate CLI or MCP entry.

Records carry `applications` (`ApplicationRecord[]`, one entry each time a result is written into the video: `state` is `pending`, `validating`, `committed`, `stale-input`, `rejected` or `cancelled`, with `commandId`, `baseVideoRevision`, `receipt { transactionId, videoRevision, refs, recovered? }` and `error`), and the three facts of cancellation `cancellation { requestedAt, localStoppedAt, remote, cost }` (architecture design §7.1–§7.4). `state` has one more value, `needs-reconciliation`: a call handed to an online or agent Provider whose result is unknown because the Runtime stopped or crashed is no longer executed. `reconcile { jobId, decision }` (`retry`, `discard`, `apply`) returns the record after handling; the legal states are in architecture design §7.5. When a decision is not legal, the result is `conflict` (`details.code: RECONCILE_NOT_ALLOWED`, with `state`, `decision`, `allowed`). `retry` and `apply` require the video to be open (`not-found`, `VIDEO_NOT_OPEN`). `apply` returns `busy` (`RECEIPT_UNKNOWN`) when the previous receipt cannot be looked up. Agents and the MCP service have no matching tool. The Web service exposes it, and refuses it when read-only (`WEB_READ_ONLY`). CLI: `cuccut jobs reconcile <jobId> retry|discard|apply`. Queued tasks (and the steps of a fixed pipeline waiting for admission, plus their parent tasks) carry `wait { reason, dimensions?, ahead?, detail, since }`: `reason` is `concurrency` (the queue's concurrency is full) or `resources` (peak demand does not fit; `dimensions` lists the missing dimensions: `memory`, `gpuMemory`, `cpuThreads`, `scratchDisk`). It is removed when execution starts or ends (architecture design §7.6, §7.7). `resources {}` is read-only and returns `ResourcesSnapshot`: `capacity` (bytes or thread counts for the four dimensions, `null` when unknown; `unifiedMemory`; the source of each dimension: `system`, `setting`, `unified-estimate`, `statfs` or `unknown`), `reserves { system, interactive }`, `leased`, `available { interactive, background }`, `leases`, `holders` (shared processes, with `users` and `processes`) and `waiting`. The Web service exposes it. CLI: `cuccut jobs resources`. |
| `pipelines` | `list` `start` `retry` | Fixed pipelines (architecture design §7.9). The executing principal is `system:pipeline`, and no agent session is created. `list` returns `{ pipelines }`, where each item gives the name, the human-readable name, the description, the steps (`name`, `label`, `optional`) and the JSON Schema of the parameters. When `transcribe` and `translate` create a caption layer they may take `params.captionStyle` (the `schema` and the `style` object of the Studio style document in video format spec §5.6). It applies only when newly created; existing shared styles are kept, and the parameters are frozen at submission. It may not be given when captions are turned off or when only a file is transcribed. `start { pipeline, params, commandId? }` validates and freezes the parameters, checks the preconditions, and returns the parent Job's `{ jobId }`; the same `commandId` returns the same Job. Space entries work as file inputs (architecture design §7.9): `transcribe`'s `file`, `transcode`'s `inputs[]` and `translate-subtitles`'s `input` may be `{ entryId }`. At submission `pipelines.start` replaces it with the entry's file from the Space directory (a file in the source directory, or a result in an output or save location), so the frozen `params` contain only paths. Media inputs accept video files, finished cuts and audio entries; subtitle inputs accept subtitle entries. An entry that does not exist gives `not-found`; one in the trash gives `conflict` (`SPACE_ENTRY_TRASHED`); the wrong kind (including video entries) gives `invalid-request` (`SPACE_ENTRY_UNSUPPORTED`); no readable file (placeholder, missing) gives `conflict` (`SPACE_ENTRY_NO_FILE`). None of these creates a Job. A `{ entryId }` passed to a pipeline directly, not through `pipelines.start`, is refused with `invalid-request`. An unknown pipeline is `not-found`; invalid parameters are `invalid-request`; unmet preconditions are refused at submission without creating a Job: no text model configured is `CAPABILITY_NOT_CONFIGURED`, and ffmpeg unavailable is `MEDIA_TOOL_UNAVAILABLE` (both in `RpcError.details.code`, with `RpcError.code` set to `conflict`). `retry { jobId }` lets a pipeline that failed, was cancelled or was interrupted continue from the step where it stopped, and returns the same `{ jobId }`. Other states are refused with `JOB_NOT_RETRYABLE` (`conflict`). The video for the video tools (`translate`, `dub`, `link-import`, `transcribe`) is given by `target` (`PipelineVideoTarget`): `{ videoId }` (an open video), `{ entryId }` (a video entry in the Space; it need not be open), or `{ create: { projectId, name?, media? } }` / `{ create: { conversationId, name?, media? } }` (a new video). Exactly one of `projectId` and `conversationId` is given: the new video goes in the project, or in the session's source directory. When the session belongs to a project, that project is used; otherwise it is the session's working directory, registered at session scope. A session that does not exist gives `not-found`. Only `link-import` and `transcribe` accept `create`: `link-import` does not take `media`, and `transcribe` must be given `media` (an absolute path to a local media file). `translate` and `dub` are refused with `invalid-request` (`PIPELINE_TARGET_UNSUPPORTED`). The top-level `videoId` remains valid and is equivalent to `target: { videoId }`. Giving both where they point to different videos, or giving `create` together with `videoId`, is `invalid-request`. `entryId` is resolved at submission, and the video is opened under a Runtime lease (the same path as restart recovery; if another connection already has it open, it attaches to that one). The lease is held until the pipeline completes, fails or is cancelled. After that, with no other opener, it closes after a grace period. An entry that does not exist is `not-found`, not a video-level `invalid-request` (`SPACE_ENTRY_NOT_VIDEO`); one in the trash is `conflict` (`SPACE_ENTRY_TRASHED`); one locked by another process is `conflict` (`VIDEO_LOCKED`). None of these creates a Job or leaves anything behind. The first step of these pipelines is `target` (resolve the target): with `entryId` it is recorded as completed and produces `{ entryId, videoId, place }`; other targets are recorded as `skipped`. `retry` first reopens the video the pipeline holds at its recorded place (when locked it is likewise refused with `VIDEO_LOCKED`; when the place no longer holds the same video, `conflict` (`STALE_JOB_INPUT`)), then continues from the step where it stopped. The parent Job record is `kind: 'pipeline'`, carrying `pipeline`: `name`, the frozen `params`, `steps` (for each step its `name`, `label`, `status` (`pending`, `running`, `completed`, `skipped`, `failed`, `cancelled`, `interrupted`), the `jobId` of its latest child Job, the number of runs `attempts`, and its output `output`), the index of the running step `current`, the step where it stopped `stoppedAt`, and the `summary` on completion. The progress unit is `steps`; `calls` is the model call count of the running step (`calls`, `retries`, `failures`). A child Job is `kind: 'pipeline-step'`, carrying `parentJobId` and `step` (`pipeline`, `name`, `label`, `index`), with `submitter` `{ kind: 'pipeline', id: <parent Job> }`; the per-sentence step progress unit is `units`. On failure the parent Job's `error.details.step` is the failed step. First batch of pipelines: `transcode` (`inputs` are absolute paths; `action` is `compress`, `merge` or `extract-audio`. `extract-audio` extracts each track in turn: AAC, MP3, Opus and FLAC streams are copied into `.m4a`, `.mp3`, `.ogg` or `.flac`, and others are re-encoded as AAC `.m4a`. An input without an audio track fails with `TRANSCODE_NO_AUDIO`, and the output's `media` is `audio`), optional `codec` (`h264`, `hevc`), `maxHeight`, `crf` or `videoBitrateKbps`, `audioBitrateKbps`, and `outDir`. When `outDir` is not given it is the Runtime's save location: `downloads.directory` if set, otherwise the host's Downloads folder, frozen into `params.outDir` at submission. It is created if it does not exist. When it cannot be written, the submission is refused with `conflict` (`OUTPUT_DESTINATION_UNAVAILABLE`) and no Job is created; if the directory is moved or its permissions change before publishing, that step fails with the same error code. `summary` is `action`, `mode` (`stream-copy`, `re-encode`), `reason`, `executor { tool, version, commands }` and `files`. Each item in `result.outputs` carries the output file's absolute `path`; `providerId` is `ffmpeg` and `modelId` is its version), and `translate` (`videoId` or `target`, `targetLanguage`, optional `documentId`, `style`, `glossary` (an array of `{ source, target, note? }`), `glossaries` (translation glossaries from the library, `{ id, version? }`, up to 20), `provider`, `model`, `batchSize` (accepted but no longer used: paging belongs to the subtitle and translation core), `captions` (default `false`), and `bilingual` (default `false`; it may only be given with `captions: true`, otherwise `invalid-request`). `summary` is the new document's `documentId`, the source document and version `source`, `targetLanguage`, `unitCount`, `providerId` and `modelId`. When a glossary was used it also carries `glossary` (`TranslateGlossaryUse`: `entries[] { id, version, contentHash, name, origin }`, where `origin` is `explicit` or `video`; `skipped[] { id, reason }` for glossaries enabled on the video but not used, where `reason` is `removed` or `language`; `terms`, the count after de-duplication; and `cappedBatches`, carried over, which is always 0 because terms are no longer truncated per batch). It also carries the caption layer `captions` (`PipelineCaptionsSummary`, see below; records from before this step existed do not have it). `result.documentId` is the new document). To refresh an existing translation in place, give `translationId` (that `translation` document; `targetLanguage` must match its language, and when `documentId` is given it must be the transcription it was translated from), and optionally `sentences` (IDs of the sentences to retranslate, 1–500; it may only be given together with `translationId`). It cannot be combined with `captions`, `captionStyle` or `bilingual`; each is `invalid-request`. When `sentences` is not given, the refresh retranslates sentences marked stale, sentences whose source was edited, and sentences with no translation yet, and it drops units whose source sentence no longer exists. When there is nothing to do, or a named sentence is not in the transcription, the result is `invalid-request` and no Job is created. The write is a single transaction covering the new version of the same translation and the subtitle document generated from it (only the cues for these sentences are replaced). `summary.documentId` is this translation, and it also carries `refresh { revision, sentences, removedUnitIds, captionDocumentIds, transactionId? }`, with no `captions`. If the transcription or this translation changes during execution, the write fails with `STALE_JOB_INPUT` (architecture design §7.9). Each run of `translate` adds a new `translation` document; it does not replace an existing one. The step `captions`, after `write`, builds a caption layer in the target language when `captions: true`. When `captions` is not given or is `false`, it is `skipped`, the same as when the step is absent. Pipeline parameters do not create one by default. The tool entry point (the video input of `translate-subtitles` in the tool catalogue carries it in `execution.params`), the CLI and the editor's “Translate to…” (together with `bilingual`) pass `captions: true`. One transaction writes one `caption` document (`extensions.pipeline` records this run) and places a caption instance on the root sequence. When only the translation is viewed, the paired original-language caption layer is disabled, not deleted. With `bilingual`, the two layers share one caption style, and the original is placed back on screen. When the same translation already has a caption layer, it is `skipped`. For pipeline records from before this step was added, the new step is run as `pending` on retry and decided by the frozen parameters; the old parameters have no `captions`, so it is skipped. `PipelineCaptionsSummary` has `status` (`created`; `existing`, already there, with `documentId` pointing to the existing one; `disabled`; `not-on-timeline`, meaning no clip on the timeline uses this asset, warning `CAPTIONS_NOT_ON_TIMELINE`; `empty`, meaning no cues could be cut, warning `CAPTIONS_EMPTY`), `documentId`, `cueCount`, `enabled` (whether the newly created layer is shown), `bilingual` of the translation, and `transactionId` (the transaction that created the caption layer when `created`; undo it with `videos.undo`). Terms come, in order, from `glossary`, `glossaries`, and the translation glossaries enabled in the video. Library glossaries have their versions frozen at start and pinned until the pipeline ends (the parent Job's `library.entries`). The translation's `glossaryRef` records the versions used and the terms that appeared (video format spec §5.3, architecture design §7.9). A glossary in `glossaries` that is not in the library is `not-found`. A glossary used for transcription with a mismatched language, or a duplicate, is `invalid-request` (`LIBRARY_ENTRY_NOT_APPLICABLE`). None of these creates a Job. The third pipeline is `link-import` (architecture design §7.9): `url`, optional `projectId`, `conversationId`, `videoId` or `target`, `audioOnly`, `subtitleLanguages` (language codes, up to 10), `transcribe` (transcribes directly to TXT/SRT), and `cookieBrowser`. The transcription's `language`, `provider`, `model` and `hint` are given only together with `transcribe`. `diarize` and `captions` (default `false`; builds a caption layer after transcription) also require a video target, otherwise `invalid-request`. Their meaning is the same as the same-named parameters of the `transcribe` pipeline. The Provider and model are frozen at submission, and the transcription glossary enabled on the video is applied when the transcription is imported into the video. With no video target, the file is downloaded and optionally transcribed. With `target.create`, an editable video is created in the project `create.projectId` or in the source directory of the session `create.conversationId`; the download location is independent. A top-level `projectId` or `conversationId` given at the same time must match it, otherwise `invalid-request`. `transcribe` may give only `create`. A non-compliant link is refused at submission with `invalid-request` (`LINK_UNSUPPORTED`, `LINK_PRIVATE_ADDRESS`). If yt-dlp is not installed, is too old, cannot run, or consent was not given, it is refused with `conflict` (`TOOL_*`). Strict offline mode is refused with `conflict` (`OFFLINE_STRICT`). The frozen `params.url` is a redacted link; the original link is referenced only by `params.sourceRef`. The steps are `target`, `resolve`, `download` (progress unit `bytes`), `verify`, `publish`, `create` (with `target.create`: a new video is created in the project or the session's source directory on the same path as `videos.create`; the name defaults to the page title; the Job holds its lease. After completion, a retry does not create it again, and the video is kept if a later step fails), `import` (with a video target: the newly created video places the material on the main track in the same transaction, starting at 0 and covering the whole media), `transcribe` (when `transcribe` is set), and `captions` (when `captions` is set; same step as in the `transcribe` pipeline; skipped when the material is not placed on the timeline or a caption layer for the same transcript already exists). `summary` is `url`, `title`, `platform`, `uploader`, `durationSec`, `description` (the page description, truncated to 1200 characters with “…” appended when truncated; `null` when absent; the complete text, up to 20000 characters, is recorded in the asset's `source.description`, video format spec §4.5), `sourceChapters` (the number of structured chapters the platform provides, 0 when none; timestamp outlines in the description do not count; earlier versions do not have these two fields), `files { media, subtitles }`, `tool { name, version, source }`, `downloadedAt`, `videoId` (the new video when one is created), `assetId`, `createdVideo` (`true` when a video was created), `transcribeJobId`, `transcriptFiles` (when transcribed separately), `documentId` (the speech document written when imported into a video), and `captions` (when `captions` is set; same as `summary.captions` of the `transcribe` pipeline). `result.outputs` carries the downloaded media file and optional TXT/SRT. The media's `artifactId` is the content digest of that file in the download directory (it is not entered into the artifact library). Only after downloading can an agent import it through `importAsset` of `edits_apply` (if the file is missing or has changed, `ARTIFACT_NOT_FOUND`). A new video's `origin` in the Space is this run (`source: 'imported'`, `jobId`, `capability: 'link-import'`; when submitted by an agent, it also carries the session and task). The fourth pipeline is `dub` (dubbing with translation, architecture design §7.9). Parameters (`DubParams`): `videoId` (or `target`, as above); at least one of `targetLanguage` and `translationId`; optional `documentId`, `voice`, `provider`, `model`. When the translation is missing, the translation parameters `textProvider`, `textModel`, `style`, `glossary`, `glossaries` and `batchSize` apply; given with `translationId`, they are refused with `invalid-request`. Also `originalAudio` (`duck`, `mute`, `keep`; default `duck`), `duckDb` (1–60, default 18), and `separateBackground` (when `keep`, no separation; frozen as `false`). After successful separation, `apply` mutes the original sentence instances that are speaking on the transcription's source (recorded in the dub plan's `mutedItemIds`). It places the separated background sound at the same positions on a new track, “Background (<language>)”, without ducking. `duck` also creates a track “Voice (<language>)” for the voice, and ducking targets this track (video format spec §7.2). Refusals at submission: `library:<id>` without a valid clone gives `VOICE_CLONE_REQUIRED`; outbound data (synthesis, and translation when the translation is missing; data kind `transcript`) without coverage gives `forbidden` (`GRANT_REQUIRED` etc.). The default grant for the speech synthesis Provider, when enabled, does not include `transcript`. When dubbing is refused for this reason, the `hint` in `details.remedy` explains it and says to re-run after granting, and `commands` lists the command to run: `cuccut grants create --recipient <Provider> --data transcript --video <videoId> --purpose "<purpose>"`. When several outbound uses lack grants, all are listed in one refusal; the desktop interface's refusal additionally carries the pending approvals (`pendingGrants`, §11.3). Voice: a voice bound to this transcript's speaker in the video (`speakerVoices` of `library.setVideoSelection`) takes priority, then `voice`, and finally the model's default voice. A bound voice is checked at the `synthesize` step. When it is unavailable (`VOICE_CLONE_REQUIRED`, `VOICE_CONSENT_REQUIRED`, `VOICE_NOT_FOUND`), that speaker's sentences are not synthesised and are reported one by one, with warning `DUB_VOICE_UNAVAILABLE`; they are not swapped for another voice. When no sentence can be synthesised at all, this step fails with that error code. The steps are `freeze-source`, `translate`, `assemble` and `write` (these four run only when the translation is missing), then `check-translation`, `separate` (runs only when separation is requested, the original is not `keep`, and a separation model bundle can be chosen; otherwise `skipped`. `separatorModel` is frozen at submission; if it is unavailable at execution, the error is `CAPABILITY_NOT_CONFIGURED`), `synthesize` (one child Job per sentence; progress unit `units`), `align`, and `apply`. `summary` (`DubSummary`) includes `videoId`, `language`, `translation { documentId, revision, created }`, `planDocumentId`, `trackId`, `groupId`, `units { total, placed, stale, offTimeline, tempo, extended, overlong, voiceUnavailable }`, `staleUnits`, `overlongUnits[] { unitId, overflowSeconds }`, `voiceUnavailableUnits[] { unitId, speakerId, voice, code, reason }`, `speakers[] { speakerId, voice, voiceSource, available, units }` (`voiceSource`: `video`, `params` or `default`), the glossary used for translation when the translation was missing (`glossary`, same as `translate`), `synthesis { providerId, modelId, voice, calls, retries, failures, reused }`, `originalAudio`, and `separation` (`completed`, `not-requested`, `not-configured`). `result.documentId` is the dub plan. Regrouping sentences: the `dub` parameter `regroup { groupId, units, seed? }` (`DubRegroup`) re-synthesises only these sentences of an existing dub group. `units` are translation unit IDs, 1–200, with no duplicates. It writes back to the same group: the same dub track, a new version of the same dub plan. No new group is created, and no other sentences or original-audio handling are changed. When `regroup` is not given, behaviour is unchanged. The translation, language, Provider, model and voice are taken from this group's dub plan (for sentences using a speaker-bound voice in the video, the voice recorded in the plan is used). So giving `translationId`, `targetLanguage`, `documentId`, `voice`, `provider`, `model`, the translation parameters, `originalAudio`, `duckDb` or `separateBackground` together with `regroup` is refused with `invalid-request` (`details.conflicting`). The text is read from the translation's current version, so to “edit the translation and redub”, first write a new version of the translation document, then use `regroup` to redub only these sentences. `seed` is `'new'` (the default; a random value is chosen at submission) or an integer from 0 to 4294967295. When the model does not accept a seed, `'new'` is recorded as `null`, and a number is refused with `invalid-request`. Refusals at submission: when this group has no dub plan, or no instance remains on the timeline, it is `invalid-request` (`DUB_GROUP_NOT_FOUND`); sentences not in the plan or the translation are `invalid-request` (`details.missing`). The grant rules are the same as for `dub` (the only outbound use is synthesis; the desktop interface shows `pendingGrants`). The frozen `pipeline.params.regroup` is `FrozenDubRegroup { groupId, units, planDocumentId, trackId, seed }`, from which the interface knows which sentences are being redubbed. The steps are the same as `dub` (the three translation steps and `separate` skipped). `check-translation` checks only these sentences; the `align` time window is still computed over all sentences. `apply`, in one transaction, imports the new audio, deletes the old instances of these sentences in this group, places the new ones on the original dub track (keeping the old instances' volume and mute, with the rate back to 1), and writes the new version of the dub plan with `putDocument { documentId }` (`summary` is recounted, `groupId` unchanged). Sentences that were synthesised but do not fit keep the old version. Each sentence's versions are recorded at `extensions['cuccut.dub'].takes[]` of the plan unit (`DubPlanTake`: `k`, `seed`, `artifactId`, `assetRef` when known, `samples`, `sampleRate`, `fit`, `tempo`, `overflowSeconds` when it does not fit, `text`, `jobId`, `at`). The current version is `take` (with `seed`) at the same place. For older plans without versions, the version already placed is backfilled as version 1, with its asset recorded. The newly placed version becomes the current one, and the instance's `extensions['cuccut.dub']` also carries `take` and `seed`. Switching versions is done by the client in one undoable edit: delete this sentence's instance, put that version back at the same place using its `assetRef` (the engine does not reclaim assets; when unknown, the asset is looked up by `provenance.source.artifactId`), and write the new version of the plan with `take` changed to that version. On completion, `summary` also carries `regroup { seed, units[] { unitId, status, take, seed } }` (`DubRegroupSummary`, `status`: `replaced`, `overlong`, `stale`, `voice-unavailable`, `off-timeline`); `groupId`, `trackId` and `planDocumentId` are those of the original group, and `units.total` is the number of sentences redubbed. The fifth pipeline is `translate-subtitles` (translation of subtitle files, architecture design §7.9): file to file, without touching a video. Parameters (`TranslateSubtitlesParams`): `input` (an absolute path to a `.srt` or `.vtt` file), `targetLanguage`, and optional `sourceLanguage`, `style`, `glossary`, `glossaries` (as for `translate`; there is no video, so the video's enabled glossaries are not used), `provider`, `model`, `batchSize`, `format` (`srt` or `vtt`; default the same as the input), `bilingual` (default `false`; original on top, translation below), and `outDir` (the default save location, see below; created if missing; when not writable, `conflict` (`OUTPUT_DESTINATION_UNAVAILABLE`), and no Job is created). `videoId` and `target` are not accepted. Input is parsed strictly at submission, and a file that cannot be read accurately creates no Job: a missing file is `not-found`; a malformed file is `invalid-request` (`SUBTITLE_FILE_INVALID`, with `details` carrying `file`, `line`, `problem`); exceeding the limit is `invalid-request` (`SUBTITLE_FILE_TOO_LARGE`). The limits are 4 MiB per file and 10000 cues, with each cue's text at most 1000 characters (exceeding this counts as a malformed file). It tolerates BOM, CRLF, UTF-16 and GBK encodings, the WebVTT header, cue settings, NOTE / STYLE / REGION blocks, multi-line text and style tags. It rejects lines with missing timing, reversed times, out-of-range minutes or seconds, `-->` in the body text, and files with no cue containing text. The outbound data kind is `transcript`, the recipient is the text model's Provider, and there is no video (`videoId: null`). The grant refusals are the same as for `translate` (`remedy`; the desktop interface additionally carries `pendingGrants`). The steps are `read` (reads the subtitles; retried with a fresh read when the source file's size or modification time changed), `translate` (translates in batches; the number of cues and their IDs in each batch must match. When they do not, it resends a bounded number of times, and if still mismatched the result is `MODEL_OUTPUT_INVALID`), `check` (writes the output and reads it back to verify: the cue count and each cue's start and end times are unchanged; for the same format the timing lines are byte-for-byte unchanged; every cue sent for translation has a translation. A mismatch is `MODEL_OUTPUT_INVALID`, with `details.problems`), and `publish`. Each cue only has its text replaced; cues are not merged or split. In the same format, the original sequence numbers, timing lines, cue settings and WebVTT blocks are kept. When the format changes, times are rewritten; cue settings and blocks dropped when converting WebVTT to SRT are reported with warning `SUBTITLE_SETTINGS_DROPPED`. Inline markup (italics, colour, position) is not kept, with warning `SUBTITLE_MARKUP_STRIPPED`. Cues with empty text stay empty and are not sent for translation. The output is UTF-8, LF, with no BOM. It is published as `<original file name without extension>.<target language>[.bilingual].<format>`, and existing files are not overwritten (a numeric suffix such as `-2` is added on a name clash). `summary` (`TranslateSubtitlesSummary`) is `source { path, format, contentHash }`, `file`, `format`, `bilingual`, `targetLanguage`, `sourceLanguage`, `cueCount`, `translatedCount`, `markupStripped`, `droppedSettings`, `droppedBlocks`, `providerId`, `modelId`, and the `glossary` used. `result.outputs` is the published subtitle file (`media.kind: 'text'`, with `entries` as the cue count). In the Space it is an entry whose origin is generated (`capability: 'translate-subtitles'`). The sixth pipeline is `transcribe` (transcription, architecture design §7.9). It shares its name with the transcription Job submitted by `models.transcribe`, but it is a different thing: it is a parent Job, and its “transcribe” step submits a `transcribe` Job whose `submitter` is this pipeline. Parameters (`TranscribeParams`): `videoId` or `target` (`{ videoId }`, `{ entryId }`, `{ create: { projectId, name?, media } }`); optional `assetId`, `language` (asserted language), `hint` (recognition hint, up to 1200 characters; the video's enabled transcription glossary is still merged in), `provider`, `model`, `diarize` (speaker diarization, same as `models.transcribe`; when not given, it follows the model), and `captions` (default `true`). Also, `destination` (`'new-video' | 'replace'`, default `'new-video'`; tools and the CLI call it `target`) takes effect only with `{ videoId }` or an `{ entryId }` target, and only when the target video already has a `speech` document. Only yt-dlp can be downloaded; ffmpeg only reports status (the audio.cpp engine for music generation is not here: it is a component of the music model package and is downloaded with that package, see architecture design §6.3). `list` and `detect { name? }` return `{ tools }` (`ExternalToolStatus`: `name`, `label`, `purpose`, `state` (`installed`, `missing`, `outdated`, `unavailable`), `reason`, `path`, `version`, `source` (`env`, `bundled` (the copy shipped with the app; a reserved value that no tool uses yet), `user`, `managed`, `system`), `minVersion`, `installable`, `offer` (`version`, `fileName`, `url`, `sizeBytes`, `estimatedBytes`, `sha256`, `license`, `homepage`, `blockedReason`), `consentRequired`, `consent` (`state`: `granted` or `revoked`, `at`, `via`: `app`, `cli`, `agent-approval`), `managed`, `userPath`, `installJobId`, `update`, `updateJobId`, `platform` (the platform of the host where the Runtime runs, such as `darwin`, `win32`, `linux`; when the UI cannot tell how to install, it uses this to list common commands), `remedy`). Detection only runs `--version` on the local machine, and it determines how the system copy was installed from the real location of the executable. `update` is `{ method (homebrew, pipx, pip, standalone; on Windows also winget, scoop, chocolatey), argv, command, runnable, reason }`. `command` is the full command for people to read and paste into a terminal (written for the platform of the Runtime host: on Windows it follows PowerShell quoting rules, with `&` in front when the first word is quoted; other systems follow POSIX shell). When `runnable: false`, `reason` explains why it cannot be run on the user's behalf (it needs administrator rights, which Chocolatey installs always do; the same Homebrew, pipx, winget, or Scoop cannot be found; the interpreter is gone). For the copy CucCut downloaded, and when the installation method cannot be determined, it is `null`. `install { name, consent?, via?, commandId? }` without `consent: true` rejects with `TOOL_CONSENT_REQUIRED` (`details.offer`). With it, the consent is recorded and a `kind: 'toolInstall'` job is submitted, returning `{ tool, jobId }`, with progress in `bytes`. If the same tool is already being installed, it returns that job. `update { name, command?, commandId? }` runs the update command on the user's behalf according to `update`. If `command` is not given, or differs from the current `update.command`, it rejects with `TOOL_UPDATE_CONFIRM_REQUIRED` and hands back `details.update`. Only when the same command the user confirmed is handed back is a `kind: 'toolUpdate'` job submitted, returning `{ tool, jobId }`. If the same tool is already being updated, it returns that job. The command runs without a shell and without elevated privileges. The phases are `downloading` (execution) and `validating` (re-detection). The output is written to `JobRecord.command` (`line`, `output` (the last ~32 KB, with terminal colors removed; lines rewritten with `\r` keep only the last write), `lines`, `truncated`, `exitCode`), updated about every 250 ms while running. When it ends, the tool is re-detected whatever the result. Exit code 0 means completed (winget exiting with 0x8A15002B, when there is no version to upgrade, also counts as completed). Otherwise the job fails with `TOOL_UPDATE_FAILED` (`details.exitCode`, `details.remedy`). Both completion and failure leave a `cuccut.tool-update/1` record in `result.artifactId` (the command, the versions before and after, the full output). `setPath { name, path }` (`null` clears it) first runs `--version` to verify, and returns `{ tool }`. `remove { name }` deletes only the managed copy. `consent { name, grant, via? }` records or withdraws consent. `cookieBrowsers {}` returns `{ platform, browsers }`. `platform` is the platform of the host where the Runtime runs (`darwin`, `win32`, `linux`, and so on; the UI uses it to prompt for system authorization). `browsers` are the browsers on this machine whose cookie stores can be found (`CookieBrowserInfo`: `id` (a value of `cookieBrowsers`), `label`, `lastUsedAt` (the most recent modification time of the cookie store; null when permission to look is not granted)), most recently used first. Each call re-checks; it only looks at whether files exist and their modification times. It does not read cookies and does not run the download tool (architecture design §7.9). These eight methods are not on the Web service allowlist; browser sessions and external-service calls are rejected with `forbidden`. The MCP external service does not offer them |

The download-video UI uses `link-import` and does not send `target`. `transcribe: true` transcribes the file directly when there is no video target; `summary.transcriptFiles` returns the TXT/SRT paths. Media and transcription results are all written to `downloads.directory`, which is frozen at submission time (by default the downloads folder of the host; see architecture design §7.9). The optional `projectId` only associates the transcription artifacts and does not change file paths. When `saveTo` (`downloads` or `project`, default `downloads`) is `project`, the save directory becomes the `downloads/` folder of the owning project (the project of `projectId` or `videoId`, or the project of `target.create`). If the owner is a session that does not belong to a project, it is still the downloads directory. The UI and CLI do not send it. (The agent's `download` sends it only when only `project` is given; the external service's `download` sends it whenever there is a destination.) `cookieBrowsers` is a list of browsers in attempt order, without duplicates. Each entry accepts only chrome, edge, firefox, safari, brave, chromium, opera, vivaldi, or whale. When not given or empty, no browser cookies are read. When resolving a link, the entries are tried one at a time in order: move to the next one when the cookies cannot be read or the site requires login, and do not move on for other failures. If none succeeds, it fails with `LINK_LOGIN_REQUIRED` (when one of them required login) or `LINK_COOKIES_UNAVAILABLE`, and `error.details.attempts` is a `{ browser, code, message }` for each browser. The browser that was used is in `summary.cookieBrowser` (null when anonymous), and the download keeps using it. The old form `cookieBrowser` (one browser) is still accepted and is equivalent to a `cookieBrowsers` list containing only it; the two cannot be given together. The download-video UI lists only the browsers detected by `externalTools.cookieBrowsers`.


Rules:

- Model methods return a `jobId` immediately. Querying the status does not trigger a new computation.
- Candidates, receipts, and check reports are all returned with stable IDs.
- To change the output frame rate, use the `ExportSettings` of `exports.create` (the `fps` of the `video` kind of export); to change the edit frame rate, use the `changeSequenceFrameRate` operation. The two do not share one ambiguous fps update interface.

### 4.2 Edit operations

The payload of `edits.apply` is a set of `EditOperation`s:

```ts
// Added by this spec: operations are distinguished by type, and each type has its own schema
type EditOperation = { type: string; [field: string]: JsonValue };
```

Operations are grouped by domain:

| Domain | Representative operations | Receipt must state |
| --- | --- | --- |
| Assets | `importAsset` `collectAssets` `removeAssets` `relinkAsset` `replaceAssetVersion` | Version, affected instances, missing assets, deleted asset records |
| Items | `addItem` `moveItems` `arrangeItem` `trimItem` `splitItem` `joinItems` `deleteItems` `removeRange` `updateItem` `setSpeed` | Old and new times, lineage, linked objects |
| Styles | `setText` `setTransform` `setStyle` `setProps` `setAnimation` `setKeyframes` `setAudioMix` | Result of property validation and scope of change |
| Transitions and effects | `setTransition` `removeTransition` `setEffects` | Transitions deleted along with it and the reason; one-sided transitions that shorten with their instance |
| Chapters and ducking | `setChapters` `upsertChapter` `removeChapter` `setDucking` `removeDucking` | Chapters and rules created or changed |
| Captions | `correctWords` `updateTranslation` `pinCaptionBreak` `setCaptionStyle` | New document version, invalidated dependencies |
| Speech | `addCuts` `restoreCut` `proposeCuts` `acceptCutSuggestions` | Safe cut points, mapping and review record; instances deleted with cuts, cuts that cannot be restored |
| Code | `publishBundle` `setCodeParameters` `replaceCodeBundle` `bakeCodeItem` | Code bundle version, compatibility and cache impact |
| Dubbing | `setDubbingScript` `attachVoiceResult` `chooseLanguageVariant` | Real duration, alignment, pending units |
| Versions | `forkSequence` `applyLocalizationOverride` | Source relationship, conflicts |
| Tracks and sequences | `addTrack` `deleteTrack` `updateTrack` `moveTrack` `updateSequence` `changeSequenceFrameRate` `setTemplate` | Quantization deviation, affected scope, rejection reason (video format spec §2.12), deleted tracks |
| Protection | `setProtection` `clearProtection` `createCheckpoint` | Scope of protection and checkpoint version |

The agent's `edits_ops` returns a catalog grouped by the operations that are open. The `family` of each group and operation entry uses stable English identifiers: `assets`, `items`, `styles`, `transitions-and-effects`, `chapters-and-ducking`, `speech`, `code`, `tracks-and-sequences`, `documents-and-versions`. These values are for programmatic reference and are kept separate from the human-readable domain names and operation descriptions.

Each operation must:

- Identify its target with a stable ID. Do not use references that depend on UI state, such as “the current segment”.
- Declare the set of affected tracks, and how a locked track is handled (reject or skip).
- When time is involved, use the time input types in §6, or semantic anchors on words, sentences or occurrences.
- When code synthesis is involved, distinguish three layers: instance, parameters and source (code bundle spec §3.4).

The fields of picture instances, and the semantics of transitions, effects, chapters and ducking, are in video format spec §3.5–§3.9, §3.13, §3.15 and §3.17. The engine validates field values and their applicable scope against the element model (`crates/timeline`). Conventions for the operations:

- `setTransform` changes the `place` of a picture instance: `x`, `y`, `w`, `scale`, `scaleY` and `rot` change only the ones given; `null` removes them (back to the per-kind default). `flipX` and `flipY` are booleans. Captions and audio have no `place`.
- `setStyle` changes only the fields given; `null` removes them. `opacity`, `radius` and `cornerRadii` are written into `place`. `mode`, `fit`, `bg` and `mask` apply to visual media. `tile` applies to images and text. `style`, `stylePresetId` and `verticalAlign` apply to text. `shape` replaces the shape parameters as a whole. `crop` applies to video and images; `null` removes the crop.
- When `trimItem`, `splitItem` or `removeRange` changes the window of an instance, keyframe bindings and volume envelopes are converted per video format spec §3.15 (`rewindow` and `split_keyframes` in `timeline::keyframes`). `localFrame` is converted by the displacement of the content; frames outside the window are removed and a sampled value is added at the new boundary; `percent` is kept as is. On a split, the left half keeps the original binding IDs, and the right half's bindings are new. A static instance that is only shortened by `removeRange` is converted by the follow-the-cut rule (its start does not move).
- `joinItems` takes `itemIds` (two items, end to start on the same track) and an optional `keep` (`first` or `second`, in the order of `itemIds`). It is the inverse of a split: the same kind; with source clocks, the same rate and exactly continuous source time; all other fields identical (except name, identity and time). Keyframes and volume envelopes can be rejoined into one sequence of frames with `join_keyframes`. When fields differ, `keep` must be given, and the fields of that side are taken (where keyframes cannot be rejoined, that side's keyframes are kept as they are). The earlier item in time is kept (its ID, start, source start and lineage); the later one is deleted and listed in the receipt's `deletedIds`. The later item's exit transition, ducking groups and caption `scopeItemIds` are repointed to the kept item. A transition between the two is deleted together with the later item and listed in `impact.removedTransitions`. If they cannot be joined, the whole request is rejected (`INVALID_OPERATION`), with `details.rule` set to `kind`, `track`, `not-adjacent`, `rate`, `source-gap` or `attributes`; the last one carries the mismatched field names in `keys`.
- `setText` takes `text` or `counter` (only one); the one given replaces the other. `setProps` replaces as a whole the kind parameters of generated elements and shapes (the one named the same as the instance kind). `setAnimation` replaces the three animation slots of an element as a whole; `null` removes them. `setKeyframes` takes `property` and `keyframes` and replaces the keyframes of that property as a whole; `null` or an empty list removes this binding. `setTemplate` replaces the template layer of the sequence as a whole; `null` removes it.
- `setAudioMix` changes the mix of an audio instance, or of the sound track a composition carries: `muted`, `volume` (a linear multiplier, 0–4), `fadeIn` and `fadeOut` (decimal seconds; `"0"` removes).
- `setTransition` takes `sequenceId`, `leftItemId` and `rightItemId` (at least one), `kind` and `params`, and optionally `duration` (a time input per §6; if given, `alignment` must be stated), `easing`, `placement` and `audioCrossfade`. Kinds are `dissolve`, `wipe`, `slide`, `zoom`, `iris`, `dip-to-color` and `push`; the last two apply only to the two-sided case. An existing transition on the same edge is replaced. Two-sided transitions must give `duration`; if the handles are insufficient the request is rejected, and it is not shortened automatically. A one-sided transition without `duration` is 0.5 seconds, and its effective length shortens with the instance (video format spec §3.9). Those that shorten are listed in the receipt's `impact.shortenedTransitions`.
- `setEffects` takes `fx` and replaces the effects of a visual medium or composition instance as a whole (video format spec §3.9); `null` removes them.
- `updateSequence` changes the sequence's `name`, `canvas` (`{ width, height }`, in pixels) and `background` (`#RRGGBB`). When `name` is given, the sequence header drops the default `nameRef` (video format spec §3.2). Positions are stored as percentages of the frame, so instances follow the canvas when its size changes.
- `setChapters` replaces the sequence's chapters as a whole and leaves other markers untouched; `chapterId` reuses existing chapters. `upsertChapter` without `chapterId` creates a chapter and requires `at` and `title`. `summary` and `thumbnail` accept `null` to remove them. When `at` is given, `alignment` must be stated. The thumbnail is `{ assetId }`, or `{ ref }` of an `importAsset` in the same transaction.
- `setDucking` without `ruleId` creates a rule and requires `trigger` and `target`; when `ruleId` is given, only the fields given change. `trigger` is `{ kind: 'speech' }` (when someone is speaking) or `{ kind: 'items', … }` (when these tracks and instances are sounding). `depth` is the attenuation in decibels (0–60). `attack` and `release` are decimal second strings. An instance-triggered `trigger` and `target` may, besides `trackIds` and `itemIds`, use `trackRefs` to reference the `ref` of an `addTrack` in the same transaction.
- `removeRange` takes `sequenceId`, `from`, `to` (time inputs per §6), `trackIds` and `alignment`. On the listed tracks it deletes `[from, to)` and moves later content forward (a ripple delete, video format spec §6.4). Video, audio and composition instances that cover the interval are split and the middle deleted; captions projected through them follow the right-hand segment. Picture, text, shape and caption instances are shortened. Instances lying entirely within the interval are deleted. Unlisted tracks are untouched. If a listed track, or an instance that would be changed, is locked, the whole request is rejected (`TARGET_LOCKED`) rather than skipped. A speech clip accepting suggestions compiles into this operation.
- `addCuts` takes `sequenceId`, `assetId` and `cuts` (`{ from, to, ref? }`: decimal seconds on the asset's clock, with `0 ≤ from < to ≤ asset duration`; `ref` is the ID of the edit suggestion). The asset duration is probed by the engine from the current asset version, and the caller does not pass it. If the asset has no known duration, the request is rejected. It adds cut points to this asset's cut set (video format spec §6.7; if none exists yet, a document of `kind: 'cut-set'` is created). In the same transaction it re-lays out the timeline: on the tracks where cut-set instances sit, it ripple-deletes; other instances move per `followPolicy` (§3.16); chapters move forward with the content (video format spec §6.7). `restoreCut` takes `sequenceId`, `assetId` and `cutId`, removes that cut and restores the material at the seam; chapters after the seam move back. Instances lying wholly within the cut interval are listed in `impact.removedByCuts`, and cuts that cannot be put back are listed in `impact.cutsNotRelaid`. When audio and picture are placed on different tracks with an offset, and one cut maps to partially overlapping intervals, the whole request is rejected (`INVALID_OPERATION`, `details.rule: 'scope-misaligned'`). If a track or an instance that would be changed is locked, the whole request is rejected (`TARGET_LOCKED`). `putDocument` writing a cut set is checked against §6.7 in the same way. `proposeCuts` takes `assetId`, optionally `speechDocumentId` (required when the asset has several transcripts) and `detect` (`pauses`, `fillers`, `minPause`, `compressTo`, `maxGap`, `fillerLanguage`, `customFillers`, `trimChapterStarts`; the seconds are decimal strings). It detects verbal tics and long pauses from the transcript and writes an editing proposal for this asset (video format spec §6.2, `kind: 'editorial-proposal'`; created if absent, the whole document replaced if present), without changing the timeline. `acceptCutSuggestions` takes `sequenceId`, `proposalId` (the ID of the proposal document) and `suggestionIds`. It compiles these suggestions into cuts (as `addCuts`, with `ref` set to the suggestion ID) and marks them `accepted`, in one transaction. An unknown suggestion ID rejects the whole request (`ENTITY_NOT_FOUND`). If the transcript was changed after the proposal was made, the whole request is rejected (`INVALID_OPERATION`, `details.rule: 'proposal-stale'`). To change an interval, use `addCuts` directly and put the suggestion's ID in `ref`.
- At the end of each edit transaction, the end point of `untilSequenceEnd` instances is computed per video format spec §3.16. Instances that change as a result are listed in `updatedIds`. Locks do not block this step, but task protection is still checked as usual.
- `insertItems` takes `assetRef` (a version of an existing asset) or `assetImportRef` (the `ref` of an `importAsset` in the same transaction, which takes that asset's current version) for video, picture, whiteboard and audio instances; give only one of the two. Stickers and placeholder boxes do the same when they reference an asset.

When `storage` is not given to `importAsset`, a file is linked (`linked`; the bytes stay where they are), and a directory (code bundle) is collected into the video (`managed`). Only `storage: 'managed'` copies a file. Assets that are already linked are collected with `collectAssets` (video format spec §4.2). `managed` requires an absolute path; `linked` may take a path relative to the video directory. The engine normalizes link locations: a file inside the project directory is recorded as a path relative to the video directory, and a file outside it as an absolute path. `relinkAsset` does the same (video format spec §4.2). Generated results (`artifactId`) are always `managed`.

`removeAssets` takes `assetIds` and deletes asset records with no references from the video. “Referenced” is checked at commit against the same graph as the references, plus the document sources: any sequence instance's `assetRef`; a composition's pre-rendered stand-in `prerender`; chapter thumbnails; and a document's `sourceAssetId` (the transcript, cut sets, and the recordings that editing proposals describe). If any listed asset still has a reference, the whole request is rejected (`INVALID_OPERATION`, `details.rule: 'asset-in-use'`; `details.usedBy` maps the asset to the IDs of the instances, markers and documents that reference it). An unknown ID is `ENTITY_NOT_FOUND`. A code bundle and the pre-rendered stand-in baked from it are handled as a pair (code bundle spec §3.3). The stand-in's provenance record (`provenance.origin: 'composition-bake'`) has a `sourceBundleRef` whose `bundleId` and `revision` match the current bundle manifest, which makes them a pair. If one of the pair is listed and the other is not referenced, both are deleted together. Deleted assets are listed in the receipt's `impact.removedAssets` and `deletedIds`. Only the records are deleted: `managed` bytes stay in `blobs/`, so content still used by undo history and frozen tasks remains, and undo can restore the records. GC reclaims the bytes later, according to the reference graph and retention policy (architecture design §5.5). `linked` source files are not touched. The engine host's read-only method `videos.unusedAssets { videoId }` returns the assets that have no references right now (`{ unused: UnusedAsset[] }`: `assetId`, `name`, `kind`, `mediaType`, the current version's `byteLength`, `storage`, and the paired `pairedWith`). It is not on the gateway; it serves the `assets_prune` tool.

`deleteTrack` takes `trackId` (`sequenceId` may be omitted; if given, it must match) and deletes an empty track. The `order` of other tracks is not renumbered. This is symmetric with `addTrack`, which takes the maximum plus one and does not touch existing tracks, so tracks created later still sort to the top. If the track still has instances, the request is rejected (`INVALID_OPERATION`, `details.rule: 'track-not-empty'`; `details.itemIds` lists them; `details.next: ['deleteItems', 'moveItem']`; `recovery` is an explanation with the same meaning). Instances may be deleted or moved away first in the same transaction, and then the track is deleted. If a ducking rule's `trigger` or `target` references the track, the request is rejected (`details.rule: 'track-in-ducking'`, `details.next: ['setDucking', 'removeDucking']`). If the track is locked, the result is `TARGET_LOCKED`. Deleted tracks are listed in `impact.removedTracks` and `deletedIds`.

`arrangeItem` takes `itemId` and `direction` (`forward` moves up one layer, `backward` down one layer, `front` to the very front, `back` to the very back; `sequenceId` may be omitted, and if given it must match). It adjusts the stacking order of a picture instance. Stacking order is the vertical order of tracks (video format spec §3.3: picture tracks and caption tracks form one stack; audio tracks form another). The operation does not write `paintOrder`. When the instance shares its track with other instances, it is split onto a newly created adjacent track of the same kind (`forward` above the original track, `backward` below it, `front` above all tracks, `back` below this stack). The other instances stay where they are. The tracks above shift up by one as a whole, and `order` never goes negative. The new track is listed in `createdIds`, and the tracks that moved over are listed in `updatedIds`. When the instance is alone on its track, the whole track moves within this stack (`forward` and `backward` swap with the adjacent track, caption tracks included; `front` and `back` move it to the top or bottom, and the others shift in order). The existing set of `order` values in this stack is reassigned in the new order. Tracks in the other stack are untouched. If an instance alone on its track is already at the front or back, the request is rejected (`INVALID_OPERATION`, `details.rule: 'already-at-edge'`, `details.edge: 'front' | 'back'`). If the instance or its track is locked, the result is `TARGET_LOCKED`. After it is split out, transitions between it and its former neighbours no longer connect. They are deleted by the transition rules in §4.2 and listed in `impact.removedTransitions`.

`moveTrack` takes `trackId`, `target` (the reference track, which must be in the same stack as the track being moved: picture and caption tracks form one stack, audio tracks another) and `position` (`above` places it above the reference, `below` places it below; `sequenceId` may be omitted, and if given it must match). It moves a track next to another track in the same stack. The existing set of `order` values in this stack is reassigned in the new order, and the other stack is untouched. Instances follow their track and do not change track. If the reference is not in the same stack, or is the track itself, the request is rejected (`INVALID_OPERATION`). If the track being moved is locked, the result is `TARGET_LOCKED`. Dragging a track header in the timeline to reorder tracks uses this operation.

The agent prunes assets with `assets_prune { video, assetIds?, apply?, revision?, commandId? }` (on the `agent`, `mcp` and `cli` surfaces). Without `apply` it is read-only. It lists the results of `videos.unusedAssets` (when `assetIds` is given, only those among them, with the paired other half included), plus `managedBytes`. IDs that are still referenced appear in `inUse`, and nonexistent ones in `notFound`. It does not change the video and needs no confirmation. With `apply: true`, if any listed asset is still in use or does not exist, nothing is committed and the request is rejected directly (the same errors as `removeAssets`). Otherwise, after confirmation, it compiles into one `removeAssets`. It returns the same receipt as `edits_apply`, plus `removed` (the list that was deleted). Its risk level is the same as `assets_import` (`edit`).

The agent adopts chapters carried by an asset's source with `chapters_adopt { video, asset?, document?, outline?, label?, revision?, dryRun? }` (on the `agent`, `mcp` and `cli` surfaces; risk level `edit`). Chapters come from the asset's source (`provenance.source`, video format spec §4.5). It first takes the structured `chapters[]`; if there are none, it parses the timestamp outline in `description` (at least two lines). When `outline` is given (`[{ at, title }]`, in source-time seconds, or a block of raw text with timestamps), it is used instead. When `asset` is not given, it takes the one asset in the video that carries source chapters or a description. If several carry them, it takes the one that is uniquely on the timeline; when `outline` is given, it may also be the only audio or video asset on the timeline. If no single asset can be chosen, the request fails with `INVALID_ARGUMENTS`. The transcript used for snapping is `document`, which must be a `speech` of this asset. When it is not given, the asset's sole transcript is used; if there are several, the request fails with `INVALID_ARGUMENTS`. With no transcript, no snapping is done. The rules (snapping, cleaning and projection) are in architecture design §7.9, “Adopt source chapters”. The result compiles into one `setChapters` (each chapter's `at` is timeline seconds, plus `title`; no summary), which replaces the existing chapters as a whole. `label` defaults to the localized “Adopt source chapters”. Confirm with the user before committing. It returns the same receipt as `edits_apply`, plus `assetId`, `documentId` (when a transcript was used), `notes` and `sourceChapters { entries, matched, ambiguous, snapped, unanchored, rows, dropped? }`. `entries` is the number of source chapters. The four counts are the status of each adopted chapter. Each item in `rows` is `{ title, at, sourceAt, status, anchor?: { tier, snippet }, offTimeline? }` (`at` in timeline seconds, `sourceAt` the snapped source time in seconds). `dropped` lists chapters that, after projection, fall on the same frame as the previous chapter and were not adopted. With `dryRun: true`, nothing is confirmed or committed; it returns `{ videoId, revision, committed: false, assetId, documentId?, chapters, sourceChapters, notes?, next }`. Rejections: if the asset's source has no chapters and its description has no outline, or the `outline` has no usable chapters, `NO_SOURCE_CHAPTERS`; if the asset is not on the root sequence (an enabled clip with no linear time mapping), `ASSET_NOT_PLACED`; an unknown asset is `ENTITY_NOT_FOUND`, and an unknown document is `DOCUMENT_NOT_FOUND`; if the caption and translation core is not built, `TOOL_UNAVAILABLE`.

### 4.3 Operations that need authorization

Ordinary, reversible edits may be executed directly under the authorization policy when the user asks for them directly. The following operations need the corresponding proposal or authorization (product design §7):

- batch re-cutting;
- edits that clearly rewrite meaning;
- paid generation;
- uploading to the cloud;
- voice cloning;
- replacing source media;
- overwriting existing output.

Do not turn every harmless micro-operation into a confirmation dialog.

Paid generation and uploading to the cloud are granted item by item through Grants: by data kind, recipient, scope, purpose and budget (architecture design §12.5, §7.8). The access mode and the service level of external services only decide whether to confirm each time; they do not replace authorization.

### 4.4 Export

Export is a Job with `kind: 'export'` (architecture design §9.11). The types are in `packages/protocol/src/exports.ts`, and the parameter Schemas are in `schemas.ts`.

```ts
type ExportSettings =
  | { kind: 'subtitles'; format: 'srt' | 'vtt' | 'ass' | 'json' } & ExportScope & TextExportOptions
  | { kind: 'transcript'; format: 'md' | 'txt' | 'json' } & ExportScope & TextExportOptions & TranscriptExportOptions
  | { kind: 'audio'; format: 'wav' | 'mp3' | 'm4a'; source?: AudioExportSource } & ExportScope & AudioExportOptions
  | { kind: 'video'; format: 'mp4' | 'webm'; source?: AudioExportSource } & ExportScope & VideoExportOptions
  | { kind: 'portable'; format?: 'cuccut'; missingAssets?: 'fail' | 'skip' }   // whole video, no range
  | { kind: 'project'; format: 'xmeml'; sequenceId?: Id };                  // one sequence, no range
```

- The range is sequence time `[start, end)`, in seconds; each segment of `ranges` produces one file. Times are all timeline times: the conversion for cutting, speed change and the instances that act is done in the engine (`exports.plan`), and cut words do not appear.
- The video must already be open (otherwise `not-found`, with `details.code` being `VIDEO_NOT_OPEN`). `create`, in one engine request, freezes the video revision and the plans for all ranges (AT-25), saves them as an `ExportSnapshot` artifact (`cuccut.export-snapshot/1`), and then runs a preflight: missing or changed source media, empty ranges, no exportable text, a target directory that is not writable or a specified file that already exists, missing ffmpeg, or loudness normalization turned on without a Render Worker found (`EXPORT_TOOL_MISSING`, `missing: 'export-worker'`). Preflight rejections are placed in `RpcError.details.code` (§11.4), and no task is created. The same `commandId` returns the original task.
- Target: by default it is the `exports/` directory under the video's source directory (for `purpose: 'preview'` it is `.cuccut-out/exports/`, which Space does not list). The file name is “video name.suffix.extension” (the suffix is the subtitle's language, `subtitles`, `transcript` or `audio`; for the rendered video it is the language of the subtitles burned into the picture, and no suffix is added if there are none; with several ranges, `.partN` is added as well). Duplicate names get a number such as “ (2)”, and existing files are not overwritten. A given `dir` must be an existing, writable absolute path; `fileName` is only available when producing one file, and if the file already exists it is rejected unless `overwrite` is set.
- The task generates each file in staging and validates each one (subtitles and transcripts: parsing, entry count, times monotonic and within range; audio: duration decoded by ffprobe within tolerance, sample rate and channels). The cancellation check comes before publishing. Publishing copies into the target directory and then hard-links to the final name, while registering as an artifact. Cancelling clears the staging and leaves no half-written file.
- `JobRecord.export` is `{ settings, snapshotArtifactId, videoRevision, sequenceId, destination: { dir, files, overwrite } }`. On completion, `result.outputs` has one entry per file: `artifactId`, `mediaType`, `byteLength`, `media` (subtitles and transcripts are `{ kind: 'text', entries, durationSec }`; audio is `{ kind: 'audio', durationSec, sampleRate, channels }`), `path` (the absolute published path), `format`, and `validation` (`checks`, expected and measured duration and entry counts, tolerance; when loudness normalization is on, `loudness: { target, measured: { inputLufs, integratedLufs, truePeakDb }, gainDb }`: `inputLufs` is the integrated loudness before mastering, `integratedLufs` and `truePeakDb` are after mastering, and `gainDb` is the sum of the static gains from each round of loudness normalization). Audio export progress is `{ unit: 'seconds', done, total }` (the sum of the output durations of the segments). When loudness normalization is on, each segment gives half to mixing and half to mastering, each advancing by its own completion ratio, and progress keeps advancing while mastering runs.
- `exports.renderText` only typesets the body of subtitles and transcripts. It does not write files, create tasks, or touch the target directory; it is used for the preview on the transcript page of the export panel and for the copy button at the top right of the preview box. It goes through the same freezing, preflight and formatting as `create`, so `content` is byte-for-byte identical to the file exported with the same settings. With several ranges there is one copy per segment; `fileName` is the expected name under the default target (when an actual export name conflicts, a number is added then); `warnings` are the same as for the export task (with several segments, `segmentId` is that copy's file name). `entries` and `durationSec` are synonymous with `media` in the export result; `words` and `cjkCharacters` are the Latin word count and Han character count of the main document body (excluding headings, speaker names, timecodes and translations). Preflight rejections are the same as for `create` (`VIDEO_NOT_OPEN`, `EXPORT_SOURCE_*`, `EXPORT_NOTHING_TO_EXPORT`, `EXPORT_RANGE_EMPTY`, etc.; the target-directory ones do not appear). Other kinds are rejected with `invalid-request` at parameter validation. It is read-only and is in the read-only set of the Web service.
- If some files fail validation or publishing fails, the task is `failed`, `error.code` is `EXPORT_PARTIALLY_PUBLISHED`, `error.details.failed` lists each file and its reason, and `result.outputs` still lists the files that were published. If all files fail, the code is `EXPORT_VALIDATION_FAILED` or `EXPORT_RENDER_FAILED`, depending on the reason.
- Audio sound source `source` (architecture design §9.13): `mix` is the finished mix. `original` disables instances carrying `extensions['cuccut.dub']` (dubbing and separated background sound and vocals), and cancels the mute of the `mutedItemIds` in the dub plans on this sequence. `{ dubGroupId }` keeps only the instances of that group and disables all others; if that group does not exist it is rejected with `invalid-request` (`DUB_GROUP_NOT_FOUND`). The source is turned into the engine's `exports.plan` `audioItems { disable, unmute }`, which changes only this export's plan, not the video. The finished video (`video`) accepts the same `source`: it changes only the sound plan and leaves the picture as is. Other kinds given `source` are rejected with `invalid-request`. The agent's `export` tool also accepts `source` (`mix`, `original` or `{ dubGroupId }`), and its risk grading is unchanged. CLI: `cuccut export <video> --kind audio|video --audio-source mix|original|dub:<groupId>`.
- Audio mixing and the frame plan share the same sound semantics (`render-graph`): gain, volume envelope (replacing volume; video format spec §3.9; segments of the range plan carry `envelope` breakpoints `[seconds, linear multiplier]`, in which case `gainDb` is 0), mute, fades, speed change, sound crossfade of transitions (equal-power; the outgoing side takes handles after the cut point, the incoming side takes handles before it), and the ducking attenuation (the v2 curve is expanded on linear gain, ramps are baked into dB breakpoints at 0.02 s and interpolated per sample), so the gain at any given moment is the same in preview and export. Speech-triggered ducking: `exports.plan` projects each transcript in the video (`kind: speech`) onto the sequence, and a word's range is its trigger range (video format spec §3.9, §5.7). Preview sends the same transcripts to the per-frame plan (`bc_set_speech` in `bindings/preview-wasm`), using the same projection, so once the transcript body is fetched, both sides attenuate equally much.
- Places that differ from the preview are written to `JobRecord.warnings`: a volume or envelope peak above 1 is 0 dB (`GAIN_ABOVE_PREVIEW`; preview tops out at 0 dB); speech-triggered ducking did not attenuate because the effective word stream is empty (`DUCK_NO_SPEECH`); a hold is silent (`HOLD_IS_SILENT`); the handles required for a crossfade exceed the source (`CROSSFADE_HANDLE_SHORT`), and missing parts are exported as silence; a style ASS cannot express (`ASS_STYLE_UNMAPPED`); subtitle split points estimated per word (`CUE_SPLIT_AT_ESTIMATED_TIMES`); a cut, incomplete sentence without a translation (`TRANSLATION_SKIPPED_PARTIAL_SENTENCE`); a translation unit marked stale was not written (`TRANSLATION_SKIPPED_STALE`); loudness that cannot be measured (`LOUDNESS_NOT_MEASURABLE`, in which case only the true-peak fallback is applied); and so on.
- Portable package (`portable`, architecture design §5.8, video format spec §8): a single file “video name.cuccut”, with `mediaType` `application/x-cuccut-package`, and `artifactId` is the sha256 of the whole file (the package is not copied into the artifact library). Preflight rejections: an unreadable source media version `ASSET_MISSING` (`conflict`, with `details.items` each `{ assetId, revision, name, reason }`, where `reason` is for example `missing`, `unreadable`, `changed`, `outside-project`); a document whose body contains a local machine path, `EXPORT_PACKAGE_LOCAL_PATH` (`invalid-request`, with `details.items` each `{ documentId, revision }`); a file that cannot be written into ustar, `EXPORT_PACKAGE_UNSUPPORTED` (`invalid-request`); insufficient space on the target disk, `EXPORT_INSUFFICIENT_SPACE` (`conflict`, with `details.required` / `available`); and `EXPORT_DESTINATION_EXISTS`, the same as for other kinds. With `missingAssets: 'skip'`, unreadable source media is not packed, with one `PACKAGE_ASSET_MISSING` warning per item; when the local paths in the other fields of the snapshot are replaced with placeholders, there is a `PACKAGE_LOCAL_PATH_REMOVED` warning. During execution: a linked asset that changed is `ASSET_CHANGED`, a full disk is `EXPORT_INSUFFICIENT_SPACE`, and a mismatch on re-reading after writing is `EXPORT_VALIDATION_FAILED`. Progress is `{ unit: 'bytes', done, total }`. `result.outputs[].media` is `{ kind: 'package', files, assets, missingAssets, documents }`, and `validation.package` is `{ files, verifiedFiles, bytes }`. `range`, `ranges` and `sequenceId` are rejected with `invalid-request`.
- Project (`project`, architecture design §9.13): one sequence (default: the main sequence) written as Final Cut Pro 7 XML, file “video name.xmeml.xml”, `mediaType` `application/xml`. Media is referenced by local path. Each item that cannot be expressed gets one `PROJECT_ITEM_OMITTED` warning (`detail` gives the instance's ID and name). If there is no clip that can be written, `EXPORT_NOTHING_TO_EXPORT`; if the sequence does not exist, `EXPORT_SOURCE_NOT_FOUND`. `result.outputs[].media` is `{ kind: 'project', clips, omitted, durationSec }`. `range` and `ranges` are rejected with `invalid-request`.
- Rendered video (`video`, architecture design §9.11, “Implementation of the rendered video”): the file name is “video name.mp4” or “video name.webm”. When subtitles are burned into the picture (`burnCaptions` not turned off), the languages of those subtitles are added, joined by `-` in timeline order from top to bottom with duplicates removed (file-name data examples: “视频名.zh-Hans.mp4” and “视频名.en-zh-Hans.mp4”, i.e. “video name.zh-Hans.mp4” and “video name.en-zh-Hans.mp4”). Only the subtitle instances enabled on the subtitle tracks actually rendered into the picture this time are counted (visible, with the solo-display rule as for the picture); documents with no language set are not counted (`burnedCaptionLanguages` of `@cuccut/protocol`). With several ranges, `.partN` is added. MP4 is H.264 or HEVC with AAC; WebM is VP9 with Opus; both are yuv420p tagged BT.709. Preflight is run by the Render Worker: content that cannot be drawn is rejected with `EXPORT_UNSUPPORTED_CONTENT` (`RpcError.code` is `invalid-request`), with `details.items` each being `{ itemId, scope, layerKind, effectId?, transitionId?, kind?, reason, message }`. `scope` is `layer` (the whole layer is not drawn), `effect` (this effect is skipped), `transition` (a hard cut instead), or `asset` (the source media cannot be decoded into a picture, so the whole layer is not drawn). `reason` is for example `generator-not-implemented`, `bundle-without-prerender`, `asset-undecodable`, `preset-unknown`, `preset-missing`, `lottie-asset-missing`, `lottie-unreadable`, `template-missing`, `template-logo-image-not-supported`, `sticker-asset-not-supported`, `placeholder-asset-not-supported`, `effect-unknown-kind`, `transition-not-implemented`, `caption-document-missing`, `caption-unknown-document`, `caption-style-missing`, `caption-unknown-style`. The judgment is made in the same place the preview lists them (architecture design §9.1). With `onUnsupported: 'skip'` it is not rejected, and each item gives one `EXPORT_CONTENT_SKIPPED` warning. Progress is `{ unit: 'frames', done, total }`. `result.outputs[].media` is `{ kind: 'video', durationSec, width, height, videoCodec, audioCodec, frames, fps }` (the same variant as file transcoding; `frames` and `fps` are always present in rendered video exports, though transcoding may omit them). `validation.video` is `{ expectedFrames, frames, width, height, fps, streams }`: the frame count differs by at most one frame, and the picture and sound durations are within one frame (sound adds 50 ms). Output size: when only `width` or `height` is given, the other side follows the canvas ratio and the picture fills the frame. When both are given, the output is exactly that size; the picture is scaled to the largest size that fits at the canvas ratio (the side that does not fill is rounded to even), centred, with the rest being black bars (a canvas wider than the output gives letterbox bars top and bottom; a narrower one gives pillarbox bars left and right). The layout within the picture scales with the canvas and is not re-laid-out for the output ratio. The size is set by the engine (`output` of `exports.plan`), and the Runtime and Worker use it as is. In the interface's export panel, the “画幅” (frame) section defaults to “跟随画布” (follow canvas; no width or height, and when only the resolution is changed, only `height` is given). 16:9, 9:16, 1:1 and 4:5 can be chosen (presets with the same ratio as the canvas are not listed): the short side is set by the resolution preset, the long side is derived from the frame ratio and rounded to even, both width and height are given, and the panel states that black bars are added. CLI `--width` and `--height`, and the agent export tool's `width` and `height`, follow the rules of `exports.create` (the tool's approval summary states the size). Warnings for rendered video: `EXPORT_SIZE_ADJUSTED` (width or height adjusted to even); `EXPORT_RENDER_NOTE` (hints from the rendering kernel, e.g. skipped element parameters, a sound wave with no spectrum, a GIF too large so only the first frame is drawn, or font families present in neither the built-in nor the local fonts; `detail` gives the instance ID and the hint); `EXPORT_CONTENT_SKIPPED`; `FONT_NOT_DOWNLOADED` (a font family in the font catalog that was not downloaded or failed to download is drawn with a fallback font, architecture design §9.11; `detail` is “「family」weight: reason, replaced with 「fallback family」”, i.e. “‘family’ weight: reason, replaced with ‘fallback family’”; `font` is `{ family, weight, italic, fallback, reason }`; it does not reject the export, and does not require choosing a substitute font first); and the mixing warnings identical to those of the audio export. When the export uses fonts that must be downloaded, there is a `downloading` stage before the task starts drawing (progress by bytes; these downloads do not create a separate `fontDownload` task). Cancelling the export only cancels downloads the export itself started. A same face already downloading elsewhere (font selection, opening a video, preview) is just waited on, and cancelling the export does not cancel it.
- Transcript format (architecture design §9.13): sentences are divided into paragraphs by the rules of the editor's transcript panel (`TRANSCRIPT_PARAGRAPH`), with a blank line between paragraphs. Markdown starts with `# video name`; plain text has no heading.
  - Timecodes (`timestamps`): append ` [mm:ss]` at the end of a paragraph (`[hh:mm:ss]` once past an hour). It is the start time of that paragraph, not in backticks. In bilingual mode it follows the end of the source paragraph.
  - Speakers (`speakers`, on by default): when a paragraph has a speaker, every paragraph writes it, even when there is only one speaker. Markdown `**Name:** body`, plain text `Name: body`; the colon is always half-width and does not follow the interface language. When a speaker has no name, use “说话人 N” (speaker N). When speakers are turned off, the JSON also does not include `speaker`.
  - Chapters (`chapters`): `kind: 'chapter'` markers on the sequence start a new paragraph at the beginning of that chapter, and the chapter subheading is written before the chapter's first paragraph: Markdown `## chapter name · mm:ss` (with `timestamps` off, only the chapter name is written), plain text `— chapter name —`. Chapters with no paragraphs after them are not written. JSON does not write chapters.
  - Front matter (`frontmatter`, Markdown only): a YAML block wrapped in `---` before `# video name`, with fields in the order `title`, `description`, `source`, `author`, `published`, `platform`, `duration`, `language`, `translation`; missing fields are omitted. Then `speakers` lists the speakers appearing in the body (not listed when speakers are off), and `chapters` lists the chapters written (`"[mm:ss] chapter name"`). All values are written as JSON strings, with line breaks folded into spaces. `source`, `author`, `published` (`YYYY-MM-DD`) and `platform` come from the import source of the link of the main document's media. `duration` is the duration of this transcript; `language` and `translation` are the languages of the main document and the bilingual secondary document. There is currently no video description, so `description` is not written.
  - Not skipping cut parts (`skipCut: false`): no timeline projection; the original text is taken directly from the document body (transcript words, sentences of the subtitle layer; words deleted in the transcript panel, which are merely hidden, are still excluded). Times are the document's own source-media clock, and chapters are moved to the corresponding position in the original text. Without a range, it is the whole document; with a range, the original text between the first and last items that the range projects to is taken, and anything cut in between is included too. The duration validated is the longer of the original text span and the source media duration.
- Word-level timing is written only when every word's timing is trustworthy (AT-05): in JSON, `wordTiming` is `word`, `partial` or `none`. Sentence-level documents, interpolated words, and missing words do not write `words`.

### 4.5 Speech Worker

The private Worker of the subtitle and translation core (architecture design §7.9, §13.1). It is not a client command surface: a fixed pipeline step starts it, and clients never see it. Transport is the same as the Model Worker: one JSON line per message over stdio. The Runtime sends `{ id, method, params }`, the Worker replies with `{ id, result }` or `{ id, error: { code, message, details? } }`, and it may push `{ event, params }` on its own. A bare `cancel` line on its own is equivalent to a `cancel` request. Protocol name `speech-worker/1`. The Runtime side is in `packages/jobs/src/pipelines/speech-worker.ts` (`runSpeechTranslate`), and the Worker is in `crates/speech-worker`.

| Direction | Message | Content |
| --- | --- | --- |
| Runtime → Worker | `hello` | Result `{ protocol: 'speech-worker/1', version, methods: ['translate'] }`. If the protocol does not match, the Runtime does not use this Worker (`WORKER_INCOMPATIBLE`). |
| Runtime → Worker | `translate { input, staging }` | The frozen input file and the staging directory for this step, both as absolute paths. Result `{ translation, cues, report, unitCount, cueCount, llmCalls }`; the first three items are file names inside staging. |
| Worker → Runtime | event `llm.request` | `{ requestId, kind, attempt, system, user, temperature, maxOutputTokens }`: one model call. `attempt` is the retry number of the core for this kind (counting from 0). `maxOutputTokens` is only set for kinds under the file contract (scaled to the input, 4096–16384); otherwise null. |
| Runtime → Worker | `llm.reply` | `{ requestId, text }` or `{ requestId, error: { code, message, class, status? } }`. Result `{}`. If it is not the call being waited on, `UNEXPECTED_REPLY`. |
| Worker → Runtime | event `progress` | `{ stage, done, total }`. `stage` is `brief`, `translate`, `align`, `row-repair` or `write`. For `translate`, the unit is sentences. |
| Worker → Runtime | event `checkpoint` | `{ phase, pages, translatedSentences }`: a checkpoint has just been written. |
| Worker → Runtime | event `resumed` | `{ phase, translatedSentences, totalSentences }`: continuing from the last checkpoint. |
| Runtime → Worker | `cancel` | Result `{}`. A running task stops before the next call or backoff and ends with `CANCELLED`. Checkpoints are kept. |

- Only one task runs at a time. Requests that arrive during a task (except `hello`, `cancel` and `llm.reply`) are queued until the task ends. Closing stdin is equivalent to cancelling: after the task wraps up, the process exits with code 0. Starting with command-line arguments exits with code 2.
- `class` decides how the core handles a failure: `retryable` (transport failure; `status` is the HTTP status, and the core retries with its own backoff), `malformed` (the answer is unusable; the core re-sends, splits pages or fills in the gaps), `terminal` (no further calls; the task fails with this `code`), and `cancelled` (same as `cancel`). For how the Runtime classifies them, see architecture design §7.9.
- Error codes: `INVALID_PARAMS` (missing path; source and target language have the same primary subtag), `METHOD_NOT_FOUND`, `UNEXPECTED_REPLY`, `INPUT_UNREADABLE` (input cannot be read, is not in the right format, or has no translatable sentences), `STAGING_WRITE_FAILED`, `MODEL_OUTPUT_INVALID` (after the core's re-sends and fill-ins are used up, some sentences still have no acceptable translation; `details.missingSentences` lists them; the checkpoint is kept and a retry only fills in those sentences), `PROVIDER_UNAVAILABLE` (a `retryable` failure after the core's retries are used up), `CANCELLED`, and the `code` of a `terminal` reply itself (e.g. `BUDGET_EXCEEDED`; `PROVIDER_REJECTED` when absent). A task failure carries `phase` and `translatedSentences` in `details`.

Input (`cuccut.speech-worker.translate/1`; unknown fields are rejected):

```ts
interface SpeechTranslateInput {
  schema: 'cuccut.speech-worker.translate/1';
  media: { assetId: Id | null; path?: string; contentHash: string; duration: MediaTime; sampleRate?: number };
  sourceLanguage: string | null;      // language of the transcript; null if unknown
  speechRef: { id: Id; revision: string };
  sequenceId: Id;
  speech: SpeechBody;                 // cuccut.speech/1 body (video format spec §5.2)
  targetLanguage: string;             // BCP 47
  glossary: { source: string; target: string; note?: string }[];   // frozen, deduplicated terms
  glossaryRef: GlossaryRef | null;    // written into the translation as-is
  params?: { instructions?: string; backoffScale?: number };       // style hints; backoff duration multiplier, default 1
  translation?: TranslationBody;      // in-place refresh: existing translation for this language (cuccut.translation/2), used as the base
  sentences?: Id[];                   // in-place refresh: sentences to re-translate (s-<first-word ID>), at least one; given together with translation, or both omitted
}
```

In-place refresh (when `translation` and `sentences` are given): the language of the base must equal `targetLanguage`, and every sentence in `sentences` must exist in the transcript, otherwise `INPUT_UNREADABLE`. Only the named sentences are sent for translation (even ones whose translation is still fresh are re-translated). No target-direction brief is made. Alignment and wrap-up only cover these sentences. `glossaryRef` is taken from the base, not from the input. `total` in `progress` is the number of named sentences.

All outputs are written to staging, written to a temporary file first and then renamed:

- `translation.json`: a `cuccut.translation/2` body (video format spec §5.3). Without a base, it is a new translation and does not read any existing one. In an in-place refresh, it is the base together with the re-translated sentences: unit IDs and order are kept, sentences that have no unit in the base are inserted by the position of their first word, and `sourceBasis` is replaced with the source of this run. The caller only takes the units of the named sentences, and the base is authoritative for the other units. Sentences are derived by the rules of the subtitle and translation core. `sourceFingerprint` is the core's fingerprint, and `sourceBasis.editViewHash` is the digest of `{ derivation: 'speech-doc/sentences', sentences: [[id, fingerprint], …] }`.
- `cues.json`: `{ schema: 'cuccut.speech-worker.cues/1', language, timescale, cues: { unitId, sentenceId, text, start, end, fallback }[] }`. Times are integer ticks on the transcript clock (same `timescale` as the transcript), clamped within the media duration, sorted by time, and non-overlapping. Empty and zero-length cues are not written. `fallback` marks the cues whose timing was spread by sentence duration because alignment was unavailable.
- `report.json`: the mode (`mode`: `full` or `refresh`), the number of sentences sent for translation (`targetSentences`), the brief (`skipped`, `generated`, `degraded`, `resumed`), paging, alignment, wrap-up rounds, number of calls and notes, for summaries and diagnostics.
- `checkpoint.json`: see “断点” (checkpoint) in architecture design §7.9.

After the Runtime reads these back, it checks them: the translation must match the shape in video format spec §5.3 and the frozen `speechRef`, and the cues must follow the rules above (in an in-place refresh, the per-unit check against cues only covers the named sentences). If they do not match, this step fails with `WORKER_OUTPUT_INVALID`. If the Worker exits unexpectedly, the step fails with `WORKER_FAILED`. The Worker's own errors become the error of this step under their `code`. Failures caused by a `terminal` reply instead throw the Runtime-side error unchanged.

## 5. Receipt

A receipt is returned after the transaction is persisted successfully. The receipt is the only evidence that “this change actually happened”. Neither the UI nor agents may claim a change is complete before they receive the receipt.

```ts
// field set completed for this spec
interface TransactionReceipt {
  transactionId: Id;
  commandId: Id;
  status: 'committed';
  videoId: Id;
  previousRevision: Revision;
  videoRevision: Revision;
  eventSeq: string;
  label: string;                                   // change name (§3.1)
  labelRef?: MessageRef;                           // message reference for the change name: engine-generated, or supplied by the caller with label
  layer?: 'instance' | 'parameter' | 'source';     // which layer a code-synthesized change belongs to
  createdIds: Id[];
  updatedIds: Id[];
  deletedIds: Id[];
  lineage: Record<Id, Id[]>;                       // old instance → new instances produced from it
  impact: {
    oldDurationFrames?: number;
    newDurationFrames?: number;
    captionProjection?: 'unchanged' | 'recomputed';
    translationUnitsStale: Id[];
    dubbingUnitsStale: Id[];
    orphanedAnchors: Id[];                         // instances whose semantic anchor cannot be resolved or placed, left in place (video format spec §3.16)
    invalidatedCaches?: string[];
    removedTransitions?: { id: Id; reason: 'item-deleted' | 'not-adjacent' | 'too-long' | 'handles-insufficient' | 'overlap' }[];
    shortenedTransitions?: { id: Id; durationFrames: number; effectiveFrames: number }[];
    removedByCuts?: Id[];                          // instances deleted along with cuts (video format spec §6.7)
    cutsNotRelaid?: Id[];                          // cuts that were restored but whose seam could not be found to put them back
    removedWithTarget?: Id[];                      // instances deleted together because their follow target (item-local) was deleted (video format spec §3.16)
    removedTracks?: Id[];                          // empty tracks removed by deleteTrack (§4.2)
    removedAssets?: Id[];                          // asset records removed by removeAssets, including code packages or pre-rendered stand-ins removed as a pair (§4.2)
  };
  timeResolution?: TimeQuantizationReceipt[];      // §6
  preserved: Id[];                                 // objects explicitly kept unchanged
  provenance?: { taskId?: Id; runId?: Id; jobIds?: Id[]; proposalId?: Id };
  undo: { available: boolean; token?: string; scope?: string; unavailableReason?: string; unavailableReasonRef?: MessageRef };
}
```

A receipt must show:

- the IDs of created, updated and deleted objects;
- lineage: how old and new instances correspond after a split or trim;
- the versions before and after the commit;
- the change in duration;
- stale dependencies: which translated sentences, dubbing units and anchors need handling;
- objects removed along with the change, and why: transitions that no longer hold after an edit are listed in `impact.removedTransitions` (video format spec §3.9), and their IDs are also in `deletedIds`; one-sided transitions shortened with the instance are in `impact.shortenedTransitions` (the written length and the effective length); instances deleted along with cuts are in `impact.removedByCuts`;
- source: which task, which run and which computations;
- the scope that can be undone;
- objects explicitly kept unchanged.

**Deleting an instance usually deletes only the reference**, not the original media, recognition results, audio, or paid-for outputs.

Stale dependencies must be reported truthfully. For example, deleting a pause between sentences does not change the content of the translated sentences, so `translationUnitsStale` is empty. Deleting content inside a sentence must report the affected stale sentences by the fingerprint of the valid sentence (video format spec §5.7). It must not always return an empty array.

## 6. Time Input and Quantization Receipt

The types `TimelineTimeInput`, `FrameAlignment` and `TimeQuantizationReceipt` are defined in video format spec §2.8 and §2.9. This chapter specifies how they are used in the protocol.

### 6.1 Input

- Visual time commands accept `TimelineTimeInput`. `seconds` and `frames` are mutually exclusive inputs and never appear together.
- The `sequenceId` in the command and the `expectedRevision` on the envelope determine which frame grid the input belongs to.
- **Commands that contain only bare frame numbers, where the sequence and frame rate cannot be determined, are always rejected** (`TIME_DOMAIN_MISMATCH`).
- Anchors for words, sentences and occurrences are the preferred input for voice-over and semantic editing. A request such as “follow this sentence” sends the anchor, and the engine resolves the current relation. The caller does not convert it to seconds first.
- The UI and agents do not compute frames themselves. A request such as “two seconds later” sends a relative offset, not a frame number computed by the caller.

### 6.2 Three values kept apart

The protocol distinguishes three values, and all three appear in the receipt:

| Value | Meaning |
| --- | --- |
| `requested` | The formatted input sent by the caller |
| `requestedTime` | The exact time the input resolves to |
| `actualFrame` / `actualTime` | The frame and time the value actually lands on after quantization |

`delta` is the actual value minus the requested value. In the receipt, `requestedTime`, `actualFrame`, `actualTime`, `delta` and `editFps` must not be omitted. Later reads must use `actualFrame` or the authoritative time, and must not be back-derived from formatted text.

### 6.3 Quantization happens inside the transaction

- After reading this operation's baseline revision, the engine parses the time input and **quantizes once** for visual targets. It commits atomically together with the edit operations, dependency impact, receipt and event sequence number.
- Preflight (§7) uses the same algorithm but does not hold on to a successful commitment.
- On formal commit, if the frame rate or video revision has changed, a conflict must be returned. **Old previews are not silently reinterpreted under the new frame rate.**

### 6.4 Quantization cannot widen scope

The requested range and the actual result both take part in permission, protection and lock checks. Quantization cannot be a reason to widen a delete range, break through a locked track, or swallow a word. If after quantization the length is zero, out of bounds, or breaks a safe interval, return `TIME_RANGE_COLLAPSED`. Do not automatically pad a frame or automatically widen the deletion.

### 6.5 Changing the edit frame rate

`changeSequenceFrameRate` is an edit transaction with a clearly defined associated scope. Without passing the `preserve` policy and dependency validation, `Sequence.fps` cannot be partially modified. For the rules, see the video format spec §2.12.

## 7. Batch preflight

Agents often need to submit several related edits at once. Preflight lets them see the impact of the batch before deciding whether to commit. **Preflight is a proposal, not a reserved success.**

### 7.1 Two methods

```ts
// Completed by this spec
interface PrepareBatchRequest {
  videoId: Id;
  baseRevision: Revision;
  operations: EditOperation[];
  label: string;
}

interface PreparedBatch {
  proposalHash: string;
  baseRevision: Revision;
  normalizedOperations: EditOperation[];
  readSet: Array<{ entityId: Id; revision: Revision }>;
  impact: JsonValue;                      // Same shape as the receipt's impact
  timeResolution: TimeQuantizationReceipt[];
  warnings: Array<{ code: string; entityIds: Id[]; message: string }>;
  protectedObjects: Id[];
  estimatedCost?: JsonValue;
  failedOperationIndex?: number;          // On preflight failure
  failure?: ErrorBody;                    // §11.1
}

interface ApplyPreparedRequest {
  proposalHash: string;                   // Must match the approved content
}
```

`edits.applyPrepared` is sent through the ordinary command envelope, with a new `commandId` and `expectedRevision`.

### 7.2 prepareBatch

`edits.prepareBatch` runs domain validation against the frozen `baseRevision` and returns: the normalized operations, `readSet`, impact summary, warnings, protected objects, estimated cost and `proposalHash`.

The agent-facing `edits_apply` has a lighter preflight, `dryRun: true`. It is not `prepareBatch`, which is not yet implemented. It runs every step on the commit path before the engine: converting artifacts into import operations, filling in operations, path restrictions for externally served paths, checking each operation against its schema, verifying that referenced existing objects and media files exist, and checking whether `expectedRevision` is the current revision. On error it returns the same error code the engine would reject with (a revision mismatch is `PROJECT_REVISION_CONFLICT`; everything else is `INVALID_OPERATION`, with the first failing operation and all problems). On success it returns the completed operations and impact (`committed: false`). It does not commit, does not enter history, and requires no confirmation. Same-track overlap, locks and task protection are only checked by the engine at commit time, so a passing preflight does not mean the commit will succeed. The CLI is `cuccut edits apply … --dry-run`.

It does **not**:

- increment the video revision;
- register a fake successful task;
- hold a lock long-term;
- execute steps that need computing or purchasing. Those start a separate Job.

### 7.3 applyPrepared

`edits.applyPrepared` rechecks:

- whether authorization still holds;
- whether the task's execution generation is still valid;
- locks and protected objects;
- the video's current revision.

Under P0, any revision conflict is rejected. **A successful earlier preflight is never grounds for writing blindly.**

- If any operation in a batch fails, return `failedOperationIndex` and the reason. The whole batch is not partially persisted.
- The same idempotency key with the same payload returns the original receipt.
- Reject when `proposalHash` does not match the content being committed now.

### 7.4 Limits and splitting

Limits on the number of operations, input size and preflight compute are returned by the capability snapshot (architecture design §3.6).

When a batch must be split beyond the limit, it must be presented explicitly as multiple commits, linked by a shared `runId` or `changeGroup`. Do not claim that multiple batches are still one atomic transaction.

### 7.5 Scope

- Adjacent, low-risk edits may form one batch.
- Long-running model computation and cross-video writes must not be packed into one batch.
- Manual gestures still go through the single-transaction path (§9). They are not forced to be wrapped as one model turn.

## 8. ChangeSet, checkpoints and undo

### 8.1 ChangeSet

A ChangeSet is a set of **pending** edits to apply, with their description: operations, `baseRevision`, `readSet`, direct impact, objects that need linked checks, and the set of objects that stay unchanged.

- A ChangeSet can be previewed, but it is not a working draft that can evolve independently.
- A formal receipt exists only after it is committed as a transaction.
- A candidate is a ChangeSet or an independent version that can be opened for viewing. An unapplied candidate is not a working draft.

### 8.2 Checkpoints

- Save a checkpoint before large structural changes.
- **P0**: named checkpoints, sequential undo, verified single-transaction compensation.
- **P1**: full branching and merging.
- “Make another version” creates a candidate or independent version. “Restore color scheme” restores only the target properties and does not roll back the entire video.

### 8.3 Undo is a compensating transaction

Undo is a **compensating transaction** against one committed transaction. On commit, it checks the current state of the target objects.

- It does not overwrite the current state with an old whole-video snapshot. When a user undoes their own edit, it does not erase supplementary footage the agent added afterward.
- Operations involving external assets only undo the reference. They do not delete generated results that other objects may use.
- Undo cannot reverse cloud billing that has already occurred.
- For operations with no safe compensation implementation, do not show an available undo button. In the receipt, set `undo.available` to `false` and explain why.
- Restoring cut content is also a new transaction (video format spec §6.2).
- When compensation leaves behind transitions that no longer hold (video format spec §3.9), undo is rejected (`UNDO_CONFLICT`; `details.removedTransitions` lists these transitions and the reasons). The transitions are not silently deleted.

### 8.4 Task-level undo

The multiple transactions of one long task form a recognizable group of operations (shared `taskId` / `runId`).

- You can “undo the application of this subtitle generation” without requiring deletion of the original recognition artifacts.
- “Stop and undo” first establishes a stop barrier, then verifies compensation transaction by transaction. It does not roll back the entire old video (architecture design §7.4).
- Do not lock the video for long during network waits.

## 9. Manual interaction

### 9.1 Gestures

```text
pointerdown  → establishes a gesture
pointermove  → updates the transient overlay, no commit
pointerup    → produces one transaction
```

- Optimistic display is allowed before confirmation. When the transaction fails, roll back **this gesture**, not the entire old video.
- Selection and viewport are saved as UI preferences and do not enter the business undo stack.
- Transient state during a gesture does not enter the video and is not read by the agent.

### 9.2 Text input

- Text input is merged into a clear editing session. Cursor movement does not produce video history.
- IME composition text is unfinished input and must not be committed.
- The throttle value for auto-commit can be tuned. But data safety must not depend on “saving a full snapshot every few minutes”.

### 9.3 Confirmed means persisted

Edits confirmed to the user must already be persisted. The UI must not show “Saved” before a receipt is received.

### 9.4 Before sending a request

Before the user submits a natural-language request, the client settles the local edits that this request references, then freezes the context (ContextBarrier, architecture design §4.6). If there are referenced edits that could not be persisted, return `CONTEXT_PENDING_EDITS`. Do not silently read the old version.

The selection sent to the agent includes `videoRevision`, `sequenceId`, instance ID, word anchors and the visible frame range. It is not a phrase like “that segment”. After a task completes, revalidate the input's version. Old results may be kept as artifacts, but they must not be automatically applied to the new selection.

## 10. Events

### 10.1 Video events

```ts
// Field set completed by this spec
interface VideoEvent {
  videoId: Id;
  eventSeq: string;                  // Monotonically increasing within the video
  videoRevision: Revision;
  transactionId: Id;
  changedIds: Id[];
  projection: JsonValue;             // Projection changes the client can consume directly
  actor: { kind: 'user' | 'agent' | 'system'; id: Id };
  label: string;                     // Same as the receipt (§3.1)
  labelRef?: MessageRef;
  taskId?: Id;
}
```

- `eventSeq` and the video revision are persisted in video storage. The Runtime's run generation only identifies one run of the service and does not take part in ordering.
- Session sequence numbers, Job sequence numbers and video event sequence numbers are **managed separately**. They do not share one ambiguous cursor.

### 10.2 Delivery

- Events and video changes are written to the outbox in the same transaction. The Runtime pushes from the committed outbox.
- Delivery semantics are **at-least-once**. Clients deduplicate by `videoId + eventSeq`.
- If the Runtime crashes after commit and before broadcast, it resumes pushing from the outbox after restart. Confirmed edits keep a recovery path and are not lost.

### 10.3 Subscription and gaps

- A subscription obtains a snapshot at the same watermark, plus the events after it.
- The client applies events in order. When a sequence gap is found, hold off on committing, then backfill the events or refetch the snapshot. **Do not keep modifying a mirror that is missing events.**
- Candidates and UI transient gestures are saved separately. When reconnection fails, do not overwrite the server with an old full snapshot.
- “Connected” does not mean “data is caught up”. Until caught up, the client shows cached data.

## 11. Error contract

### 11.1 Structure

```ts
interface ErrorBody {
  code: string;
  message: string;                   // Human-readable description; programs do not parse it
  entityIds: Id[];
  inputRevisions: VersionRef[];
  retryability: 'same-command' | 'after-refresh' | 'after-user-action' | 'never';   // Values completed by this spec
  details: JsonValue;
  recovery?: string;                 // Suggested recovery
  messageRef?: MessageRef;           // Message reference for message (end of §11.1)
  recoveryRef?: MessageRef;          // Message reference for recovery
}
```

An error response must include `code`, `entityIds`, `inputRevisions`, `retryability` and `details`. It must not return only a stderr blob that the agent has to guess from.

| `retryability` | Meaning |
| --- | --- |
| `same-command` | Can be retried as-is with the same `commandId` |
| `after-refresh` | Re-read first, then submit a new operation |
| `after-user-action` | The user must supply, authorize, or make a choice |
| `never` | This request will never succeed |

The gateway's error `RpcError` is `{ code, message, details?, messageRef? }`. `message` is generated in the Runtime's current language (`ui.language`), and `messageRef` is its message reference `{ key, params? }` (params are scalars or nested references). When `messageRef` is present, the UI and CLI use it to regenerate the description in their own language. Keys they do not recognise (sent by a newer Runtime) fall back to `message`. Programs judge errors only by `code` and `details`, not by these two fields. The engine's `ErrorBody` likewise carries references: `message` and `recovery` are the English default text, and `messageRef` / `recoveryRef` are their references (keys live in the `engine.*` and `engineHost.*` areas; entity kinds and multiple parallel causes use nested references). When the Runtime converts it to an `RpcError`, it expands `message` in its own language and attaches `messageRef`. When the UI shows `recovery`, it uses `localizeText(recovery, recoveryRef)`. The reason an undo is unavailable works the same way: next to the receipt's `undo.unavailableReason` is `undo.unavailableReasonRef`. The convention is in [repo conventions §5](../repo-conventions.md#5-copy-and-multilingual-support).

Warning for moving the model directory (`JobRecord.warnings`): `MODELS_DIR_SOURCE_KEPT` (after the move, some files in the original directory could not be deleted; `detail` names a few; they can be deleted manually).

Warnings (`JobRecord.warnings`) for dubbing and voice cloning: `DUB_UNITS_STALE` (stale translations were not synthesized), `DUB_UNITS_OVERLONG` (sentences that did not fit were not placed), `DUB_UNITS_OFF_TIMELINE` (the source sentence is not on the timeline), `DUB_BACKGROUND_MUTED` (original audio was muted without separating the background, so the background was lost too), `DUB_SEPARATION_NOT_CONFIGURED` (separation was requested but there is no executor; this step is skipped), `DUB_VOICE_UNAVAILABLE` (the voice bound to the speaker is unavailable; that speaker's sentences were not synthesized, and were not switched to another voice), `DUB_MUTED_UNVOICED` (in instances that mute the original audio, some sentences had an unavailable voice and were not synthesized, so their original audio was muted too), `VOICE_CLONE_OLD_NOT_DELETED` (the replaced old clone was not deleted from the remote; `detail` carries its `voiceId`).

The model interface service (architecture design §4.8) does not use the gateway's `RpcError`. Errors are answered with an HTTP status and an OpenAI-style error body `{ error: { message, type, code, param: null } }`. `type` follows OpenAI's convention for the status, and `code` is one of the error codes below, with only a one-sentence description and no `details`:

| HTTP | `code` | Meaning |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | The request body is not valid JSON or multipart, a field is missing, or a value is invalid |
| 400 | `UNSUPPORTED_PARAMETER` | A recognized but unsupported parameter: an image in `url` form, streaming speech and transcription, tool calls, `n > 1`, `logprobs`, unsupported formats |
| 400 | `PROVIDER_REJECTED`, `INPUT_TOO_LONG`, `ASSET_MISSING` | The job failed with these errors |
| 401 | `AUTHENTICATION_REQUIRED` | No token, a wrong token, or a revoked token (with `WWW-Authenticate: Bearer`) |
| 403 | `ORIGIN_NOT_ALLOWED`, `HOST_NOT_ALLOWED` | The request carries an `Origin`; the `Host` is not a loopback address |
| 403 | `SERVICE_READ_ONLY` | A generation request at the `read` level |
| 403 | `SERVICE_APPROVAL_DENIED` | The approval at the `ask` level was denied, timed out, or cancelled |
| 403 | `GRANT_REQUIRED`, `GRANT_REVOKED` | No grant covers this outbound send (the `auto` level does not generate approvals), or the grant was revoked or has expired; the grant became invalid before the job started |
| 403 | `FORBIDDEN` | Any other denial |
| 404 | `NOT_FOUND`, `MODEL_NOT_FOUND` | No such endpoint; an unknown or unroutable model (including an alias with the wrong capability) |
| 405 | `METHOD_NOT_ALLOWED` | The endpoint does not accept this method (with `Allow`) |
| 409 | `JOB_CANCELLED` | The job was cancelled in CucCut |
| 409 | `BUDGET_EXCEEDED`, `BUDGET_UNVERIFIABLE` | The grant's budget is used up, or there is an amount cap but the amount cannot be estimated; answered before approval and submission, so the request never reaches the provider |
| 413 | `PAYLOAD_TOO_LARGE` | The upload or JSON request body exceeds the limit |
| 429 | `TOO_MANY_REQUESTS` | This client's in-flight generation requests have reached the limit (`Retry-After: 1`) |
| 429 | `PROVIDER_QUOTA_EXCEEDED` | The provider's rate limit or quota is exhausted; if the provider sent `Retry-After`, it is passed through unchanged |
| 502 | `MODEL_OUTPUT_INVALID`, `PROVIDER_AUTH_FAILED`, `PROVIDER_UNAVAILABLE`, `REMOTE_NODE_REJECTED`, `REMOTE_NODE_LOST` | The job failed with these errors (structured output that does not match the schema is `MODEL_OUTPUT_INVALID`) |
| 503 | `CAPABILITY_NOT_CONFIGURED`, `MODEL_UNAVAILABLE`, `RUNTIME_BUSY`, `JOB_INTERRUPTED` | This capability has no routable model right now (the message explains how to enable it); the Runtime is stopping; the job was interrupted |

`PROVIDER_*` are the values of `JobRecord.error.code` when a job fails. `models.configure`, `models.addAccount`, and `models.updateAccount` with `verify` also use them when verification fails, placed in `RpcError.details.code` (`RpcError.code` is `conflict`), and the configuration is not saved. The `message` and `details` of these errors contain no keys: a key echoed back by the provider is replaced with `[REDACTED]`.

### 11.4 Assets, code and rendering

| Code | Meaning | Prescribed recovery |
| --- | --- | --- |
| `ASSET_MISSING` / `ASSET_CHANGED` | Media is missing, or its bytes do not match the record | Relink, or explicitly change the version |
| `FONT_MISSING` | The font cannot be reproduced | Supply it, or accept a substitute. Export of a finished cut freezes the local fonts it uses (file, face index, and whole-file digest, `ExportSnapshot.fonts`). If at execution the file is missing or differs from the frozen one, the whole job fails with this code, and `details` is `{ family, weight, italic, path, reason }` (`reason` is `missing`, `changed`, or `unreadable`). Restore the original font file or re-export (re-freeze). A family that is in neither the render kernel's bundled fonts nor the local fonts at freeze time does not use this code: it is drawn with the kernel's fallback rules and reported in the result's `warnings` (`EXPORT_RENDER_NOTE`, for both text elements and subtitles), and the export is not rejected. A family in the Google Fonts catalog is downloaded during the export job (one already in the download cache is still frozen, `source: 'downloaded'`). When it is not downloaded (`fonts.autoDownload` is off, or the setup is strictly offline) or the download fails, this code is also not used: it is drawn with the fallback font and warned with `FONT_NOT_DOWNLOADED` (`detail` gives the family, weight, and reason) |
| `ADAPTER_CAPABILITY_MISSING` | The runtime environment does not support the required capability | Change the adapter, explicitly Bake, or refuse |
| `NONDETERMINISTIC_SOURCE` | The result of seeking to frames does not meet the declaration | Modify the source, switch to sequential, or Bake in a fixed environment |
| `CODE_SANDBOX_UNAVAILABLE` | The required isolation environment is not available | Refuse to run untrusted code |
| `FRAME_NOT_PRESENTED` | The target frame did not reach the verified presentation contract | Retry within limits, fall back to the baseline path, or report the failure |
| `SOURCE_TIME_OUT_OF_RANGE` | A request for source or media exceeds the available span | Explicitly trim, hold, or re-arrange; do not clamp silently |
| `EVIDENCE_SNAPSHOT_MISMATCH` | The evidence does not belong to the requested version or quality | Keep as history; re-request the correct evidence |
| `EXPORT_VALIDATION_FAILED` | The output does not satisfy the contract (for an export job, `error.details.failed[].problems` lists the specific checks; for file transcoding, when the output's duration, video track, encoding, or height does not match, it is `details.problems`) | Keep the previous successful output; report the specific checks |
| `EXPORT_KIND_UNSUPPORTED` | This version cannot export this kind (`details.supported`). Placed in `RpcError.details.code`, with `RpcError.code` set to `invalid-request` | Choose a supported kind; do not assemble the cut another way |

| `EXPORT_DESTINATION_UNWRITABLE` | The target directory does not exist, is not an absolute path, is not writable, or cannot be written to when publishing | Choose a writable directory, or have the user change the permissions |

At pre-check placed in `RpcError.details.code` (`RpcError.code` is `conflict`); at execution it is the job's `error.code` | The user installs ffmpeg, builds the Render Worker, or sets the environment variable; nothing is downloaded automatically |

| `MEDIA_TOOL_UNAVAILABLE` | The fixed flow (file transcoding) cannot find ffmpeg / ffprobe, or it cannot run properly (export uses `EXPORT_TOOL_MISSING`). Found at submission, it is placed in `RpcError.details.code` (`conflict`); found during execution, it is the job's `error.code` | Install ffmpeg, or specify it with `CUCCUT_FFMPEG` / `CUCCUT_FFPROBE`, then retry |
| `SUBTITLE_FILE_INVALID` | The subtitle file cannot be read for translation: it is not a strictly parseable SRT / WebVTT (`details.line`, `details.problem`), or no cue has any text. At submission it is `invalid-request` (`details.code`, `details.file`); on retry, if the source file has been corrupted, it is the job's `error.code` | Fix the file or choose another; do not retry the same input |

`LIBRARY_*` codes are placed in `RpcError.details.code`, and `RpcError.code` is the value in parentheses.

Warnings (`JobRecord.warnings`) for subtitle file translation: `SUBTITLE_MARKUP_STRIPPED` (inline markup of the source was not carried into the translation), `SUBTITLE_SETTINGS_DROPPED` (when converting WebVTT to SRT, the cue settings and the NOTE / STYLE / REGION blocks could not be kept).

The `ASSET_MISSING` / `ASSET_CHANGED` in export pre-checks are likewise placed in `RpcError.details.code` (`RpcError.code` is `conflict`): the linked asset's content digest is checked once at pre-check. After queuing, if the file's length or modification time has changed, it is checked again before execution, and on a mismatch the job fails with the same error code.

### 11.5 Time

| Error code | Condition | Prescribed recovery |
| --- | --- | --- |
| `TIME_DOMAIN_MISMATCH` | Raw frame, time domain mismatch, or source time mixed with sequence time | Rebuild the command after reading the scope and `Rate` |
| `INVALID_TIME_VALUE` | Invalid decimal, negative absolute position, zero timebase | Correct the input; do not guess silently |
| `TIME_ARITHMETIC_OVERFLOW` | Input or intermediate rational exceeds the contract limit | Reject and report the field and limit; do not fall back to floating point |
| `TIME_NOT_ON_FRAME_GRID` | A request for `exact-frame` is not on a valid boundary | Give candidate boundaries; the caller resubmits with an explicit policy |
| `TIME_RANGE_COLLAPSED` | After quantization, length is zero, out of bounds, or the safe interval is broken | Change the range or policy; do not auto-fill frames, do not widen the deletion |
| `EXPORT_RANGE_NOT_ON_OUTPUT_GRID` | Output of `exact-grid` is not divisible | Explicitly change the range or frame rate, or choose `cover-range` |
| `EDIT_FPS_CHANGE_UNSUPPORTED` | The `preserve` policy, or a capability that relies on dependency remapping, is not verified | Close this operation; do not use the export frame rate as a substitute write |

### 11.6 Rules

- Numeric mismatches do not bypass the normal checks for version conflicts, permissions, locks and targets.
- Subdividing error codes does not mean adding a new peer background service.
- An evidence hash is not source authentication; a contract hash is not permission; a resource lease is not task authorization.
- When adding an error code, you must give both its condition and its prescribed recovery.

### 11.7 CLI exit codes and `next`

The CLI writes both success and failure as envelopes: success `{ ok: true, result, next?, runtime? }` (`next` appears only once, at the top level of the envelope: a `next` in the result is lifted to the top level and not repeated inside `result`), failure `{ ok: false, error, runtime? }`. `error` has the same shape as the error object of `catalog.call`. Problems the CLI detects itself (arguments, missing `--yes`, Runtime unavailable) also use this shape. `runtime: { started: true }` means this call auto-started the Runtime. Exit codes are looked up from one table keyed by error code (`apps/cli/src/envelope.ts`), shared by derived commands, meta commands and management commands ([Agent capability surface design §5.2](../design/agent-surface/agent-surface-design.md#52-exit-codes)):

| Exit code | Meaning | Error codes |
| --- | --- | --- |
| 0 | Success, including a task waited on to completion | — |
| 1 | Failure or cancellation: tool or engine rejected; task terminal state `failed` / `cancelled` / `interrupted` / `needs-reconciliation`; wait timed out (`WAIT_TIMEOUT`, task keeps running); management command did not succeed (`COMMAND_FAILED` etc.); Runtime not owned by this CLI to stop, or still in use by someone; skill doc not found or malformed (`catalog.agentSkill`) | `RUNTIME_NOT_OWNED` `RUNTIME_IN_USE` `AGENT_SKILL_NOT_FOUND` `AGENT_SKILL_INVALID`; any error code not listed in this table is 1 |
| 2 | The user must first do something: configure a capability, authorize or set a budget, consent to or install an external tool, log in, authorize a voice; output carries `remedy` and `next`, and the Agent tells the user rather than bypassing it itself | `CAPABILITY_NOT_CONFIGURED` `DUB_SEPARATION_NOT_CONFIGURED` `MODELS_DIR_MISSING` `CREDENTIAL_UNAVAILABLE` `AUTHENTICATION_REQUIRED` `OFFLINE_STRICT` `GRANT_REQUIRED` `GRANT_REVOKED` `BUDGET_EXCEEDED` `BUDGET_UNVERIFIABLE` `TASK_BUDGET_EXCEEDED` `TASK_BUDGET_UNVERIFIABLE` `TOOL_UNAVAILABLE` `TOOL_CONSENT_REQUIRED` `TOOL_UPDATE_CONFIRM_REQUIRED` `TOOL_UPDATE_MANUAL` `MEDIA_TOOL_UNAVAILABLE` `EXPORT_TOOL_MISSING` `LINK_LOGIN_REQUIRED` `LINK_COOKIES_UNAVAILABLE` `LINK_TOOL_UPDATE_REQUIRED` `VOICE_CONSENT_REQUIRED` `VOICE_CLONE_REQUIRED` |
| 3 | Runtime unavailable: cannot connect; none running with `--no-start`; cannot be started; protocol or interface version differs; offline with neither a snapshot nor a Runtime | `RUNTIME_UNAVAILABLE` `RUNTIME_START_FAILED` `PROTOCOL_MISMATCH` `INTERFACE_VERSION_MISMATCH` `CATALOG_UNAVAILABLE` |
| 4 | Wrong arguments, or a command that needs confirmation lacks `--yes` (no default consent outside a terminal; `models install` without `--yes` only reports the model pack and size and does not download) | `INVALID_ARGUMENTS` `UNKNOWN_COMMAND` `UNKNOWN_TOOL` `CONFIRMATION_REQUIRED` |

When a task ends as failed or cancelled, the table is looked up by the task's error code, so the result is always 1 or 2. The gateway's `RpcError` takes `details.code`; when that is absent, `code` is converted to uppercase with underscores and looked up. Ctrl-C first cancels the task being waited on; a second press exits immediately (130).

`next` is the suggested next step. When a tool writes `next`, it uses the tool name (MCP style, `jobs_wait`, `models_install`). For `catalog.call` on a `cli` connection, the `<noun>_<verb>` in the catalog within the top-level `next` of both results and errors is replaced with `cuccut <noun> <verb>` (multi-word verb `_` → `-`); first-level verbs are the same on both sides and are not changed; other subjects are kept as they are. `next` written by the CLI itself (`cuccut runtime ensure`, `cuccut jobs wait <jobId>`) is already a command.

## 12. Examples

The following are examples of the target contract. `actor` is injected by the server.

### 12.1 Moving an instance by seconds

In the video, the edit frame rate of the `main` sequence is 30000/1001, and the baseline version is 7.

Request:

```json
{
  "protocolVersion": 1,
  "requestId": "req-time-001",
  "commandId": "move-scene-2-to-10s",
  "method": "edits.apply",
  "videoId": "video-demo",
  "expectedRevision": "7",
  "payload": {
    "operations": [{
      "type": "moveItem",
      "itemId": "scene-2",
      "sequenceId": "main",
      "at": { "unit": "seconds", "value": "10.000" },
      "alignment": "nearest-frame"
    }]
  }
}
```

Receipt (excerpt):

```json
{
  "transactionId": "tx-time-001",
  "videoRevision": "8",
  "timeResolution": [{
    "domain": { "kind": "sequence", "sequenceId": "main" },
    "sequenceRevision": "5",
    "editFps": { "num": 30000, "den": 1001 },
    "requested": { "unit": "seconds", "value": "10.000" },
    "requestedTime": { "ticks": "10", "timescale": 1 },
    "actualFrame": 300,
    "actualTime": { "ticks": "1001", "timescale": 100 },
    "delta": { "ticks": "1", "timescale": 100 },
    "policy": "nearest-frame"
  }]
}
```

- The video revision and the sequence revision are two separate version axes; in the example above, 8 and 5 need not be equal.
- The actual landing point is frame 300, i.e. 10.010 seconds, 10 milliseconds later than requested. This is quantization to the frame grid.
- To output at 60 fps, declare `fps: { "num": 60, "den": 1 }` in the frozen export; do not call `changeSequenceFrameRate`.
- “10 seconds, 600 frames” holds only when the frozen range really is 10 seconds; do not write the visual 10.010 seconds as 10 seconds.

### 12.2 Accepting a talking-head cut suggestion

This is the **internal transaction** that the Runtime hands to the engine. Public clients only submit `commandId`, `expectedRevision` and domain operations, and cannot declare `actor` themselves.

```json
{
  "id": "tx-cut-001",
  "videoId": "video-demo",
  "baseVideoRevision": "7",
  "idempotencyKey": "accept-cut-proposal-001-v1",
  "actor": { "kind": "agent", "id": "agent-session-1" },
  "readSet": [
    { "entityId": "main", "revision": "4" },
    { "entityId": "talk-full", "revision": "2" },
    { "entityId": "speech-zh", "revision": "1" }
  ],
  "label": "删除已确认的长停顿",
  "operations": [{
    "type": "acceptCutSuggestions",
    "sequenceId": "main",
    "proposalId": "cut-proposal-001",
    "suggestionIds": ["cut-sl-w12"]
  }]
}
```

The time range comes from the source range that this suggestion recorded in the proposal. The engine compiles it into cut points, and this request cannot override it with a separate set of seconds (§4.2). To change the range, use `addCuts` and put the suggestion's ID in `ref`. How the other instances move is governed by each one's `followPolicy` (video format spec §3.16). When a locked track or instance would have to move, the whole transaction is rejected (`TARGET_LOCKED`).

Receipt:

```json
{
  "transactionId": "tx-cut-001",
  "status": "committed",
  "previousRevision": "7",
  "videoRevision": "8",
  "createdIds": ["talk-a", "talk-b"],
  "updatedIds": ["main", "caption-zh"],
  "deletedIds": ["talk-full"],
  "lineage": { "talk-full": ["talk-a", "talk-b"] },
  "impact": {
    "oldDurationFrames": 360,
    "newDurationFrames": 300,
    "captionProjection": "recomputed",
    "translationUnitsStale": [],
    "dubbingUnitsStale": [],
    "orphanedAnchors": []
  },
  "undo": { "available": true, "token": "undo-tx-cut-001" }
}
```

This example deletes a pause between sentences; the content of the translated sentences does not change, so the stale lists are empty. The numbers agree with the recomputation example in video format spec §6.6: a 12-second, 30 fps clip with 2 seconds removed goes from 360 frames to 300 frames.

### 12.3 Changing the parameters of a code composition

```json
{
  "type": "setCodeParameters",
  "itemId": "earth-instance-1",
  "expectedBundleRef": { "id": "earth", "revision": "3" },
  "values": { "rotationSpeed": 0.15 },
  "scope": "selected-instance"
}
```

Fields that the parameter Schema does not allow fail immediately. To replace the source, use `replaceCodeBundle`; do not reuse this operation.

### 12.4 Submitting a dubbing computation

```json
{
  "capability": "tts",
  "inputVersionRefs": [
    { "id": "dubbing-unit-3-script", "revision": "2" }
  ],
  "parameters": {
    "language": "en-US",
    "voiceBindingId": "speaker-1-en",
    "output": { "sampleRate": 48000, "channels": 1 }
  },
  "permissionGrant": "grant-tts-17",

```

The result of a computation does not modify the timeline directly. Only after its real duration has been verified and it has passed through the engine's transaction may “Applied” be shown.

### 12.6 Replacing a code picture in place

The lower-third subtitle bar changed color. After it is repackaged as version 2, a new pre-render is baked and imported as an asset, the instance on the timeline is swapped to the new version (code bundle spec §3.3). The agent reaches this step through `replace` in `compositions_import`.

```json
{
  "type": "replaceCodeBundle",
  "itemId": "lower-third-1",
  "assetRef": { "id": "asset-lower-third-v2", "revision": "1" },
  "prerender": { "id": "asset-lower-third-v2-prerender", "revision": "1" }
}
```

Receipt (excerpt):

```json
{
  "updatedIds": ["lower-third-1"],
  "impact": {
    "codeEdits": [{
      "itemId": "lower-third-1",
      "layer": "source",
      "previousBundleRef": { "id": "asset-lower-third-v1", "revision": "1" },
      "bundleRef": { "id": "asset-lower-third-v2", "revision": "1" },
      "previousPrerender": { "id": "asset-lower-third-v1-prerender", "revision": "1" },
      "prerender": { "id": "asset-lower-third-v2-prerender", "revision": "1" },
      "oldDurationFrames": 120,
      "newDurationFrames": 90
    }]
  }
}
```

- Instance ID, track, start, geometry and opacity, name, effects and keyframes are unchanged; `timeMap` returns to a linear mapping starting from 0.
- The new version is 30 frames shorter, so the instance is trimmed from its tail; `oldDurationFrames` and `newDurationFrames` make the trim visible. If the new version is longer and collides with a later instance on the same track, it is rejected with `TIMELINE_OVERLAP`, and `recovery` suggests running `moveItem` or `deleteItems` first.
- If the instance has parameters and the new manifest removes or changes `parametersSchemaRef`, `parameterValues` must also be supplied; otherwise it is rejected with `INVALID_OPERATION` (`details.rule: "parameters-incompatible"`).

### 12.7 Pruning superseded old versions

Continuing from §12.6: the code package of version 1 and its prerendered stand-in are no longer referenced. `assets_prune` (without `apply`) lists them and marks each as the counterpart of the other. Once you confirm there will be no further rollback, listing only the code package is also enough to delete the pair.

```json
{ "type": "removeAssets", "assetIds": ["asset-lower-third-v1"] }
```

Receipt (excerpt):

```json
{
  "deletedIds": ["asset-lower-third-v1", "asset-lower-third-v1-prerender"],
  "impact": { "removedAssets": ["asset-lower-third-v1", "asset-lower-third-v1-prerender"] }
}
```

- If the listed asset is version 2 (instances still use it), the whole operation is rejected: `INVALID_OPERATION`, `details: { "rule": "asset-in-use", "usedBy": { "asset-lower-third-v2": ["lower-third-1"] } }`.
- Records only: undo this operation and both assets come back unchanged; the bytes are reclaimed later by GC.
